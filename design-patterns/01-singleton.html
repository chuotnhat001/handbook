Singleton Pattern

Đảm bảo một class chỉ có duy nhất một instance và cung cấp điểm truy cập toàn cục

Nguồn: Design Patterns — Creational Pattern
Tư duy cốt lõi Singleton là "nguồn sự thật duy nhất" — giống như đồng hồ trong phòng thi, tất cả mọi người nhìn vào cùng một chiếc để không xảy ra tranh cãi về thời gian.

Vấn đề Singleton giải quyết

Không có Singleton, tạo nhiều instance ApplicationSettings từ các màn hình khác nhau gây ra:

  • Data conflicts: Một phần ứng dụng dùng tiếng Việt, phần khác dùng tiếng Anh do đọc config khác nhau
  • Resource waste: Mỗi instance đọc file và parse JSON lại từ đầu — tốn tài nguyên
  • Loss of control: Không có "single source of truth" cho cấu hình

Cấu trúc

Ba yếu tố cốt lõi của Singleton:

Thành phầnVai trò
private static instanceLưu trữ instance duy nhất của class
private constructorChặn bên ngoài tạo instance mới bằng new
public static getInstance()Điểm truy cập được kiểm soát duy nhất

Triển khai

Cách 1: Lazy Initialization

Tạo instance chỉ khi được yêu cầu lần đầu tiên:

public class Singleton {
    private static Singleton instance;

    private Singleton() {
        // private constructor — chặn khởi tạo từ bên ngoài
    }

    public static Singleton getInstance() {
        if (instance == null) {
            instance = new Singleton();
        }
        return instance;
    }
}
Lưu ý Lazy initialization không thread-safe trong môi trường multi-threaded — cần thêm synchronized hoặc dùng double-checked locking.

Cách 2: Eager Initialization

Tạo instance ngay khi class được load vào JVM:

public class Singleton {
    private static final Singleton instance = new Singleton();

    private Singleton() {}

    public static Singleton getInstance() {
        return instance;
    }
}

Ưu điểm: Thread-safe mặc định nhờ JVM class loading mechanism. Code đơn giản hơn.

Nhược điểm: Instance được tạo dù có dùng hay không — tốn memory nếu object nặng.

Kiểm tra tính duy nhất

Singleton s1 = Singleton.getInstance();
Singleton s2 = Singleton.getInstance();
System.out.println(s1 == s2); // Luôn in ra: true

Ưu điểm & Nhược điểm

Ưu điểm

  • Đảm bảo chỉ có một instance — tránh conflict dữ liệu
  • Tiết kiệm tài nguyên khi dùng shared resource (connection pool, cache)
  • Global access point tiện lợi — không cần truyền object qua nhiều tầng
  • Lazy initialization tiết kiệm memory khi object không được dùng ngay

Nhược điểm

  • Khó test: Global state làm unit test phức tạp — cần cleanup giữa các test, khó mock
  • Vi phạm SRP: Class vừa quản lý logic nghiệp vụ vừa quản lý vòng đời của chính nó
  • Coupling cao: Code phụ thuộc trực tiếp vào Singleton, khó thay thế
  • Không cần thiết trong modern frameworks: Spring Boot tự quản lý singleton scope qua DI

Khi nào nên dùng

Phù hợp Logger, Configuration Manager, Caching, Database Connection Pool, Thread Pool Manager
Tránh dùng Không dùng như "túi đựng đồ" để truyền biến giữa các màn hình/module — dẫn đến Spaghetti Code. Không thay thế cho DI trong các dự án Spring/Jakarta EE.

Ví dụ thực tế

ApplicationSettings — Quản lý cấu hình ứng dụng

Vấn đề: Màn hình A tạo new ApplicationSettings() đọc file config → ngôn ngữ = "vi". Màn hình B tạo instance khác → ngôn ngữ = "en". Kết quả: ứng dụng hiển thị hai ngôn ngữ lẫn lộn.

Giải pháp: Tất cả màn hình đều gọi ApplicationSettings.getInstance() — nhận cùng một object, cùng trạng thái, không conflict.
