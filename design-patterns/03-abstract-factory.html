Abstract Factory Pattern

Tạo ra các họ object liên quan mà không chỉ định class cụ thể của chúng

Nguồn: Design Patterns — Creational Pattern
Tư duy cốt lõi Khác với Factory Method (tạo 1 sản phẩm), Abstract Factory tạo nhiều sản phẩm cùng họ một lúc, đảm bảo tính tương thích giữa chúng. "Program to an interface, not an implementation."

Cấu trúc

Thành phầnVai trò
AbstractFactoryInterface khai báo các phương thức tạo sản phẩm trừu tượng
ConcreteFactoryTriển khai cụ thể, mỗi factory tương ứng với một họ sản phẩm
AbstractProductInterface cho từng loại sản phẩm
ConcreteProductTriển khai cụ thể của AbstractProduct
ClientLàm việc chỉ với interface, không biết lớp cụ thể

Triển khai

Ví dụ: Nhà hàng gọi món

Mỗi món có bộ nguyên liệu riêng (protein, carbohydrate, rau) nhưng quy trình chuẩn bị giống nhau.

// Abstract Products
public interface IProtein {
    void prepare();
}

public interface ICarbohydrate {
    void prepare();
}

public interface IVegetable {
    void prepare();
}

// Concrete Products cho món Lẩu
public class Beef implements IProtein {
    public void prepare() {
        System.out.println("Chuẩn bị thịt bò thái lát cho lẩu");
    }
}

public class RiceNoodle implements ICarbohydrate {
    public void prepare() {
        System.out.println("Chuẩn bị bún gạo cho lẩu");
    }
}

// Concrete Products cho món Phở
public class Chicken implements IProtein {
    public void prepare() {
        System.out.println("Chuẩn bị gà cho phở");
    }
}

public class PhoNoodle implements ICarbohydrate {
    public void prepare() {
        System.out.println("Chuẩn bị bánh phở");
    }
}

Abstract Factory và Concrete Factories

// Abstract Factory
public interface FoodFactory {
    IProtein createProtein();
    ICarbohydrate createCarbohydrate();
    IVegetable createVegetable();
}

// Factory cho món Lẩu
public class LauFactory implements FoodFactory {
    public IProtein createProtein() {
        return new Beef();
    }
    public ICarbohydrate createCarbohydrate() {
        return new RiceNoodle();
    }
    public IVegetable createVegetable() {
        return new Cabbage();
    }
}

// Factory cho món Phở
public class PhoFactory implements FoodFactory {
    public IProtein createProtein() {
        return new Chicken();
    }
    public ICarbohydrate createCarbohydrate() {
        return new PhoNoodle();
    }
    public IVegetable createVegetable() {
        return new BeanSprouts();
    }
}

Client sử dụng

public class Restaurant {
    private FoodFactory factory;

    public Restaurant(FoodFactory factory) {
        this.factory = factory;
    }

    public void prepareMeal() {
        IProtein protein = factory.createProtein();
        ICarbohydrate carb = factory.createCarbohydrate();
        IVegetable veg = factory.createVegetable();

        protein.prepare();
        carb.prepare();
        veg.prepare();
    }
}

// Chuyển từ lẩu sang phở — chỉ đổi factory
Restaurant lau = new Restaurant(new LauFactory());
lau.prepareMeal();

Restaurant pho = new Restaurant(new PhoFactory());
pho.prepareMeal();

Ưu điểm & Nhược điểm

Ưu điểm

  • Tính tương thích đảm bảo: Sản phẩm từ cùng factory luôn tương thích nhau
  • Open/Closed Principle: Thêm họ sản phẩm mới chỉ cần tạo ConcreteFactory mới
  • Single Responsibility: Code tạo đối tượng tập trung tại factory
  • Dễ hoán đổi: Thay toàn bộ họ sản phẩm chỉ bằng cách truyền factory khác

Nhược điểm

  • Phức tạp hóa codebase: Số lượng interface và class tăng đáng kể
  • Khó mở rộng kiểu sản phẩm: Thêm loại sản phẩm mới yêu cầu sửa AbstractFactory và tất cả ConcreteFactory
  • Over-engineering: Với hệ thống nhỏ, pattern này quá phức tạp

Khi nào nên dùng

Nên dùng khi
  • Hệ thống cần làm việc với nhiều họ sản phẩm và phải đảm bảo tính tương thích
  • Muốn cung cấp thư viện sản phẩm mà che giấu implementation
  • Cần dễ dàng hoán đổi toàn bộ họ sản phẩm (đổi theme, database driver, UI platform)
Không nên dùng khi Chỉ có một họ sản phẩm duy nhất (dùng Factory Method đơn giản hơn). Cần thường xuyên thêm loại sản phẩm mới vào factory.

UI Cross-platform
