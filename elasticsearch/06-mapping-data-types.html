Mapping & Data Types

text vs keyword, object vs nested, multi-fields — thiết kế schema đúng ngay từ đầu

Nguồn: Elastic — Mapping, Elastic — Field Data Types

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Hiểu mapping là gì, phân biệt dynamic và explicit mapping. Chọn đúng field type cho từng loại dữ liệu, đặc biệt là text vs keyword và object vs nested. Dùng multi-fields và copy_to. Nắm các mapping parameters quan trọng và lý do không thể đổi type field đã tồn tại.

Kiến Thức Tiên Quyết

  • Bài 02: Lucene — Inverted index, mỗi field có index riêng
  • Bài 05: Document CRUD — Index document, reindex
  • JSON — Kiểu dữ liệu, object lồng nhau, array

Mapping Là Gì

Mapping là schema của một index — định nghĩa các field và cách mỗi field được lưu trữ, index và phân tích. Nó quyết định bạn tìm kiếm, sort, aggregate được gì và nhanh ra sao.

# Xem mapping hiện tại
GET /products/_mapping
Tư duy cốt lõi Mapping giống schema của bảng SQL, nhưng linh hoạt hơn: ES có thể tự suy ra type (dynamic), và một field text có thể vừa full-text search vừa có sub-field keyword để sort/aggregate. Thiết kế mapping đúng từ đầu quan trọng vì không đổi được type sau khi tạo.

Dynamic vs Explicit Mapping

Dynamic mapping

Khi index document vào field chưa khai báo, ES tự đoán type. Tiện cho prototyping nhưng rủi ro ở production (đoán sai, mapping phình to).

Giá trị JSONType ES tự đoán
"hello"text + sub-field keyword
123long
123.45float
trueboolean
"2026-01-15"date (nếu khớp format)

Explicit mapping

Khai báo field tường minh khi tạo index — kiểm soát hoàn toàn, khuyến nghị cho production.

PUT /products
{
  "mappings": {
    "properties": {
      "name":        { "type": "text" },
      "sku":         { "type": "keyword" },
      "price":       { "type": "scaled_float", "scaling_factor": 100 },
      "in_stock":    { "type": "boolean" },
      "created_at":  { "type": "date" }
    }
  }
}

Kiểm soát dynamic

dynamicHành vi khi gặp field mới
true (mặc định)Tự thêm field mới vào mapping
runtimeThêm như runtime field (tính lúc query, không index)
falseField mới bị bỏ qua khỏi index (vẫn lưu trong _source)
strictTừ chối document chứa field lạ (ném lỗi)

Dynamic Templates

Quy tắc áp type cho field mới theo pattern tên hoặc kiểu dữ liệu — hữu ích khi field động nhưng muốn kiểm soát.

PUT /logs
{
  "mappings": {
    "dynamic_templates": [
      {
        "strings_as_keyword": {
          "match_mapping_type": "string",
          "mapping": { "type": "keyword" }
        }
      }
    ]
  }
}
# Mọi string mới → keyword thay vì text+keyword

text vs keyword — Khác Biệt Quan Trọng Nhất

textkeyword
Phân tích (analyze)Có — tách thành tokensKhông — lưu nguyên giá trị
Dùng choFull-text search (match)Exact match, sort, aggregate (term)
Ví dụ querymatchterm, terms
Sort/aggregateKhông (trừ khi bật fielddata — tốn RAM)Có (qua doc_values)
Lỗi kinh điển Dùng text cho field email/status/tag rồi ngạc nhiên vì không sort/aggregate được, hoặc term query không khớp (vì text đã bị lowercase + tokenize). Quy tắc: text để đọc/tìm kiếm tự nhiên, keyword để lọc/sort/nhóm chính xác.

Numeric, Date, Boolean

  • Numeric: long, integer, short, byte, double, float, half_float, scaled_float. Chọn type nhỏ nhất đủ dùng để tiết kiệm.
  • scaled_float: lưu số thực dưới dạng long × scaling_factor — lý tưởng cho tiền tệ (chính xác, nhỏ gọn).
  • date: hỗ trợ nhiều format qua format parameter; lưu nội bộ dạng epoch millis.
"created_at": {
  "type": "date",
  "format": "yyyy-MM-dd'T'HH:mm:ss||yyyy-MM-dd||epoch_millis"
}
Số dùng để lọc range vs chỉ để hiển thị Nếu một "số" như mã bưu chính, số điện thoại chỉ cần exact match (không range/toán học), hãy dùng keyword — nhanh hơn và đúng ngữ nghĩa hơn numeric.

object vs nested — Cạm Bẫy Mảng Object

Field object (mặc định cho JSON lồng nhau) bị ES flatten. Với mảng object, điều này làm mất quan hệ giữa các field trong cùng một phần tử.

# Document
{ "user": [ { "first": "Alice", "last": "Smith" },
            { "first": "Bob", "last": "Jones" } ] }

# Với type object → ES flatten thành:
# user.first: ["Alice", "Bob"]
# user.last:  ["Smith", "Jones"]
# → Query "first=Alice AND last=Jones" SAI khớp! (quan hệ bị mất)

Dùng type nested để giữ mỗi phần tử mảng như một document ẩn riêng, bảo toàn quan hệ:

PUT /blog
{ "mappings": { "properties": {
  "comments": { "type": "nested",
    "properties": { "author": {"type":"keyword"}, "text": {"type":"text"} }
  }
}}}

# Phải dùng nested query để truy vấn
GET /blog/_search
{ "query": { "nested": { "path": "comments",
  "query": { "bool": { "must": [
    { "match": { "comments.author": "alice" } },
    { "match": { "comments.text": "great" } }
  ]}}}}}
Chi phí của nested nested mạnh nhưng tốn kém (mỗi phần tử = 1 Lucene doc ẩn) và cần query đặc biệt. Chỉ dùng khi thực sự cần giữ quan hệ trong mảng object. Ngoài ra có flattened cho object nhiều key động mà không muốn nổ mapping.

Specialized Types

TypeDùng cho
geo_pointTọa độ lat/lon — query khoảng cách, bounding box
geo_shapeHình học phức tạp (polygon, line)
ipĐịa chỉ IPv4/IPv6 — query theo CIDR range
completionAutocomplete / search-as-you-type (suggester)
dense_vectorVector embedding — semantic search, kNN
flattenedObject nhiều key động, index cả cây như một field

Multi-fields & copy_to

Một field có thể được index theo nhiều cách cùng lúc. Phổ biến nhất: text cho full-text + sub-field keyword cho sort/aggregate.

"title": {
  "type": "text",
  "fields": {
    "keyword": { "type": "keyword", "ignore_above": 256 },
    "english": { "type": "text", "analyzer": "english" }
  }
}
# Query full-text: match trên "title"
# Sort/aggregate/exact: dùng "title.keyword"

copy_to gom nhiều field vào một field tổng hợp để search chung:

"first_name": { "type": "text", "copy_to": "full_name" },
"last_name":  { "type": "text", "copy_to": "full_name" },
"full_name":  { "type": "text" }
# Search "full_name" khớp cả first + last

Mapping Parameters Quan Trọng

ParameterÝ nghĩa
indexfalse = không tạo inverted index (không search được field, nhưng vẫn lưu/aggregate) → tiết kiệm
doc_valuestrue mặc định — cột lưu cho sort/aggregate. Tắt nếu field không cần sort/agg để tiết kiệm disk
normsLưu thông tin length-normalization cho scoring. Tắt cho field không cần relevance scoring
analyzerAnalyzer áp cho field text (xem Bài 07)
ignore_abovekeyword dài hơn N ký tự thì không index (tránh key quá dài)
enabledfalse = lưu nhưng không xử lý gì cả (chỉ trong _source)

Giới Hạn & Vì Sao Phải Reindex

Không thể đổi type của field đã tồn tại. Lý do: inverted index và doc_values đã được xây theo type cũ; đổi type nghĩa là xây lại toàn bộ cấu trúc → bắt buộc tạo index mới với mapping đúng rồi reindex (Bài 05).

Có thể thêm field mới vào mapping, nhưng không sửa/xóa field cũ.

Mapping explosion Dynamic mapping + dữ liệu có key động (vd field đặt theo giá trị) → mapping phình hàng nghìn field → cluster state khổng lồ, cluster chậm/sập. ES giới hạn mặc định index.mapping.total_fields.limit: 1000. Nếu chạm giới hạn, đừng vội nâng — xem lại thiết kế (dùng flattened hoặc dynamic: false).

Bài Lab: Thiết Kế Mapping Cho E-commerce Product Catalog

Yêu cầu

Thiết kế mapping cho catalog sản phẩm: tìm kiếm full-text theo tên/mô tả, lọc theo danh mục/tag, sort theo giá, lọc range giá, và truy vấn biến thể (variants) giữ quan hệ.

PUT /ecommerce-products
{
  "mappings": {
    "properties": {
      "name":        { "type": "text",
                       "fields": { "keyword": { "type": "keyword", "ignore_above": 256 } } },
      "description": { "type": "text" },
      "sku":         { "type": "keyword" },
      "price":       { "type": "scaled_float", "scaling_factor": 100 },
      "category":    { "type": "keyword" },
      "tags":        { "type": "keyword" },
      "in_stock":    { "type": "boolean" },
      "created_at":  { "type": "date" },
      "location":    { "type": "geo_point" },
      "variants": {
        "type": "nested",
        "properties": {
          "color": { "type": "keyword" },
          "size":  { "type": "keyword" },
          "stock": { "type": "integer" }
        }
      }
    }
  }
}

Lý do thiết kế

  • name: text (search) + keyword (sort theo tên, aggregate)
  • price: scaled_float → chính xác tiền tệ, range query được
  • category/tags: keyword → filter & aggregate (facet)
  • variants: nested → giữ quan hệ color+size+stock trong từng biến thể
  • location: geo_point → tìm cửa hàng gần nhất
Xác minh thành công Index với mapping này cho phép: match trên name/description, term filter theo category/tags, range trên price, nested query trên variants, và geo_distance trên location — đủ cho một product search thực tế.

Checklist Kiến Thức

  • ☐ Chọn đúng text vs keyword cho từng use case

  • ☐ Phân biệt object vs nested và biết khi nào dùng nested

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Dùng text cho field cần sort/aggregate — Không sort/agg được (hoặc phải bật fielddata tốn RAM). Dùng keyword hoặc multi-field.
  • term query trên field text — Không khớp vì text đã tokenize + lowercase. Dùng keyword cho exact match.
  • Mảng object mà không dùng nested — Quan hệ giữa field bị mất, query sai khớp.
  • Để dynamic mapping ở production — ES đoán sai type, mapping phình. Dùng explicit mapping + dynamic templates.
  • Nâng total_fields.limit để "sửa" mapping explosion — Chữa triệu chứng, không chữa gốc. Xem lại thiết kế dữ liệu.
  • Mong đổi type field tại chỗ — Không được. Phải reindex sang index mới.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Production: luôn explicit mapping; dynamic: strict hoặc runtime cho field ngoài kế hoạch
  • text cho full-text, keyword cho filter/sort/aggregate; dùng multi-field khi cần cả hai
  • Dùng scaled_float cho tiền tệ; chọn numeric type nhỏ nhất đủ dùng
  • Chỉ dùng nested khi thực sự cần giữ quan hệ trong mảng object
  • Tắt doc_values/norms/index cho field không cần, để tiết kiệm disk
  • Thiết kế mapping cẩn thận từ đầu — đổi type nghĩa là reindex toàn bộ
