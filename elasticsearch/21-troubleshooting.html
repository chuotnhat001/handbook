Troubleshooting

Unassigned shard, circuit breaker, thread pool rejection, hot threads, slow log — quy trình chẩn đoán có hệ thống

Nguồn: Elastic — Troubleshooting, Elastic — Circuit Breaker Errors

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Áp dụng một quy trình chẩn đoán có thứ tự thay vì thử ngẫu nhiên. Dùng thành thạo bộ công cụ: Health Report, allocation explain, _cat, nodes stats, hot threads, tasks, slow log. Xử lý các sự cố phổ biến: cluster red, circuit breaker, thread pool rejection, CPU cao, query chậm. Biết các biện pháp cuối cùng và cái giá của chúng.

Quy Trình Chẩn Đoán

Triệu chứng → Phạm vi → Thay đổi gần đây → Bằng chứng → Giả thuyết → Sửa & xác minh
  1. Triệu chứng: chính xác là gì? "Search chậm" là p95 tăng từ 100 ms lên 3 s, hay timeout hoàn toàn?
  2. Phạm vi: toàn cluster, một node, một index, hay một loại query?
  3. Thay đổi gần đây: deploy mới, đổi mapping, tăng traffic, nâng cấp version, thêm dashboard? Phần lớn sự cố bắt nguồn từ một thay đổi
  4. Bằng chứng: thu thập từ API và log trước khi sửa. Restart làm mất bằng chứng
  5. Giả thuyết: một nguyên nhân cụ thể, kiểm chứng được
  6. Sửa và xác minh: một thay đổi mỗi lần, xác nhận triệu chứng biến mất, ghi lại nguyên nhân gốc
Tư duy cốt lõi Restart node thường làm triệu chứng tạm biến mất mà không sửa nguyên nhân, đồng thời xóa hot threads, task đang chạy, và trạng thái heap. Thu thập bằng chứng trước, restart sau, và chỉ khi có lý do.

Circuit Breaker

Circuit breaker từ chối request trước khi nó làm cạn heap và gây OutOfMemoryError. Client nhận lỗi HTTP 429 circuit_breaking_exception.

BreakerBảo vệGiới hạn mặc định
parentTổng bộ nhớ của mọi breaker và heap thực tế95% heap
requestCấu trúc dữ liệu tạm của một request (aggregation buckets)60% heap
fielddataFielddata cache40% heap
in_flight_requestsKích thước request đang truyền tới (bulk lớn)100% heap
GET /_nodes/stats/breaker?human&filter_path=nodes.*.name,nodes.*.breakers.*.estimated_size,nodes.*.breakers.*.tripped
GET /_cat/fielddata?v&s=size:desc

Thông báo lỗi cho biết breaker nào bị chạm và request cần bao nhiêu bộ nhớ, ví dụ: [parent] Data too large, data for [<http_request>] would be [16gb], which is larger than the limit of [15.2gb].

Đừng nâng giới hạn breaker Breaker bị chạm là triệu chứng của heap thật sự đang thiếu. Nâng giới hạn chỉ đổi lỗi 429 lấy OutOfMemoryError và node chết. Tìm nguyên nhân: aggregation quá nhiều bucket, bulk quá lớn, fielddata trên field text, quá nhiều shard trên node, hoặc heap quá nhỏ cho workload.

Thread Pool Rejection

Mỗi loại thao tác có thread pool với hàng đợi giới hạn. Khi hàng đợi đầy, request mới bị từ chối với HTTP 429 es_rejected_execution_exception.

GET /_cat/thread_pool/write,search,get?v&h=node_name,name,size,active,queue,queue_size,rejected,completed
  • write rejected: client gửi nhanh hơn cluster index được. Có thể do một node chậm hơn các node khác (hot spot), hoặc mọi node đều đã chạm trần (Bài 19)
  • search rejected: quá nhiều search đồng thời, hoặc search chậm làm thread bị chiếm lâu
  • Rejection chỉ trên một node: kiểm tra phân bổ shard có lệch không (một node giữ nhiều primary shard đang ghi)
429 là backpressure, không phải lỗi cần che giấu Client nên retry với exponential backoff khi nhận 429. Các client chính thức, Beats, Logstash đều làm vậy. Tăng queue_size chỉ làm request chờ lâu hơn và tốn thêm heap, không tăng năng lực xử lý.

CPU Cao & Hot Threads

# Những thread tốn CPU nhất trên mỗi node, kèm stack trace
GET /_nodes/hot_threads?threads=5&interval=500ms
GET /_nodes/es02/hot_threads

Output là văn bản. Đọc tên thread và các dòng stack trace đầu tiên để biết CPU đang dành cho việc gì:

Tên thread chứaĐang làmHướng tìm hiểu
[search]Thực thi querySlow log, Profile API, query wildcard/regex/script
[write]Index documentIngest pipeline nặng, mapping phức tạp, analyzer tốn kém
Lucene Merge ThreadGộp segmentRefresh quá dày, force merge trên index đang ghi
[management], [generic]Tác vụ quản trị, recoveryRecovery, rebalance, snapshot đang chạy
GC (thấy qua _nodes/stats/jvm)Thu gom rácÁp lực heap, xem mục circuit breaker
# Tìm và hủy task gây tải
GET /_tasks?actions=*search*&detailed=true&group_by=parents
POST /_tasks/<node_id>:<task_id>/_cancel

Query Chậm

  1. Tìm query: slow log (Bài 19), hoặc _tasks với detailed=true trong lúc nó đang chạy
  2. Xác định ai gửi: dùng header X-Opaque-Id từ ứng dụng, nó xuất hiện trong slow log và tasks
  3. Profile: chạy lại query với "profile": true để thấy clause tốn kém
  4. Đối chiếu nguyên nhân phổ biến:
    • Wildcard đầu chuỗi, regex, fuzzy trên field lớn
    • Script query hoặc script field trên nhiều document
    • Aggregation terms với cardinality cao, lồng nhiều tầng
    • Deep pagination
    • Khoảng thời gian rất rộng trên index không có ILM
    • Query chạm quá nhiều shard nhỏ
# Ứng dụng gắn định danh vào request
curl -H "X-Opaque-Id: orders-service/search-page" "$ES/orders/_search" ...

# Đặt timeout để một query không chiếm tài nguyên mãi
GET /orders/_search
{ "timeout": "5s", "query": { ... } }

# Chặn query tốn kém trên toàn cluster
PUT /_cluster/settings
{ "persistent": { "search.allow_expensive_queries": false } }

Bài Lab: Gây Lỗi, Chẩn Đoán & Sửa

Mỗi kịch bản dưới đây: tạo lỗi, chẩn đoán chỉ bằng API, rồi sửa. Dùng cluster lab có security từ Bài 13 (source .env để có $ES, $AUTH).

Kịch bản 1: Index red do allocation rule

curl $AUTH -X PUT "$ES/lab-red" -H 'Content-Type: application/json' -d '{
  "settings": { "number_of_shards": 1, "number_of_replicas": 0,
    "index.routing.allocation.require._name": "node-khong-ton-tai" } }'
curl $AUTH "$ES/_cluster/health?filter_path=status"            # red

# Chẩn đoán
curl $AUTH "$ES/_cat/shards/lab-red?v&h=index,shard,prirep,state,unassigned.reason"
curl $AUTH "$ES/_cluster/allocation/explain?pretty" -H 'Content-Type: application/json' \
  -d '{"index":"lab-red","shard":0,"primary":true}' | grep -A3 '"decider" : "filter"'

# Sửa
curl $AUTH -X PUT "$ES/lab-red/_settings" -H 'Content-Type: application/json' \
  -d '{"index.routing.allocation.require._name": null}'
curl $AUTH "$ES/_cluster/health?filter_path=status"

Kịch bản 2: Circuit breaker

# Hạ tạm request breaker xuống rất thấp để mô phỏng heap thiếu (CHỈ cho lab)
curl $AUTH -X PUT "$ES/_cluster/settings" -H 'Content-Type: application/json' \
  -d '{"persistent":{"indices.breaker.request.limit":"1kb"}}'

curl $AUTH "$ES/access-logs,lab-orders/_search?size=0" -H 'Content-Type: application/json' -d '{
  "aggs": { "x": { "terms": { "field": "_index", "size": 1000 } } } }'
# Mong đợi 429 circuit_breaking_exception: [request] Data too large ...

curl $AUTH "$ES/_nodes/stats/breaker?filter_path=nodes.*.breakers.request.tripped&pretty"

# Sửa: trả breaker về mặc định
curl $AUTH -X PUT "$ES/_cluster/settings" -H 'Content-Type: application/json' \
  -d '{"persistent":{"indices.breaker.request.limit":null}}'

Kịch bản 3: Query chậm và hot threads

# Bật slow log ngưỡng thấp cho index lab
curl $AUTH -X PUT "$ES/access-logs/_settings" -H 'Content-Type: application/json' \
  -d '{"index.search.slowlog.threshold.query.info":"0ms"}'

# Gửi một query tốn kém, có định danh
curl $AUTH -H "X-Opaque-Id: lab/slow-query" "$ES/access-logs/_search?size=0" -H 'Content-Type: application/json' -d '{
  "query": { "script": { "script": "doc[\"latency_ms\"].value * 2 > 100" } } }'

# Hot threads trong lúc chạy (cluster lab ít dữ liệu nên có thể không bắt kịp)
curl $AUTH "$ES/_nodes/hot_threads?threads=3"

# Tìm query trong slow log theo định danh X-Opaque-Id
docker compose exec es01 sh -c 'grep "lab/slow-query" logs/*_index_search_slowlog.json | tail -n 1'

# Sửa: trả slow log về ngưỡng hợp lý
curl $AUTH -X PUT "$ES/access-logs/_settings" -H 'Content-Type: application/json' \
  -d '{"index.search.slowlog.threshold.query.info":null}'
Slow log nằm trên node chứa shard Slow log được ghi trên node thực thi shard, không phải node nhận request. Nếu không thấy ở es01, xem GET /_cat/shards/access-logs?v để biết shard nằm ở node nào. Tên file và field trong log có thể khác nhau giữa các version, mở file để xem đúng cấu trúc.

Kịch bản 4: Mất node chứa primary

curl $AUTH -X PUT "$ES/lab-noderisk" -H 'Content-Type: application/json' -d '{
  "settings": { "number_of_shards": 1, "number_of_replicas": 0 } }'
NODE=$(curl -s $AUTH "$ES/_cat/shards/lab-noderisk?h=node" | tr -d '[:space:]')
echo "Primary nằm ở $NODE"
docker compose stop "$NODE"         # dừng node chứa primary (chọn node không phải es01 nếu có thể)

curl $AUTH "$ES/_cat/shards/lab-noderisk?v&h=shard,prirep,state,unassigned.reason"   # NODE_LEFT
docker compose start "$NODE"
curl $AUTH "$ES/_cluster/health/lab-noderisk?wait_for_status=green&timeout=2m&filter_path=status"
Nếu node chứa primary là es01 $ES trỏ vào es01 qua cổng 9200, nên dừng es01 thì lệnh curl tiếp theo không kết nối được. Khi đó tạo lại index với "index.routing.allocation.exclude._name": "es01" rồi làm lại kịch bản.
Xác minh thành công Bạn đã thấy bốn loại sự cố, đọc được lý do chính xác từ API (decider filter, breaker request, slow log có X-Opaque-Id, reason NODE_LEFT), và sửa mà không cần restart cluster hay đoán mò. Kịch bản 4 cho thấy vì sao index quan trọng cần ít nhất một replica.

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Restart ngay khi có sự cố: mất bằng chứng, nguyên nhân gốc vẫn còn và lặp lại.
  • Đổi nhiều thứ cùng lúc: không biết thay đổi nào đã sửa được lỗi, hay thay đổi nào gây lỗi mới.
  • Nâng giới hạn breaker, queue_size, max_shards: che triệu chứng, đổi lỗi nhẹ lấy lỗi nặng.
  • Dùng allocate_empty_primary khi còn snapshot: mất dữ liệu không cần thiết.
  • Không đọc log của node: nhiều nguyên nhân (OOM, disk lỗi, mạng) chỉ xuất hiện trong log.
  • Không ghi lại sau sự cố: đội vận hành gặp lại đúng sự cố đó mà không có tài liệu.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Viết runbook cho từng loại sự cố phổ biến, liên kết từ cảnh báo (Bài 18)
  • Bắt ứng dụng gửi X-Opaque-Id để truy vết nguồn gốc request
  • Thu thập log và slow log của Elasticsearch về monitoring cluster
  • Bật search.allow_expensive_queries: false và đặt timeout cho search ở cluster dùng chung
  • Giữ replica ≥ 1 và snapshot thường xuyên để không bao giờ cần đến biện pháp cuối cùng
  • Viết postmortem không đổ lỗi sau mỗi sự cố lớn
