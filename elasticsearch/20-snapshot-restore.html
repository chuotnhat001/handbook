Snapshot & Restore

Repository, snapshot incremental, restore, SLM, searchable snapshot, diễn tập disaster recovery

Nguồn: Elastic — Snapshot and Restore, Elastic — SLM

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Hiểu snapshot lưu gì và vì sao snapshot là incremental. Đăng ký repository trên filesystem chia sẻ hoặc object storage (S3, Azure, GCS). Tạo snapshot, restore toàn bộ hoặc một phần, restore sang tên khác. Tự động hóa bằng SLM với retention. Biết searchable snapshot dùng cho cold/frozen tier. Lập và diễn tập kế hoạch disaster recovery.

Snapshot Hoạt Động Thế Nào

Snapshot là bản sao lưu của index (hoặc toàn cluster) tại một thời điểm, lưu trong một repository nằm ngoài cluster.

  • Incremental: vì segment của Lucene là bất biến, snapshot chỉ copy những segment file mà repository chưa có. Snapshot đầu tiên copy toàn bộ, các snapshot sau chỉ copy phần mới
  • Mỗi snapshot vẫn độc lập logic: xóa một snapshot cũ không làm hỏng snapshot khác, file dùng chung chỉ bị xóa khi không còn snapshot nào tham chiếu
  • Không chặn ghi: snapshot chạy trong lúc cluster vẫn index bình thường, và phản ánh trạng thái tại lúc bắt đầu
  • Snapshot có thể bao gồm cluster state (template, ILM policy, pipeline, role...) qua include_global_state và feature states (index hệ thống của Kibana, security, Fleet...)
Replica không phải backup Replica bảo vệ khỏi mất node. Nó không bảo vệ khỏi xóa nhầm index, mapping sai ghi đè dữ liệu, ransomware, hay lỗi phần mềm: mọi thay đổi trên primary đều được sao chép ngay sang replica. Chỉ snapshot ở nơi khác mới khôi phục được những trường hợp này.
Không backup bằng cách copy thư mục data Copy thư mục path.data của node đang chạy cho ra bản sao không nhất quán và không khôi phục được đáng tin cậy. Snapshot API là cách backup duy nhất được hỗ trợ.

# fs: elasticsearch.yml trên MỌI master và data node, cần restart
path.repo: ["/mnt/es-snapshots"]

PUT /_snapshot/nfs_backup
{ "type": "fs", "settings": { "location": "/mnt/es-snapshots" } }

# S3: credential đặt trong keystore của mọi node, rồi reload
bin/elasticsearch-keystore add s3.client.default.access_key
bin/elasticsearch-keystore add s3.client.default.secret_key
POST /_nodes/reload_secure_settings

PUT /_snapshot/s3_backup
{ "type": "s3", "settings": { "bucket": "company-es-snapshots", "base_path": "prod-cluster" } }

# Kiểm tra mọi node đều ghi/đọc được repository
POST /_snapshot/s3_backup/_verify
Một repository, một cluster ghi Không để hai cluster cùng ghi vào một repository (cùng bucket + base_path), dữ liệu metadata sẽ hỏng. Cluster khác chỉ đọc thì đăng ký với "readonly": true.

Tạo Snapshot

# Snapshot một số index, chạy nền
PUT /_snapshot/s3_backup/snap-2026.10.28?wait_for_completion=false
{
  "indices": "orders-*,customers",
  "ignore_unavailable": true,
  "include_global_state": false,
  "metadata": { "taken_by": "ops", "reason": "before mapping change" }
}

# Snapshot toàn cluster kèm feature state
PUT /_snapshot/s3_backup/full-2026.10.28
{ "include_global_state": true, "feature_states": ["kibana", "security"] }

# Theo dõi
GET /_snapshot/s3_backup/snap-2026.10.28/_status
GET /_cat/snapshots/s3_backup?v&s=end_epoch
GET /_snapshot/s3_backup/_current
Trạng tháiÝ nghĩa
SUCCESSMọi shard đã snapshot xong
PARTIALMột số shard không snapshot được (ví dụ primary chưa cấp phát)
FAILEDSnapshot thất bại
IN_PROGRESSĐang chạy

Data stream được snapshot như một đơn vị: chỉ định tên data stream trong indices, mọi backing index đi kèm.

Restore

# Restore index sang tên mới, không đụng index đang chạy
POST /_snapshot/s3_backup/snap-2026.10.28/_restore
{
  "indices": "orders-2026.10",
  "rename_pattern": "(.+)",
  "rename_replacement": "restored-$1",
  "include_aliases": false,
  "index_settings": { "index.number_of_replicas": 0 }
}

# Restore đè index cũ: index cùng tên phải được đóng hoặc xóa trước
POST /customers/_close
POST /_snapshot/s3_backup/snap-2026.10.28/_restore
{ "indices": "customers" }

# Theo dõi tiến độ
GET /_cat/recovery?v&active_only=true
  • Restore sang tên khác là cách an toàn để lấy lại vài document bị xóa nhầm: restore → reindex phần cần → xóa index tạm
  • Restore toàn cluster sau thảm họa: cluster đích nên trống, restore với include_global_state: true và feature states
  • Cluster đích phải cùng version hoặc mới hơn (tương thích tối đa một major version, ví dụ snapshot 7.x restore được vào 8.x)

SLM

Snapshot Lifecycle Management tự động tạo snapshot theo lịch và xóa snapshot cũ theo retention.

PUT /_slm/policy/nightly
{
  "schedule": "0 30 1 * * ?",                 # 01:30 mỗi ngày (cron của Elasticsearch, giờ UTC)
  "name": "<nightly-snap-{now/d}>",
  "repository": "s3_backup",
  "config": {
    "indices": ["*"],
    "include_global_state": true,
    "feature_states": ["kibana", "security", "fleet"]
  },
  "retention": {
    "expire_after": "30d",
    "min_count": 7,
    "max_count": 60
  }
}

# Chạy thử ngay, xem lịch sử và thống kê
POST /_slm/policy/nightly/_execute
GET /_slm/policy/nightly
GET /_slm/stats
  • Cron gồm 6 trường: giây, phút, giờ, ngày, tháng, thứ. Lịch chạy theo UTC: 0 30 1 * * ? là 08:30 giờ Việt Nam
  • min_count giữ lại số snapshot tối thiểu dù đã quá hạn, tránh mất hết backup khi SLM ngừng chạy một thời gian
  • Kết hợp với ILM (Bài 12): action delete có wait_for_snapshot để chỉ xóa index sau khi SLM đã snapshot nó

Searchable Snapshots

Searchable snapshot cho phép search trực tiếp trên dữ liệu nằm trong repository, không cần restore. Đây là nền tảng của cold và frozen tier.

Chế độTierCách hoạt động
Fully mountedColdCopy toàn bộ dữ liệu về disk local của node. Search nhanh. Không cần replica vì snapshot đóng vai trò bản sao
Partially mountedFrozenChỉ giữ cache cục bộ, tải phần dữ liệu cần từ object storage khi search. Rất rẻ, search chậm hơn
# Thường dùng qua ILM
"cold":   { "min_age": "30d",  "actions": { "searchable_snapshot": { "snapshot_repository": "s3_backup" } } },
"frozen": { "min_age": "90d",  "actions": { "searchable_snapshot": { "snapshot_repository": "s3_backup" } } }

# Hoặc mount thủ công
POST /_snapshot/s3_backup/snap-2026.10.28/_mount?storage=shared_cache
{ "index": "orders-2026.01", "renamed_index": "frozen-orders-2026.01" }
License và repository Searchable snapshot cần license trả phí. Không được xóa snapshot đang được mount: index searchable snapshot mất nguồn dữ liệu. SLM retention tự bỏ qua các snapshot này.

Disaster Recovery

Khái niệmCâu hỏiPhụ thuộc vào
RPO (Recovery Point Objective)Chấp nhận mất tối đa bao nhiêu dữ liệu?Tần suất snapshot, hoặc CCR (Bài 22) cho RPO gần 0
RTO (Recovery Time Objective)Cần khôi phục trong bao lâu?Lượng dữ liệu, băng thông tới repository, có sẵn cluster dự phòng hay không
  • Repository nằm ở region khác hoặc bucket có replication sang region khác
  • Bật versioning và object lock (immutability) trên bucket để chống ransomware xóa backup
  • Tài khoản cluster dùng ghi snapshot không có quyền xóa vĩnh viễn bucket
  • Lưu riêng ngoài cluster: certificate, keystore, cấu hình elasticsearch.yml, file compose/manifest. Snapshot không chứa chúng
  • Diễn tập restore định kỳ và đo thời gian thật. Backup chưa từng restore thử là backup chưa được kiểm chứng
Tư duy cốt lõi Mục tiêu của backup là khôi phục được. Kế hoạch DR chỉ có giá trị khi đã chạy thử: biết restore mất bao lâu, cần những bước nào, và ai làm.

Bài Lab: Backup, Restore & Diễn Tập DR

Bước 1: Thêm repository fs dùng chung cho cluster lab

Mọi node phải thấy cùng một thư mục. Trong Docker Compose, dùng một volume chung mount vào tất cả node ES.

# Thêm vào environment của MỌI node ES (es01..es05)
      - path.repo=/usr/share/elasticsearch/snapshots
# Thêm vào volumes của MỌI node ES
      - snapshots:/usr/share/elasticsearch/snapshots
# Thêm vào mục volumes ở cuối file
  snapshots: {}
# path.repo là cấu hình tĩnh: rolling restart (Bài 10) hoặc restart cả cluster lab
docker compose up -d
source .env
curl $AUTH -X PUT "$ES/_snapshot/lab_repo" -H 'Content-Type: application/json' \
  -d '{"type":"fs","settings":{"location":"/usr/share/elasticsearch/snapshots"}}'
curl $AUTH -X POST "$ES/_snapshot/lab_repo/_verify?pretty"

Bước 2: Dữ liệu mẫu và snapshot đầu tiên

curl $AUTH -X POST "$ES/lab-orders/_bulk?refresh=true" -H 'Content-Type: application/x-ndjson' --data-binary $'{"index":{"_id":"1"}}\n{"customer":"an","total":120}\n{"index":{"_id":"2"}}\n{"customer":"binh","total":80}\n{"index":{"_id":"3"}}\n{"customer":"chi","total":250}\n'

curl $AUTH -X PUT "$ES/_snapshot/lab_repo/snap-1?wait_for_completion=true&pretty" \
  -H 'Content-Type: application/json' -d '{"indices":"lab-orders","include_global_state":false}'

Bước 3: Snapshot incremental

curl $AUTH -X POST "$ES/lab-orders/_doc/4?refresh=true" -H 'Content-Type: application/json' -d '{"customer":"dung","total":60}'
curl $AUTH -X PUT "$ES/_snapshot/lab_repo/snap-2?wait_for_completion=true" -H 'Content-Type: application/json' -d '{"indices":"lab-orders"}'

# So sánh dung lượng thực sự được copy ở mỗi snapshot
curl $AUTH "$ES/_snapshot/lab_repo/snap-1,snap-2/_status?filter_path=snapshots.snapshot,snapshots.stats.incremental,snapshots.stats.total&pretty"

Bước 4: "Sự cố" và khôi phục

# Xóa nhầm document và cả index
curl $AUTH -X DELETE "$ES/lab-orders/_doc/1"
curl $AUTH -X DELETE "$ES/lab-orders"

# Restore sang tên khác trước để kiểm tra
curl $AUTH -X POST "$ES/_snapshot/lab_repo/snap-2/_restore?wait_for_completion=true" -H 'Content-Type: application/json' -d '{
  "indices":"lab-orders","rename_pattern":"(.+)","rename_replacement":"restored-$1"}'
curl $AUTH "$ES/restored-lab-orders/_count"   # 4

# Restore đúng tên gốc
curl $AUTH -X POST "$ES/_snapshot/lab_repo/snap-2/_restore?wait_for_completion=true" -H 'Content-Type: application/json' -d '{"indices":"lab-orders"}'
curl $AUTH "$ES/lab-orders/_doc/1?filter_path=found,_source"

Bước 5: SLM

curl $AUTH -X PUT "$ES/_slm/policy/lab-nightly" -H 'Content-Type: application/json' -d '{
  "schedule": "0 30 1 * * ?", "name": "<lab-snap-{now/d}>", "repository": "lab_repo",
  "config": { "indices": ["lab-*"], "include_global_state": false },
  "retention": { "expire_after": "7d", "min_count": 2, "max_count": 10 }
}'
curl $AUTH -X POST "$ES/_slm/policy/lab-nightly/_execute"
curl $AUTH "$ES/_cat/snapshots/lab_repo?v"

Bước 6: Diễn tập DR (tùy chọn)

Ghi lại thời gian bắt đầu. Dừng cluster, xóa toàn bộ volume data (chỉ trong lab), giữ lại volume snapshots. Dựng lại cluster trống, đăng ký lại lab_repo, restore snapshot mới nhất. Ghi lại thời gian kết thúc và các bước đã làm: đó là RTO thực tế và bản nháp runbook của bạn.

docker compose down
docker volume ls | grep data0          # xác định đúng tên volume data của lab trước khi xóa
docker volume rm <project>_data01 <project>_data02 <project>_data03
docker compose up -d
# ... đăng ký lại lab_repo, restore lab-orders ...
Mất cả user và mật khẩu Xóa volume data cũng xóa index security: cluster dựng lại có mật khẩu elastic mới từ ELASTIC_PASSWORD, các user, role, API key tạo ở bài trước đều mất cho đến khi restore feature state security. Đây chính là lý do snapshot production nên có include_global_state và feature states.
Xác minh thành công Snapshot thứ hai chỉ copy một phần nhỏ dữ liệu so với snapshot đầu (incremental). Index bị xóa được khôi phục đủ 4 document. SLM tạo snapshot đặt tên theo ngày. Nếu làm bước 6, bạn có con số RTO đo được thay vì ước đoán.

Checklist Kiến Thức

  • ☐ Giải thích snapshot incremental và nội dung một snapshot
  • ☐ Đăng ký và verify repository fs, S3
  • ☐ Tạo snapshot, theo dõi trạng thái
  • ☐ Restore toàn bộ, một phần, sang tên khác
  • ☐ Cấu hình SLM với lịch và retention
  • ☐ Biết searchable snapshot dùng cho cold/frozen
  • ☐ Lập kế hoạch DR có RPO, RTO và diễn tập

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Coi replica là backup: xóa nhầm index thì replica mất theo.
  • Repository cùng hạ tầng với cluster: sự cố datacenter mất cả cluster lẫn backup.
  • Hai cluster cùng ghi một repository: metadata hỏng, snapshot không dùng được.
  • Chưa từng restore thử: phát hiện backup thiếu hoặc hỏng đúng lúc cần nó.
  • Không snapshot global state và feature states: restore xong thiếu template, ILM policy, user, dashboard.
  • Quên cron chạy theo UTC: snapshot chạy đúng giờ cao điểm.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Dùng object storage (S3/Azure/GCS) ở region khác, bật versioning và object lock
  • SLM cho mọi cluster production, có min_count và cảnh báo khi SLM thất bại (Bài 18)
  • Snapshot kèm global state và feature states cho bản backup toàn cluster
  • Snapshot thủ công trước mọi thay đổi rủi ro: nâng cấp, đổi mapping, xóa dữ liệu hàng loạt
  • Diễn tập restore ít nhất mỗi quý, ghi lại RTO thực tế
  • Lưu certificate, keystore và cấu hình ngoài cluster, có kiểm soát truy cập
