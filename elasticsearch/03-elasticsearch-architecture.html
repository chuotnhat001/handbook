Kiến Trúc Elasticsearch

Node roles, cluster state, master election, shard — hiểu cách các node phối hợp thành một distributed system

Nguồn: Elastic — Life Inside a Cluster, Elastic — Node Roles

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Hiểu các node roles trong một cluster và vai trò của từng loại. Nắm được cluster state là gì và master node quản lý nó thế nào. Giải thích cơ chế discovery và master election. Hiểu quan hệ shard ↔ Lucene index, primary vs replica, và cách routing định tuyến document. Mô tả được write path và read path của một request.

Node Roles

Một Elasticsearch cluster gồm một hoặc nhiều node (mỗi node là một tiến trình JVM chạy Elasticsearch). Mỗi node có thể đảm nhận một hoặc nhiều vai trò (role), cấu hình qua node.roles trong elasticsearch.yml.

RoleKý hiệuTrách nhiệm
master-eligiblemasterỨng cử làm master, quản lý cluster state (tạo/xóa index, theo dõi node, phân bổ shard)
datadataLưu shard, thực thi CRUD, search, aggregations
data_content / data_hot / data_warm / data_cold / data_frozendata_*Data node chuyên biệt theo tier (dùng với ILM)
ingestingestChạy ingest pipeline (tiền xử lý document trước khi index)
coordinating(mặc định mọi node)Nhận request, route tới shard, gom kết quả. Node không có role nào = coordinating-only
mlmlChạy machine learning jobs
remote_cluster_clientremote_cluster_clientKết nối remote cluster (CCS/CCR)
Tư duy cốt lõi Trong cluster nhỏ (dev, <5 node), một node thường kiêm tất cả role. Khi scale lên production, tách role ra các node chuyên biệt (dedicated master, dedicated data) để một loại workload không làm nghẽn loại khác.

Dedicated Master Nodes

Trong cluster lớn, nên có 3 dedicated master-eligible node không mang data. Lý do: master cần ổn định để quản lý cluster state; nếu master cũng là data node nặng tải, GC pause hoặc search nặng có thể khiến nó mất kết nối → bầu lại master → cluster bất ổn.

# Dedicated master node
node.roles: [ master ]

# Dedicated data node (hot tier)
node.roles: [ data_hot, data_content ]

# Coordinating-only node (load balancer nội bộ)
node.roles: [ ]

Cluster State

Cluster state là một cấu trúc dữ liệu toàn cục mô tả toàn bộ cluster: danh sách node, mapping của mọi index, vị trí mọi shard, settings, templates... Chỉ master node được phép thay đổi cluster state, sau đó publish bản cập nhật tới tất cả node khác.

  • Nguồn chân lý duy nhất (single source of truth) — mọi node tham chiếu cùng một cluster state
  • Thay đổi tuần tự — master xử lý các cluster-state update theo thứ tự, tránh race condition
  • Publish 2 pha — master gửi state mới, chờ đủ node xác nhận (quorum) rồi mới commit
# Xem cluster state (có thể rất lớn — lọc field)
GET /_cluster/state/master_node,nodes,routing_table?filter_path=**.name

# Xem cluster health
GET /_cluster/health
Cảnh báo quy mô Cluster state càng lớn (nhiều index/shard) → publish càng chậm → master càng dễ nghẽn. Đây là lý do chính của khuyến nghị "đừng over-shard" (xem Bài 11).

Discovery & Master Election

Discovery là quá trình các node tìm thấy nhau và hình thành cluster. Khi khởi động, node liên hệ danh sách discovery.seed_hosts để tham gia cluster hiện có hoặc bầu master mới.

Bootstrap cluster lần đầu

# elasticsearch.yml — chỉ đặt khi khởi tạo cluster LẦN ĐẦU
cluster.initial_master_nodes: ["node-1", "node-2", "node-3"]
discovery.seed_hosts: ["10.0.0.1", "10.0.0.2", "10.0.0.3"]

Master Election

Từ ES 7.0, Elasticsearch dùng thuật toán consensus riêng (dựa trên Raft-like, gọi là cluster coordination subsystem). Để bầu/commit master cần quorum = (số master-eligible / 2) + 1.

Số master-eligibleQuorumChịu được mất
110 node (không HA)
220 node (tệ — mất 1 là treo)
321 node
532 node
Split-brain Số master-eligible chẵn (đặc biệt là 2) dễ gây split-brain hoặc mất HA. Luôn dùng số lẻ: 3 là chuẩn production. ES 7+ tự quản lý quorum (voting configuration), không còn minimum_master_nodes thủ công như ES 6.

Shard = Lucene Index

Khi tạo index, bạn chỉ định số primary shard. Mỗi shard là một Lucene index độc lập (Bài 02) — đơn vị nhỏ nhất mà ES phân tán và scale.

PUT /products
{
  "settings": {
    "number_of_shards": 3,
    "number_of_replicas": 1
  }
}
# → 3 primary + 3 replica = 6 shard tổng, phân bổ trên các data node
Lưu ý bất biến Số number_of_shards cố định sau khi tạo index — muốn đổi phải reindex (hoặc dùng split/shrink API). Ngược lại, number_of_replicas thay đổi động bất cứ lúc nào.

Primary vs Replica

  • Primary shard — nơi document được ghi đầu tiên. Mỗi document thuộc đúng 1 primary shard.
  • Replica shard — bản sao của primary, phục vụ 2 mục đích: high availability (primary chết → replica được promote) và tăng throughput đọc (search chạy song song trên primary + replica).
Quy tắc phân bổ Primary và replica của cùng một shard không bao giờ nằm trên cùng một node — nếu không, mất node đó là mất cả hai. Đây là lý do cluster 1 node luôn ở trạng thái yellow khi có replica (replica không thể được cấp phát).

Cluster Health

Trạng tháiÝ nghĩa
greenTất cả primary và replica đều được cấp phát
yellowTất cả primary OK, nhưng có replica chưa cấp phát (vẫn hoạt động, giảm HA)
redCó primary chưa cấp phát → mất dữ liệu / một phần index không truy cập được

Routing

Làm sao ES biết document thuộc shard nào? Qua công thức routing:

shard = hash(routing) % number_of_primary_shards
# routing mặc định = _id của document

Vì number_of_primary_shards nằm trong công thức, đổi số primary shard sẽ làm routing sai → đây là lý do thứ hai khiến số primary cố định.

Custom routing (đưa document liên quan vào cùng shard) giúp tối ưu search:

PUT /orders/_doc/1?routing=user_42
{ "user": "user_42", "total": 250 }

# Search chỉ trên shard chứa user_42 → nhanh hơn
GET /orders/_search?routing=user_42
{ "query": { "term": { "user": "user_42" } } }

Write Path

Khi index một document:

Client → Coordinating node → Tính routing → Primary shard → Ghi primary + translog → Forward song song tới các Replica → Chờ replica ACK → trả client
  1. Coordinating node nhận request, dùng routing xác định primary shard.
  2. Primary thực thi ghi, ghi vào translog (write-ahead log, đảm bảo durability trước refresh).
  3. Primary forward operation tới tất cả replica in-sync song song.
  4. Khi đủ replica ACK (theo wait_for_active_shards), primary trả kết quả về client.

Read Path

Client → Coordinating node → Query Phase (scatter tới shard) → Fetch Phase (lấy _source top-N) → Gom & sort → trả client
  • Query Phase — coordinating node gửi query tới một bản sao (primary hoặc replica) của mỗi shard. Mỗi shard trả về danh sách doc_id + score của top-N.
  • Fetch Phase — sau khi gom và sort toàn cục, coordinating node fetch _source của đúng những document lọt top-N từ các shard liên quan.
  • Adaptive replica selection — ES chọn bản sao shard phản hồi nhanh nhất, không chỉ round-robin.

Bài Lab: Quan Sát Kiến Trúc Cluster

Yêu cầu

Một cluster đang chạy (dùng cluster 3 node từ Bài 01, hoặc single-node Docker).

Bước 1: Xem các node và role

GET /_cat/nodes?v&h=name,node.role,master,heap.percent,cpu
# Cột node.role: m=master, d=data, i=ingest, c=coordinating...
# Cột master: dấu * là master hiện tại

Bước 2: Tạo index và quan sát shard phân bổ

PUT /lab-arch
{ "settings": { "number_of_shards": 3, "number_of_replicas": 1 } }

GET /_cat/shards/lab-arch?v&h=index,shard,prirep,state,node
# prirep: p=primary, r=replica
# Quan sát: primary và replica KHÔNG cùng node

Bước 3: Kiểm tra routing

PUT /lab-arch/_doc/hello
{ "msg": "test routing" }

GET /lab-arch/_doc/hello?_source=false
# Trả về _shards info → document nằm ở shard nào
GET /_cat/shards/lab-arch?v

Bước 4: Xem cluster health chuyển trạng thái

# Tăng replica lên cao hơn số data node → yellow
PUT /lab-arch/_settings
{ "number_of_replicas": 5 }
GET /_cluster/health/lab-arch
# status: yellow (replica chưa cấp phát đủ)

# Trả về bình thường
PUT /lab-arch/_settings
{ "number_of_replicas": 1 }
Xác minh thành công Bạn đã thấy: node mang role gì, master là node nào, shard phân bổ ra sao (primary ≠ replica node), và cluster health phản ứng thế nào khi replica không cấp phát được.

Lỗi Thường Gặp

Những hiểu lầm phổ biến:
  • Dùng 2 master-eligible node — Tưởng là HA nhưng thực tế mất 1 node là treo cluster. Luôn dùng 3.
  • Để cluster.initial_master_nodes mãi mãi — Chỉ dùng lúc bootstrap lần đầu, giữ lại gây rắc rối khi restart.
  • Over-sharding — Quá nhiều shard nhỏ làm cluster state phình, master nghẽn. Mỗi shard có overhead cố định.
  • Nghĩ replica = backup — Replica là HA runtime, không thay thế snapshot (Bài 20). Xóa nhầm index thì mọi replica cũng mất.
  • Đổ mọi request vào 1 node — Dùng coordinating-only node hoặc client round-robin để phân tải.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Production: 3 dedicated master-eligible node (số lẻ), tách khỏi data node
  • Giữ cluster state nhỏ — kiểm soát số index/shard, dùng ILM để rollover
  • Dùng _cat/nodes, _cat/shards, _cluster/health để kiểm tra nhanh
  • Replica ≥ 1 cho index quan trọng, nhưng không quá nhiều (lãng phí tài nguyên)
  • Cân nhắc custom routing khi dữ liệu có khóa phân vùng tự nhiên (user_id, tenant_id)
