Search DSL

Query vs filter context, match, term, bool, nested, highlight, pagination — ngôn ngữ truy vấn của Elasticsearch

Nguồn: Elastic — Query DSL, Elastic — Paginate Search Results

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Phân biệt query context (có scoring) và filter context (không scoring, cache được). Dùng full-text query (match, multi_match, match_phrase) và term-level query (term, terms, range, exists). Kết hợp điều kiện bằng bool query. Truy vấn nested/join, highlight kết quả, gợi ý từ khóa, và phân trang đúng cách với search_after.

Query Context vs Filter Context

Query contextFilter context
Câu hỏi"Document khớp tốt đến đâu?""Document có khớp không?" (yes/no)
Tính _scoreCó (BM25)Không
CacheKhôngCó (node query cache)
Dùng choFull-text, relevanceLọc chính xác: status, category, date range
Vị tríbool.must, bool.shouldbool.filter, bool.must_not
Tư duy cốt lõi Điều kiện nào không ảnh hưởng đến thứ hạng (giá trong khoảng, đang còn hàng, thuộc tenant X) thì đặt vào filter. Nhanh hơn vì bỏ qua scoring, và được cache cho các query lặp lại.

Full-text Queries

Query text được analyze bằng cùng analyzer với field (hoặc search_analyzer) trước khi tìm.

# match — query phổ biến nhất
GET /products/_search
{ "query": { "match": { "name": "laptop gaming" } } }
# Mặc định OR: khớp "laptop" HOẶC "gaming"

# Yêu cầu tất cả terms
{ "query": { "match": { "name": { "query": "laptop gaming", "operator": "and" } } } }

# Ít nhất 75% terms phải khớp
{ "query": { "match": { "name": { "query": "laptop gaming rgb", "minimum_should_match": "75%" } } } }

# Chịu lỗi chính tả
{ "query": { "match": { "name": { "query": "labtop", "fuzziness": "AUTO" } } } }
# match_phrase — các term phải đúng thứ tự, liền nhau
{ "query": { "match_phrase": { "description": "pin dùng cả ngày" } } }
# slop cho phép cách nhau tối đa N vị trí
{ "query": { "match_phrase": { "description": { "query": "pin cả ngày", "slop": 1 } } } }

# multi_match — tìm trên nhiều field, có boost
{ "query": { "multi_match": {
    "query": "macbook pro",
    "fields": ["name^3", "brand^2", "description"],
    "type": "best_fields"
} } }
multi_match typeHành vi
best_fields (mặc định)Lấy score của field khớp tốt nhất
most_fieldsCộng score của mọi field khớp (hợp với multi-field cùng dữ liệu)
cross_fieldsCoi nhiều field như một field lớn (vd first_name + last_name)
phrase / phrase_prefixmatch_phrase trên từng field

Term-level Queries

Term-level query không analyze input — so khớp chính xác với term trong index. Dùng cho field keyword, số, ngày, boolean.

# term — exact match
{ "query": { "term": { "status": "published" } } }

# terms — khớp một trong nhiều giá trị (như SQL IN)
{ "query": { "terms": { "category": ["laptop", "tablet"] } } }

# range
{ "query": { "range": { "price": { "gte": 500, "lte": 1500 } } } }
{ "query": { "range": { "created_at": { "gte": "now-7d/d", "lt": "now/d" } } } }

# exists — field có giá trị
{ "query": { "exists": { "field": "discount" } } }

# prefix / wildcard (dùng thận trọng)
{ "query": { "prefix": { "sku": "LAP-" } } }
term trên field text {"term": {"name": "Laptop Gaming"}} trên field text gần như luôn trả rỗng: index lưu "laptop", "gaming" (đã lowercase, tách từ), còn term tìm nguyên chuỗi "Laptop Gaming". Dùng match cho text, hoặc term trên name.keyword.
Wildcard có ký tự đầu "wildcard": {"name": "*phone"} buộc ES quét toàn bộ term dictionary — rất chậm trên index lớn. Thay bằng edge_ngram, field wildcard, hoặc thiết kế lại. Có thể chặn hẳn bằng search.allow_expensive_queries: false.

Bool Query

Kết hợp nhiều điều kiện:

ClauseÝ nghĩaScoring
mustBắt buộc khớp (AND)Có
filterBắt buộc khớpKhông, cache được
shouldNên khớp — khớp thì cộng điểmCó
must_notKhông được khớp (NOT)Không
GET /products/_search
{
  "query": {
    "bool": {
      "must": [
        { "match": { "name": "laptop" } }
      ],
      "filter": [
        { "term":  { "in_stock": true } },
        { "terms": { "category": ["laptop", "ultrabook"] } },
        { "range": { "price": { "lte": 2000 } } }
      ],
      "should": [
        { "term": { "brand": { "value": "dell", "boost": 2 } } },
        { "match": { "description": "pin lâu" } }
      ],
      "must_not": [
        { "term": { "status": "discontinued" } }
      ]
    }
  }
}
should và minimum_should_match Khi bool có must hoặc filter, các should chỉ cộng điểm (không bắt buộc). Khi bool chỉ có should, ít nhất 1 should phải khớp. Đặt minimum_should_match để kiểm soát rõ ràng.

Nested & Join Queries

nested query

Field kiểu nested (Bài 06) phải truy vấn qua nested query để giữ quan hệ trong từng phần tử:

GET /ecommerce-products/_search
{
  "query": {
    "nested": {
      "path": "variants",
      "query": { "bool": { "filter": [
        { "term":  { "variants.color": "black" } },
        { "range": { "variants.stock": { "gt": 0 } } }
      ]}},
      "inner_hits": {}
    }
  }
}
# inner_hits trả về biến thể nào đã khớp

has_child / has_parent (join field)

Field join mô hình quan hệ cha–con trong cùng index (vd question–answer). Cha và con phải cùng shard (dùng routing).

PUT /qa
{ "mappings": { "properties": {
  "relation": { "type": "join", "relations": { "question": "answer" } }
}}}

PUT /qa/_doc/1
{ "title": "Cách tối ưu bulk?", "relation": "question" }
PUT /qa/_doc/2?routing=1
{ "body": "Dùng batch 5-15MB", "relation": { "name": "answer", "parent": "1" } }

# Câu hỏi có câu trả lời chứa "batch"
GET /qa/_search
{ "query": { "has_child": { "type": "answer", "query": { "match": { "body": "batch" } } } } }
Join đắt has_child/has_parent chậm hơn nhiều so với query thường. Elasticsearch khuyến nghị denormalize (nhân bản dữ liệu vào document) khi có thể; chỉ dùng join khi con cập nhật rất thường xuyên độc lập với cha.

Highlighting

GET /articles/_search
{
  "query": { "match": { "body": "elasticsearch cluster" } },
  "highlight": {
    "pre_tags": ["<mark>"],
    "post_tags": ["</mark>"],
    "fields": {
      "body": { "fragment_size": 150, "number_of_fragments": 3 }
    }
  }
}
# Response: hits[].highlight.body = ["... <mark>Elasticsearch</mark> ..."]
XSS khi hiển thị highlight Fragment highlight chứa nội dung gốc của document. Nếu nội dung đến từ người dùng, phải escape HTML trước khi render, hoặc đặt "encoder": "html" để ES escape nội dung và chỉ giữ thẻ highlight.

Suggesters

SuggesterDùng cho
termGợi ý sửa chính tả từng từ ("labtop" → "laptop")
phraseGợi ý sửa cả cụm từ
completionAutocomplete rất nhanh (cấu trúc FST trong bộ nhớ), cần field type completion
# "Ý bạn là..."
GET /products/_search
{ "suggest": { "fix": { "text": "labtop gamng", "term": { "field": "name" } } } }

# Autocomplete (field "suggest" kiểu completion)
GET /products/_search
{ "suggest": { "auto": {
  "prefix": "mac",
  "completion": { "field": "suggest", "size": 5, "skip_duplicates": true }
} } }

Pagination

from + size — trang nông

GET /products/_search
{ "from": 20, "size": 10, "query": { "match_all": {} } }
Deep pagination Với from: 10000, size: 10, mỗi shard phải lấy và sort 10.010 kết quả rồi coordinating node gom lại. Chi phí tăng theo độ sâu. ES chặn mặc định ở index.max_result_window: 10000.

search_after + PIT — trang sâu

Dùng sort values của kết quả cuối trang trước làm "con trỏ". Kết hợp Point in Time (PIT) để giữ snapshot nhất quán khi dữ liệu đang thay đổi.

# 1. Mở PIT
POST /products/_pit?keep_alive=1m
# → { "id": "46ToAwMDaWR..." }

# 2. Trang đầu
GET /_search
{
  "size": 100,
  "pit": { "id": "46ToAwMDaWR...", "keep_alive": "1m" },
  "sort": [ { "created_at": "desc" }, { "_shard_doc": "asc" } ]
}

# 3. Trang tiếp: truyền sort values của hit cuối cùng
GET /_search
{
  "size": 100,
  "pit": { "id": "46ToAwMDaWR...", "keep_alive": "1m" },
  "sort": [ { "created_at": "desc" }, { "_shard_doc": "asc" } ],
  "search_after": [ 1761600000000, 4294967298 ]
}

# 4. Đóng PIT khi xong
DELETE /_pit
{ "id": "46ToAwMDaWR..." }
CáchKhi nào dùng
from/sizeUI phân trang vài trang đầu
search_after + PITInfinite scroll, duyệt sâu, export lớn
scroll APICách cũ — ES khuyến nghị chuyển sang search_after + PIT

Sorting & Boosting

# Sort theo field (dùng keyword/numeric/date — có doc_values)
GET /products/_search
{
  "query": { "match": { "name": "laptop" } },
  "sort": [
    { "price": "asc" },
    { "_score": "desc" }
  ]
}

# function_score — kết hợp relevance với độ phổ biến
GET /products/_search
{
  "query": {
    "function_score": {
      "query": { "match": { "name": "laptop" } },
      "functions": [
        { "field_value_factor": { "field": "sold_count", "modifier": "log1p", "factor": 0.5 } }
      ],
      "boost_mode": "sum"
    }
  }
}

Dùng "explain": true (Bài 02) hoặc _validate/query?explain để xem vì sao một document có score như vậy.

{
  "query": {
    "bool": {
      "must": [
        { "multi_match": { "query": "elasticsearch cluster", "fields": ["title^3", "body"] } }
      ],
      "filter": [
        { "term": { "status": "published" } },
        { "range": { "published_at": { "gte": "2026-01-01" } } }
      ],
      "should": [
        { "terms": { "tags": ["performance"] } }
      ]
    }
  },

  "_source": ["title", "author", "published_at"],
  "size": 10
}

Bước 3: Phân trang với search_after

GET /blog-posts/_search
{
  "size": 1,
  "query": { "term": { "status": "published" } },
  "sort": [ { "published_at": "desc" }, { "title.keyword": "asc" } ]
}
# Lấy giá trị "sort" của hit cuối, truyền vào search_after cho trang sau
Xác minh thành công Query kết hợp đủ 4 thành phần: full-text có boost (must), lọc chính xác không tính điểm (filter), tăng hạng tùy chọn (should), highlight an toàn. Đây là khung chuẩn cho hầu hết search UI.

Câu Hỏi Ôn Tập

  1. Khác biệt giữa query context và filter context? Vì sao filter nhanh hơn?
  2. Vì sao term query trên field text thường trả rỗng?
  3. So sánh match, match_phrase, multi_match.
  4. Giải thích 4 clause của bool query và clause nào tính điểm.
  5. Khi nào dùng nested query? Khi nào dùng has_child, và vì sao nên tránh nếu có thể?
  6. Vì sao deep pagination với from/size tốn kém? search_after + PIT giải quyết thế nào?
  7. Rủi ro bảo mật khi hiển thị highlight là gì?

Checklist Kiến Thức

  • ☐ Phân biệt query context và filter context
  • ☐ Dùng match, match_phrase, multi_match với operator/fuzziness/boost
  • ☐ Dùng term, terms, range, exists trên keyword/numeric/date
  • ☐ Viết bool query với must/filter/should/must_not
  • ☐ Truy vấn nested và join field
  • ☐ Cấu hình highlight an toàn
  • ☐ Dùng term và completion suggester
  • ☐ Phân trang sâu bằng search_after + PIT

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Đặt điều kiện lọc vào must — Tính điểm vô ích và mất cache. Lọc chính xác → filter.
  • term trên text, match trên keyword — Sai loại query cho loại field. Kiểm tra mapping trước.
  • Deep pagination bằng from/size — Chậm và chạm max_result_window. Dùng search_after.
  • Wildcard/regex có ký tự đầu — Quét toàn bộ term dictionary, có thể làm nghẽn cluster.
  • Render highlight không escape — Lỗ hổng XSS nếu nội dung do người dùng nhập.
  • Sort trên field text — Lỗi fielddata. Sort trên sub-field keyword.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Mặc định đặt mọi điều kiện không ảnh hưởng thứ hạng vào filter
  • Giới hạn _source chỉ lấy field cần hiển thị để giảm payload
  • Dùng search_after + PIT cho mọi trường hợp duyệt quá vài trang
  • Bật search.allow_expensive_queries: false ở cluster dùng chung để chặn query nguy hiểm
  • Denormalize thay vì join khi có thể
  • Kiểm tra relevance bằng explain và tập query mẫu trước khi tinh chỉnh boost
