Bảo Mật Elasticsearch

TLS, xác thực, realms, RBAC, field/document level security, API key, audit log — bảo vệ cluster production

Nguồn: Elastic — Secure the Elastic Stack, Elastic — User Authorization

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Bật TLS cho cả transport layer (giữa các node) và HTTP layer (client tới cluster). Hiểu built-in users, realm chain và các phương thức xác thực. Tạo API key và service token cho ứng dụng. Thiết kế role theo nguyên tắc least privilege, giới hạn tới mức field và document. Bật audit log. Biết tính năng nào cần license trả phí.

TLS: HTTP & Transport

Elasticsearch có hai lớp mạng, mỗi lớp cấu hình TLS riêng:

LớpCổng mặc địnhAi dùngTLS
Transport9300Node với node (replication, cluster state)Bắt buộc khi bật security trên cluster nhiều node
HTTP9200Client, Kibana, Beats, ứng dụngKhông bắt buộc về kỹ thuật, nhưng thiếu TLS thì mật khẩu và API key đi dạng rõ
# elasticsearch.yml
xpack.security.enabled: true

# Transport: node xác thực lẫn nhau bằng certificate cùng CA
xpack.security.transport.ssl.enabled: true
xpack.security.transport.ssl.verification_mode: certificate
xpack.security.transport.ssl.key: certs/node-1/node-1.key
xpack.security.transport.ssl.certificate: certs/node-1/node-1.crt
xpack.security.transport.ssl.certificate_authorities: certs/ca/ca.crt

# HTTP
xpack.security.http.ssl.enabled: true
xpack.security.http.ssl.key: certs/node-1/node-1.key
xpack.security.http.ssl.certificate: certs/node-1/node-1.crt
xpack.security.http.ssl.certificate_authorities: certs/ca/ca.crt
verification_modeKiểm tra
fullCertificate hợp lệ, do CA tin cậy cấp, và hostname/IP khớp
certificateCertificate hợp lệ và do CA tin cậy cấp, không kiểm tra hostname
noneKhông kiểm tra gì. Chỉ để debug, không bao giờ dùng ở production
Tư duy cốt lõi Transport TLS chứng minh "node này thuộc cluster của tôi": chỉ node có certificate do CA của bạn cấp mới join được. HTTP TLS bảo vệ thông tin xác thực trên đường truyền. Thiếu một trong hai là để hở một mặt tấn công.

Sinh Certificate

Công cụ elasticsearch-certutil đi kèm Elasticsearch:

# 1. Tạo CA (giữ ca.key thật cẩn thận, ai có nó là cấp được certificate hợp lệ)
bin/elasticsearch-certutil ca --pem --out ca.zip

# 2. Khai báo các node
cat > instances.yml <<'EOF'
instances:
  - name: node-1
    dns: [ node-1.internal, localhost ]
    ip:  [ 10.0.0.1, 127.0.0.1 ]
  - name: node-2
    dns: [ node-2.internal ]
    ip:  [ 10.0.0.2 ]
EOF

# 3. Cấp certificate cho từng node, ký bởi CA
bin/elasticsearch-certutil cert --pem \
  --ca-cert ca/ca.crt --ca-key ca/ca.key \
  --in instances.yml --out certs.zip
Certificate cho HTTP Với HTTP layer phục vụ trình duyệt hoặc client bên ngoài, nên dùng certificate do CA nội bộ của tổ chức (hoặc CA công khai) cấp, để client không phải tin một CA tự tạo. Lệnh bin/elasticsearch-certutil http hướng dẫn từng bước tạo CSR cho trường hợp này. Đặt lịch gia hạn certificate trước khi hết hạn, vì certificate hết hạn làm node không nói chuyện được với nhau.

Built-in Users

UserDùng cho
elasticSuperuser. Chỉ dùng để thiết lập ban đầu và xử lý khẩn cấp
kibana_systemKibana kết nối tới Elasticsearch
logstash_systemLogstash gửi dữ liệu monitoring
beats_systemBeats gửi dữ liệu monitoring
remote_monitoring_userMetricbeat thu thập metric của Stack
# Đặt mật khẩu tương tác hoặc tự sinh
bin/elasticsearch-reset-password -u kibana_system -i
bin/elasticsearch-reset-password -u elastic --auto

# Đổi mật khẩu qua API
POST /_security/user/kibana_system/_password
{ "password": "a-long-random-password" }
Không dùng elastic cho ứng dụng Ứng dụng dùng user elastic nghĩa là một lỗ hổng ở ứng dụng trao toàn quyền cluster cho kẻ tấn công. Tạo user hoặc API key riêng cho từng ứng dụng, chỉ cấp đúng quyền cần.

Realms

Realm là nguồn xác thực danh tính. Elasticsearch thử các realm theo thứ tự order (realm chain) cho đến khi một realm xác thực thành công.

RealmNguồn danh tínhLicense
nativeUser lưu trong index nội bộ của ESBasic (miễn phí)
fileUser trong file trên từng node. Dùng làm tài khoản khẩn cấp khi native không khả dụngBasic
ldap, active_directoryThư mục doanh nghiệpTrả phí
saml, oidcSSO qua Identity Provider (Okta, Keycloak, Azure AD...)Trả phí
pki, kerberos, jwtClient certificate, Kerberos ticket, JWTTrả phí
# elasticsearch.yml: native trước, LDAP sau
xpack.security.authc.realms:
  native.native1:
    order: 0
  ldap.corp_ldap:
    order: 1
    url: "ldaps://ldap.corp.example:636"
    bind_dn: "cn=es-bind,ou=services,dc=corp,dc=example"
    user_search.base_dn: "ou=people,dc=corp,dc=example"
    group_search.base_dn: "ou=groups,dc=corp,dc=example"
    ssl.certificate_authorities: [ "certs/corp-ca.crt" ]
# Mật khẩu bind lưu trong keystore, không để trong file cấu hình:
# bin/elasticsearch-keystore add xpack.security.authc.realms.ldap.corp_ldap.secure_bind_password

User từ realm bên ngoài nhận role qua role mapping, thường dựa trên group:

PUT /_security/role_mapping/ldap-log-readers
{
  "roles": [ "logs_reader" ],
  "enabled": true,
  "rules": { "field": { "groups": "cn=sre,ou=groups,dc=corp,dc=example" } }
}

API Keys & Service Accounts

API key phù hợp cho ứng dụng và script: có thể đặt thời hạn, giới hạn quyền và thu hồi riêng lẻ mà không đổi mật khẩu của ai.

POST /_security/api_key
{
  "name": "order-service",
  "expiration": "90d",
  "role_descriptors": {
    "orders_writer": {
      "indices": [ { "names": [ "orders-*" ], "privileges": [ "create_doc", "read" ] } ]
    }
  },
  "metadata": { "owner": "team-orders" }
}
# Response có "encoded" = base64(id:api_key). Gửi kèm request:
# Authorization: ApiKey <encoded>

# Liệt kê và thu hồi
GET /_security/api_key?name=order-service
DELETE /_security/api_key
{ "name": "order-service" }
Quyền của API key Quyền thực tế của API key là giao của role_descriptors với quyền của user tạo ra nó. API key không bao giờ có nhiều quyền hơn người tạo.

Service account là danh tính cố định cho thành phần của Stack, như elastic/kibana và elastic/fleet-server. Chúng xác thực bằng service token:

POST /_security/service/elastic/fleet-server/credential/token/fleet-token-1
# hoặc tạo token dạng file trên node:
bin/elasticsearch-service-tokens create elastic/fleet-server fleet-token-1

RBAC

Quyền được gom thành role, role gán cho user (hoặc API key, role mapping). Một role gồm:

  • Cluster privileges: monitor, manage_ilm, manage_index_templates, manage, all...
  • Index privileges trên pattern index: read, view_index_metadata, create_doc, write, create_index, manage, all...
  • Application privileges: quyền trong Kibana (cấu hình qua Kibana, Bài 14)
PUT /_security/role/logs_reader
{
  "cluster": [ "monitor" ],
  "indices": [
    { "names": [ "logs-*" ], "privileges": [ "read", "view_index_metadata" ] }
  ]
}

PUT /_security/user/an
{
  "password": "a-long-random-password",
  "roles": [ "logs_reader" ],
  "full_name": "Nguyen Van An"
}

# Kiểm tra user hiện tại có quyền gì
GET /_security/_authenticate
GET /_security/user/_has_privileges
{ "index": [ { "names": [ "logs-app" ], "privileges": [ "read", "write" ] } ] }
Least privilege Ứng dụng chỉ ghi log cần create_doc trên đúng pattern index, không cần write (bao gồm cả update và delete), càng không cần all. Ứng dụng đọc cho dashboard cần read, không cần quyền cluster nào ngoài monitor.

Field & Document Level Security

Hai cơ chế này giới hạn quyền bên trong một index. Cả hai đều cần license trả phí.

PUT /_security/role/support_vn
{
  "indices": [
    {
      "names": [ "customers" ],
      "privileges": [ "read" ],
      "field_security": {
        "grant": [ "*" ],
        "except": [ "national_id", "card_number" ]
      },
      "query": { "term": { "country": "VN" } }
    }
  ]
}
# Nhân viên support Việt Nam chỉ thấy khách hàng VN,
# và không bao giờ thấy CCCD hay số thẻ
Template query Document level security có thể dùng template để lọc theo thuộc tính của chính user đang truy vấn, ví dụ {"term": {"owner": "{{_user.username}}"}}. Một role dùng chung được cho mọi người mà mỗi người chỉ thấy dữ liệu của mình.

Audit Logging

Audit log ghi lại ai làm gì: đăng nhập thất bại, truy cập bị từ chối, thay đổi user/role. Đây thường là yêu cầu bắt buộc của kiểm toán và quy định (ví dụ trong ngân hàng). Tính năng cần license trả phí.

# elasticsearch.yml
xpack.security.audit.enabled: true
xpack.security.audit.logfile.events.include:
  - authentication_failed
  - access_denied
  - security_config_change
  - run_as_denied
# Log ghi ra <cluster_name>_audit.json trong thư mục logs, dạng JSON
# Thu thập bằng Filebeat/Elastic Agent (Bài 16) về một cluster riêng
Ghi quá nhiều Bật các event như access_granted trên cluster bận sẽ sinh lượng log khổng lồ và ảnh hưởng performance. Bắt đầu với các event thất bại và thay đổi cấu hình, chỉ mở rộng khi có yêu cầu cụ thể.

Tính Năng Theo License

Tính năngBasic (miễn phí)Trả phí
TLS transport và HTTPCóCó
Native và file realm, RBAC, API keyCóCó
LDAP, AD, SAML, OIDC, PKI, Kerberos, JWTKhôngCó
Field và document level securityKhôngCó
Audit loggingKhôngCó
GET /_license
# Dùng thử đầy đủ tính năng 30 ngày (một lần cho mỗi cluster)
POST /_license/start_trial?acknowledge=true
Kiểm tra lại trước khi ra quyết định Phân bổ tính năng theo license có thể thay đổi giữa các phiên bản. Bảng trên phản ánh cách phân bổ phổ biến của dòng 8.x. Trước khi lập kế hoạch, đối chiếu trang Elastic Subscriptions cho đúng version bạn dùng.

Bài Lab: Bật TLS + RBAC Cho Cluster Lab

Lab này chuyển cluster 3 node của Bài 04 từ không có security sang có TLS và xác thực. Từ bài này trở đi, các lab dùng cluster đã bảo mật.

Bước 1: Sinh CA và certificate

mkdir -p certs
cat > certs/instances.yml <<'EOF'
instances:
  - name: es01
    dns: [ es01, localhost ]
    ip:  [ 127.0.0.1 ]
  - name: es02
    dns: [ es02 ]
  - name: es03
    dns: [ es03 ]
EOF

docker run --rm -u 0 -v "$PWD/certs:/certs" \
  docker.elastic.co/elasticsearch/elasticsearch:8.15.0 bash -c '
  bin/elasticsearch-certutil ca --silent --pem --out /certs/ca.zip &&
  unzip -o -q /certs/ca.zip -d /certs &&
  bin/elasticsearch-certutil cert --silent --pem \
    --ca-cert /certs/ca/ca.crt --ca-key /certs/ca/ca.key \
    --in /certs/instances.yml --out /certs/certs.zip &&
  unzip -o -q /certs/certs.zip -d /certs &&
  chown -R 1000:0 /certs'
ls certs/es01   # es01.crt  es01.key

Bước 2: Cập nhật docker-compose.yml

Tạo file .env chứa mật khẩu (không commit file này):

ELASTIC_PASSWORD=change-me-long-random

Với mỗi node, thay dòng xpack.security.enabled=false bằng khối dưới đây (đổi es01 thành tên node tương ứng) và mount thư mục certs:

    environment:
      # ... giữ nguyên node.name, cluster.name, discovery ...
      - ELASTIC_PASSWORD=${ELASTIC_PASSWORD}
      - xpack.security.enabled=true
      - xpack.security.http.ssl.enabled=true
      - xpack.security.http.ssl.key=certs/es01/es01.key
      - xpack.security.http.ssl.certificate=certs/es01/es01.crt
      - xpack.security.http.ssl.certificate_authorities=certs/ca/ca.crt
      - xpack.security.transport.ssl.enabled=true
      - xpack.security.transport.ssl.key=certs/es01/es01.key
      - xpack.security.transport.ssl.certificate=certs/es01/es01.crt
      - xpack.security.transport.ssl.certificate_authorities=certs/ca/ca.crt
      - xpack.security.transport.ssl.verification_mode=certificate
    volumes:
      - data01:/usr/share/elasticsearch/data
      - ./certs:/usr/share/elasticsearch/config/certs
Bật security cần restart toàn cluster Không thể bật transport TLS bằng rolling restart từ trạng thái không TLS, vì node cũ và node mới không nói chuyện được với nhau. Dừng cả cluster rồi khởi động lại: docker compose down && docker compose up -d. Dữ liệu trong volume vẫn giữ nguyên. Nếu bạn đã thêm es04, es05 ở Bài 10, sinh certificate và cấu hình cho cả hai node đó.

Bước 3: Kiểm tra kết nối bảo mật

source .env
ES=https://localhost:9200
AUTH="--cacert certs/ca/ca.crt -u elastic:$ELASTIC_PASSWORD"

curl $AUTH "$ES/_cluster/health?pretty"     # thành công
curl --cacert certs/ca/ca.crt "$ES"          # 401: thiếu thông tin xác thực
curl "http://localhost:9200"                 # thất bại: cổng chỉ nhận HTTPS

Hai biến ES và AUTH được dùng lại trong các lab từ Bài 14 trở đi.

Bước 4: Tạo role, user và API key

curl $AUTH -X PUT "$ES/_security/role/logs_reader" -H 'Content-Type: application/json' -d '{
  "cluster": ["monitor"],
  "indices": [{ "names": ["logs-*"], "privileges": ["read","view_index_metadata"] }]
}'
curl $AUTH -X PUT "$ES/_security/user/an" -H 'Content-Type: application/json' -d '{
  "password": "an-lab-password-123", "roles": ["logs_reader"]
}'

# User "an" đọc được logs-*, nhưng không ghi được
curl --cacert certs/ca/ca.crt -u an:an-lab-password-123 "$ES/logs-*/_search?size=0"
curl --cacert certs/ca/ca.crt -u an:an-lab-password-123 -X POST "$ES/logs-app/_doc" \
  -H 'Content-Type: application/json' -d '{"@timestamp":"2026-10-28T08:00:00Z"}'
# → 403 security_exception: action [indices:data/write/...] is unauthorized

# API key chỉ được thêm document vào logs-*
curl $AUTH -X POST "$ES/_security/api_key" -H 'Content-Type: application/json' -d '{
  "name": "lab-shipper", "expiration": "1d",
  "role_descriptors": { "shipper": { "indices": [{ "names": ["logs-*"], "privileges": ["create_doc","auto_configure"] }] } }
}'
# Dùng giá trị "encoded" trong response:
curl --cacert certs/ca/ca.crt -H "Authorization: ApiKey <encoded>" -X POST "$ES/logs-app/_doc" \
  -H 'Content-Type: application/json' -d '{"@timestamp":"2026-10-28T08:00:00Z","msg":"hello"}'

Bước 5 (tùy chọn): Thử FLS/DLS với trial license

curl $AUTH -X POST "$ES/_license/start_trial?acknowledge=true"
curl $AUTH -X PUT "$ES/_security/role/logs_no_ip" -H 'Content-Type: application/json' -d '{
  "indices": [{ "names": ["logs-*"], "privileges": ["read"],
    "field_security": { "grant": ["*"], "except": ["client_ip"] } }]
}'

Tích hợp LDAP cần một LDAP server và license trả phí (hoặc trial). Cấu hình realm theo mẫu ở mục Realms, rồi kiểm tra bằng GET /_security/_authenticate với user LDAP.

Xác minh thành công Cluster chỉ nhận HTTPS, request không có thông tin xác thực bị từ chối, user an đọc được nhưng không ghi được, và API key chỉ thêm được document vào logs-*. Đây là cấu hình tối thiểu cho bất kỳ cluster nào có dữ liệu thật.

Checklist Kiến Thức

  • ☐ Sinh CA và certificate bằng elasticsearch-certutil
  • ☐ Cấu hình TLS cho transport và HTTP
  • ☐ Quản lý mật khẩu built-in user
  • ☐ Hiểu realm chain và role mapping
  • ☐ Tạo, giới hạn quyền và thu hồi API key
  • ☐ Viết role theo least privilege
  • ☐ Biết FLS, DLS, audit log và yêu cầu license của chúng

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Ứng dụng dùng user elastic: một lỗ hổng ứng dụng thành lỗ hổng toàn cluster.
  • Mật khẩu trong elasticsearch.yml hoặc code: dùng keystore cho cấu hình, secret manager cho ứng dụng.
  • verification_mode: none ở production: bất kỳ ai cũng có thể giả làm node.
  • Để certificate hết hạn: các node mất kết nối với nhau, cluster dừng hoạt động.
  • Mở cổng 9200 ra internet: ngay cả khi có xác thực, hãy đặt cluster sau firewall hoặc VPN.
  • API key không có thời hạn: key bị lộ sẽ hợp lệ mãi mãi. Đặt expiration và xoay vòng định kỳ.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Bật TLS cho cả hai lớp, verification_mode: full khi hạ tầng DNS cho phép
  • Mỗi ứng dụng một API key với quyền tối thiểu và thời hạn rõ ràng
  • Con người đăng nhập qua SSO (SAML/OIDC) hoặc LDAP, quyền cấp qua role mapping theo group
  • Lưu secret trong keystore, không trong file cấu hình hay biến môi trường bị log
  • Bật audit log cho event thất bại và thay đổi cấu hình bảo mật, gửi về cluster riêng
  • Giám sát ngày hết hạn certificate
