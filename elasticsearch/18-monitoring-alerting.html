Monitoring & Alerting

Stack Monitoring, metric quan trọng, health report, Kibana alerting và Watcher

Nguồn: Elastic — Monitor a Cluster, Elastic — Kibana Alerting

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Thu thập metric của Elasticsearch, Kibana, Logstash bằng Stack Monitoring và hiểu vì sao nên gửi về một monitoring cluster riêng. Biết nhóm metric nào cần theo dõi và ngưỡng tham khảo. Chẩn đoán nhanh bằng _cat, _nodes/stats và Health Report API. Tạo cảnh báo bằng Kibana Alerting, so sánh với Watcher, và thiết kế cảnh báo ít nhiễu.

Kiến Thức Tiên Quyết

  • Bài 10, 11 — Cluster health, shard allocation, disk watermark
  • Bài 14: Kibana — Đã chạy, có encryption key (bắt buộc cho alerting)
  • Bài 16, 17 — Metricbeat hoặc Elastic Agent

Stack Monitoring

Stack Monitoring là ứng dụng trong Kibana hiển thị sức khỏe của Elasticsearch, Kibana, Logstash, Beats và agent: heap, CPU, indexing rate, search latency, số shard... theo từng cluster, node và index.

Cách thu thậpTrạng tháiGhi chú
Elastic Agent + integration Elasticsearch (chế độ Stack Monitoring)Khuyến nghịQuản lý qua Fleet
Metricbeat module elasticsearch với xpack.enabled: trueĐược hỗ trợNhư Lab Bài 16
Legacy internal collection (xpack.monitoring.collection.enabled)DeprecatedKhông dùng cho triển khai mới
# metricbeat.yml: module elasticsearch cho Stack Monitoring
- module: elasticsearch
  xpack.enabled: true
  period: 10s
  hosts: ["https://es01:9200", "https://es02:9200", "https://es03:9200"]
  username: "remote_monitoring_user"
  password: "${MONITORING_PASSWORD}"
  ssl.certificate_authorities: ["/certs/ca/ca.crt"]
  scope: cluster        # một Metricbeat thu thập cả cluster qua API
                        # scope: node (mặc định) cần một Metricbeat trên mỗi node

Dữ liệu được ghi vào data stream .monitoring-es-8-mb, .monitoring-kibana-8-mb... Kibana Stack Monitoring đọc các index này.

Monitoring Cluster Riêng

Tư duy cốt lõi Một cluster không thể tự báo cáo đáng tin cậy rằng nó đang chết. Khi cluster production quá tải hoặc red, chính dữ liệu monitoring của nó cũng không ghi được. Gửi monitoring về một cluster nhỏ riêng để vẫn nhìn thấy production lúc nó gặp sự cố.
Production cluster → Metricbeat / Agent → Monitoring cluster → Kibana Stack Monitoring + Alerting
  • Monitoring cluster có thể nhỏ (1–3 node), có ILM giữ dữ liệu 7–30 ngày
  • Version của monitoring cluster nên ≥ version của các cluster được giám sát
  • Một monitoring cluster giám sát được nhiều cluster production
  • Khi chỉ có một cluster (lab, môi trường nhỏ), gửi về chính nó vẫn hơn không giám sát gì

Health Report

Từ ES 8.7, Health Report API tổng hợp sức khỏe theo từng thành phần (indicator), kèm nguyên nhân và hướng xử lý cụ thể. Đây là điểm khởi đầu tốt khi chưa biết cluster đang gặp vấn đề gì.

GET /_health_report

# Chỉ một indicator, kèm chi tiết
GET /_health_report/shards_availability?verbose=true
IndicatorKiểm tra
master_is_stableMaster có ổn định hay bị bầu lại liên tục
shards_availabilityShard primary/replica chưa cấp phát
diskNode vượt watermark
ilm, slmILM/SLM bị dừng hoặc policy lỗi
shards_capacitySắp chạm giới hạn số shard
repository_integritySnapshot repository bị hỏng

Mỗi indicator trả về status (green/yellow/red/unknown), symptom, impacts và diagnosis có trường action mô tả cách sửa.

Kibana Alerting

Kibana Alerting gồm hai khái niệm:

  • Rule: điều kiện kiểm tra theo chu kỳ (ví dụ: số log lỗi trong 5 phút > 50)
  • Connector: nơi gửi thông báo (email, Slack, Microsoft Teams, PagerDuty, webhook, ghi vào index)
Loại ruleDùng cho
Elasticsearch queryQuery DSL, KQL hoặc ES|QL trả về số document vượt ngưỡng
Index thresholdAggregation (count, avg, max...) vượt ngưỡng, có thể group theo field
Stack Monitoring rulesCó sẵn: CPU, disk, heap, cluster health, thread pool rejection, license sắp hết hạn
Observability rulesLog threshold, metric threshold, uptime, APM latency/error rate
Security detection rulesPhát hiện tấn công (Bài 25)
# Tạo rule qua API: cảnh báo khi có hơn 50 lỗi 5xx trong 5 phút
POST kbn:/api/alerting/rule
{
  "name": "Nhiều lỗi 5xx",
  "rule_type_id": ".es-query",
  "consumer": "stackAlerts",
  "schedule": { "interval": "1m" },
  "params": {
    "searchType": "esQuery",
    "index": ["access-logs"],
    "timeField": "@timestamp",
    "esQuery": "{\"query\":{\"range\":{\"status_code\":{\"gte\":500}}}}",
    "timeWindowSize": 5,
    "timeWindowUnit": "m",
    "threshold": [50],
    "thresholdComparator": ">",
    "size": 0
  },
  "actions": [
    {
      "id": "<connector-id>",
      "group": "query matched",
      "frequency": { "summary": false, "notify_when": "onActionGroupChange", "throttle": null },
      "params": { "message": "{{rule.name}}: {{context.value}} lỗi 5xx trong 5 phút. {{context.link}}" }
    }
  ]
}
Điều kiện để Alerting hoạt động Kibana cần xpack.encryptedSavedObjects.encryptionKey (Bài 14) và cluster bật security với TLS trên HTTP. Một số connector (email, Slack, PagerDuty...) chỉ có ở license trả phí; connector ghi vào index và server log có ở bản miễn phí. Đối chiếu trang Elastic Subscriptions cho đúng version.

Watcher

Watcher là hệ thống cảnh báo chạy bên trong Elasticsearch (cần license trả phí). Một watch gồm trigger, input, condition và actions, viết bằng JSON.

PUT /_watcher/watch/cluster_not_green
{
  "trigger": { "schedule": { "interval": "1m" } },
  "input": { "http": { "request": { "host": "localhost", "port": 9200, "path": "/_cluster/health", "scheme": "https" } } },
  "condition": { "compare": { "ctx.payload.status": { "not_eq": "green" } } },
  "throttle_period": "15m",
  "actions": {
    "notify": { "webhook": { "method": "POST", "url": "https://hooks.example.com/oncall",
      "body": "Cluster {{ctx.payload.cluster_name}} đang {{ctx.payload.status}}" } }
  }
}
Kibana AlertingWatcher
Chạy ởKibana task managerElasticsearch
Tạo ruleGiao diện, API, rule có sẵnChỉ JSON qua API
Linh hoạtTheo các loại rule có sẵnRất cao: chuỗi input, transform bằng Painless
Hướng phát triểnHướng chính của ElasticVẫn được hỗ trợ

Triển khai mới nên dùng Kibana Alerting. Dùng Watcher khi cần logic mà rule type có sẵn không biểu diễn được.

Thiết Kế Cảnh Báo

Alert fatigue Cảnh báo nhiều và sai làm đội vận hành bỏ qua cả cảnh báo thật. Mỗi cảnh báo nên trả lời được: điều gì đang hỏng, ảnh hưởng tới ai, và cần làm gì ngay.
  • Cảnh báo theo triệu chứng người dùng cảm nhận (tỷ lệ lỗi, latency, cluster red) trước, nguyên nhân (CPU cao) sau
  • Có khoảng chờ: điều kiện kéo dài vài phút mới báo, tránh báo vì một đỉnh nhọn thoáng qua
  • Chia mức độ: critical (gọi người trực), warning (gửi kênh team), info (chỉ lưu)
  • Chỉ báo khi đổi trạng thái (onActionGroupChange), không báo lặp mỗi phút
  • Kèm link tới dashboard hoặc Discover với filter sẵn
  • Có runbook: link tới tài liệu xử lý cho từng cảnh báo
  • Giám sát chính hệ thống giám sát: cảnh báo khi không nhận được dữ liệu monitoring (no data)

Bài Lab: Cảnh Báo Khi Cluster Chuyển Yellow

Bước 1: Bật Stack Monitoring bằng Metricbeat

Trong lab, gửi monitoring về chính cluster lab (production nên dùng cluster riêng).

source .env
curl $AUTH -X POST "$ES/_security/user/remote_monitoring_user/_password" \
  -H 'Content-Type: application/json' -d '{"password":"monitoring-lab-password-123"}'
echo "MONITORING_PASSWORD=monitoring-lab-password-123" >> .env

cat >> beats/metricbeat.yml <<'EOF'
  - module: elasticsearch
    xpack.enabled: true
    period: 10s
    scope: cluster
    hosts: ["https://es01:9200"]
    username: "remote_monitoring_user"
    password: "${MONITORING_PASSWORD}"
    ssl.certificate_authorities: ["/certs/ca/ca.crt"]
EOF
Kiểm tra vị trí khối vừa thêm Lệnh cat >> nối vào cuối file, tức là sau khối output.elasticsearch. Mở beats/metricbeat.yml và chuyển khối module elasticsearch lên nằm trong danh sách metricbeat.modules, thụt lề giống các module khác. Đồng thời thêm MONITORING_PASSWORD=${MONITORING_PASSWORD} vào environment của service metricbeat, và thêm .monitoring-* vào danh sách index trong API key của Beats (Bài 16). 
docker compose up -d --force-recreate metricbeat
curl $AUTH "$ES/_data_stream/.monitoring-es-8-mb?filter_path=**.name"
# Kibana → Stack Monitoring: thấy cluster, 3 node, các index

Bước 2: Connector và rule

  1. Stack Management → Connectors → Create: loại Index, tên "Alert history", ghi vào index alert-history-lab. Connector này có ở bản miễn phí, phù hợp cho lab
  2. Stack Management → Rules → Create rule: loại Elasticsearch query, data view hoặc index .monitoring-es-8-mb, KQL elasticsearch.cluster.stats.status : "yellow" or elasticsearch.cluster.stats.status : "red", điều kiện "IS ABOVE 0" trong 2 phút gần nhất, chạy mỗi 1 phút
  3. Action: connector "Alert history", chạy khi trạng thái thay đổi, nội dung document có {{rule.name}}, {{context.date}}, {{context.hits}}

Stack Monitoring cũng có sẵn rule "Cluster health" (Stack Monitoring → Alerts and rules). Bật nó để so sánh với rule tự tạo.

Bước 3: Gây ra trạng thái yellow

# Yêu cầu nhiều replica hơn số node → replica không cấp phát được → yellow
curl $AUTH -X PUT "$ES/lab-yellow" -H 'Content-Type: application/json' \
  -d '{"settings":{"number_of_shards":1,"number_of_replicas":5}}'
curl $AUTH "$ES/_cluster/health?filter_path=status"

# Health Report giải thích nguyên nhân
curl $AUTH "$ES/_health_report/shards_availability?pretty"

Bước 4: Xác nhận cảnh báo và khôi phục

# Chờ 1–3 phút cho Metricbeat thu thập và rule chạy
curl $AUTH "$ES/alert-history-lab/_search?pretty&size=5"

# Khôi phục và kiểm tra rule trở về trạng thái bình thường
curl $AUTH -X DELETE "$ES/lab-yellow"
Xác minh thành công Stack Monitoring hiển thị cluster chuyển vàng, Health Report chỉ ra index lab-yellow thiếu replica, rule ghi một document vào alert-history-lab. Sau khi xóa index, rule trở về trạng thái OK và không gửi lặp. Thay connector Index bằng Slack/email/webhook là có cảnh báo thật.

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Chỉ giám sát bằng chính cluster production: cluster chết là mất luôn khả năng nhìn thấy.
  • Dùng legacy internal collection cho triển khai mới: đã deprecated, chuyển sang Metricbeat hoặc Agent.
  • Cảnh báo heap > 75% tức thời: báo liên tục theo nhịp GC, không ai còn đọc.
  • Không có cảnh báo "no data": Metricbeat chết thì mọi rule im lặng, trông như mọi thứ đều ổn.
  • Kibana thiếu encryption key: không tạo hoặc chạy được rule.
  • Cảnh báo không có hướng xử lý: người trực nhận cảnh báo lúc 3 giờ sáng mà không biết làm gì.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Monitoring cluster riêng, nhỏ, có ILM giữ 7–30 ngày
  • Thu thập bằng Elastic Agent qua Fleet hoặc Metricbeat với scope: cluster
  • Bật các rule Stack Monitoring có sẵn trước khi tự viết rule
  • Cảnh báo critical cho: cluster red, disk > 85%, thread pool rejection, mất monitoring data
  • Mỗi cảnh báo có runbook và link tới dashboard
  • Xem lại định kỳ cảnh báo nào hay bị bỏ qua để chỉnh hoặc gỡ
