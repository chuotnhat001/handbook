Case Studies Production

E-commerce search, centralized logging, SIEM, observability, fraud detection — áp dụng toàn bộ giáo trình

Nguồn: Elastic — Elasticsearch Guide, Elastic — Elastic Security

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Ghép kiến thức của 24 bài trước thành kiến trúc hoàn chỉnh cho 5 bài toán production phổ biến: search thương mại điện tử, centralized logging, SIEM, observability và phát hiện gian lận. Với mỗi bài toán, biết luồng dữ liệu, mapping và query cốt lõi, quyết định vận hành, và các rủi ro chính. Nhận ra các mẫu thiết kế lặp lại giữa các hệ thống.

Kiến Thức Tiên Quyết

  • Toàn bộ giáo trình, đặc biệt Bài 06–09 (mapping, analysis, search, aggregation), Bài 12–13 (ILM, bảo mật), Bài 15–17 (thu thập dữ liệu), Bài 22–23 (multi-cluster, data stream)
Về các case study Đây là các kiến trúc tham khảo tổng hợp từ những mẫu thiết kế phổ biến, không mô tả hệ thống của một công ty cụ thể nào. Con số trong bài là ví dụ để minh họa cách tính, cần thay bằng số liệu thật của bạn.

Case 1: E-commerce Search

Bài toán

Sàn thương mại điện tử với vài triệu sản phẩm. Người dùng gõ có dấu, không dấu, sai chính tả. Cần gợi ý khi gõ, bộ lọc kèm số lượng (facet), và xếp hạng kết hợp mức độ liên quan với độ phổ biến, tồn kho.

Kiến trúc

Database sản phẩm → CDC / Kafka → Indexer service → Elasticsearch (alias products) → Search API
  • Database là nguồn chân lý, Elasticsearch là bản đọc tối ưu cho search. Thay đổi đi qua Change Data Capture (CDC) để không bỏ sót
  • Indexer denormalize: gộp tên danh mục, thương hiệu, giá khuyến mãi, tồn kho vào một document
  • Alias products trỏ vào index thật. Khi đổi mapping: tạo index mới, reindex, chuyển alias trong một thao tác atomic

Mapping và query cốt lõi

"name": {
  "type": "text", "analyzer": "vietnamese",             // Bài 07: icu + asciifolding (preserve_original)
  "fields": {
    "keyword":  { "type": "keyword" },
    "suggest":  { "type": "search_as_you_type" }
  }
},
"category": { "type": "keyword" },
"brand":    { "type": "keyword" },
"price":    { "type": "scaled_float", "scaling_factor": 100 },
"in_stock": { "type": "boolean" },
"sold_30d": { "type": "integer" },
"attributes": { "type": "nested", "properties": { "name": {"type":"keyword"}, "value": {"type":"keyword"} } }
GET /products/_search
{
  "query": {
    "function_score": {
      "query": { "bool": {
        "must":   [ { "multi_match": { "query": "tai nghe bluetooth", "fields": ["name^3", "brand^2", "description"], "fuzziness": "AUTO" } } ],
        "filter": [ { "term": { "in_stock": true } }, { "range": { "price": { "lte": 2000000 } } } ]
      } },
      "functions": [ { "field_value_factor": { "field": "sold_30d", "modifier": "log1p", "factor": 0.3 } } ],
      "boost_mode": "sum"
    }
  },
  "aggs": {
    "brands": { "terms": { "field": "brand", "size": 20 } },
    "price_bands": { "range": { "field": "price", "ranges": [ {"to": 500000}, {"from": 500000, "to": 1500000}, {"from": 1500000} ] } }
  },
  "post_filter": { "terms": { "brand": ["sony"] } }
}

post_filter lọc kết quả hiển thị theo brand người dùng chọn, nhưng aggregation brands vẫn tính trên toàn bộ kết quả, nên bộ lọc vẫn hiện số lượng của các brand khác.

Quyết định vận hành

  • Index nhỏ (vài chục GB): 1–3 primary shard, nhiều replica để chia tải đọc
  • Cập nhật tồn kho, giá liên tục: gom cập nhật theo batch ngắn, refresh_interval 1–5 giây
  • Đo chất lượng search bằng tập query mẫu và Ranking Evaluation API (_rank_eval) trước mỗi lần đổi boost
  • Hybrid search: thêm dense_vector và kNN cho truy vấn mô tả bằng ngôn ngữ tự nhiên, kết hợp với BM25
Rủi ro chính Index lệch với database khi CDC lỗi mà không ai biết. Theo dõi độ trễ đồng bộ, và chạy định kỳ một job so sánh số lượng hoặc checksum giữa hai bên.

Case 2: Centralized Logging

Bài toán

Vài trăm microservice trên Kubernetes, vài trăm GB log mỗi ngày. Đội phát triển cần tìm log theo request id trong vài giây. Giữ 30 ngày để điều tra, 1 năm cho kiểm toán. Mỗi team chỉ xem log của mình.

Kiến trúc

Pod (stdout JSON) → Elastic Agent DaemonSet → Kafka (tùy chọn) → Ingest pipeline → Data stream logs-*-<team>
  • Log có cấu trúc (JSON) ngay từ ứng dụng, theo ECS: service.name, trace.id, log.level. Rẻ hơn nhiều so với grok sau này
  • Elastic Agent chạy dạng DaemonSet, quản lý qua Fleet (Bài 17), tự gắn metadata Kubernetes
  • Kafka đặt giữa khi cần chịu được cluster bảo trì hoặc đột biến traffic mà không mất log
  • Namespace theo team: logs-k8s.container-payments, phân quyền bằng role đọc logs-*-payments (Bài 13, 23)

Vòng đời dữ liệu

PUT /_ilm/policy/app-logs
{ "policy": { "phases": {
  "hot":    { "actions": { "rollover": { "max_primary_shard_size": "50gb", "max_age": "1d" } } },
  "warm":   { "min_age": "3d",  "actions": { "forcemerge": { "max_num_segments": 1 }, "shrink": { "number_of_shards": 1 } } },
  "frozen": { "min_age": "30d", "actions": { "searchable_snapshot": { "snapshot_repository": "s3-logs" } } },
  "delete": { "min_age": "365d", "actions": { "delete": { "delete_searchable_snapshot": true } } }
}}}

Quyết định vận hành

  • Bỏ log debug và healthcheck từ nguồn (processor drop) để giảm 20–40% khối lượng
  • Che dữ liệu nhạy cảm (số thẻ, CCCD, token) trong ingest pipeline trước khi lưu
  • Bật synthetic _source / LogsDB nếu license cho phép (Bài 23)
  • Cảnh báo "service X ngừng gửi log" song song với cảnh báo lỗi (Bài 18)
Rủi ro chính Mapping explosion khi ứng dụng log JSON với key động (ví dụ dùng user id làm tên field). Đặt dynamic: false hoặc flattened cho object tự do, và giới hạn total_fields (Bài 06).

Case 3: SIEM

Bài toán

Đội bảo mật cần thu thập log từ firewall, Active Directory, máy trạm, máy chủ, cloud audit log; phát hiện hành vi đáng ngờ theo thời gian gần thực; điều tra sự cố trên dữ liệu 6–12 tháng.

Kiến trúc

  • Nguồn: Elastic Agent với integration System, Windows, Elastic Defend trên endpoint; syslog từ firewall qua Agent hoặc Logstash; integration AWS CloudTrail, Azure, Okta...
  • Chuẩn hóa ECS: bắt buộc. Detection rule có sẵn dựa trên tên field ECS như event.category, source.ip, user.name
  • Elastic Security: detection rule (query, threshold, EQL sequence, ML), timeline điều tra, case management
  • Cluster riêng cho dữ liệu bảo mật, tách khỏi cluster log ứng dụng, quyền truy cập hẹp

Rule phát hiện

// Threshold: quá 20 lần đăng nhập thất bại cho một user trong 5 phút
event.category: "authentication" and event.outcome: "failure"
→ threshold: group by user.name, count >= 20, chạy mỗi 5 phút

// EQL sequence: đăng nhập thành công ngay sau chuỗi thất bại từ cùng IP
sequence by source.ip with maxspan=10m
  [authentication where event.outcome == "failure"] with runs=10
  [authentication where event.outcome == "success"]

EQL (Event Query Language) mô tả chuỗi sự kiện theo thứ tự thời gian, phù hợp với hành vi tấn công nhiều bước.

Quyết định vận hành

  • Audit log của chính cluster SIEM (Bài 13) gửi sang nơi đội bảo mật kiểm soát
  • Snapshot với object lock để chống kẻ tấn công xóa dấu vết (Bài 20)
  • Tinh chỉnh rule để giảm false positive, đánh dấu exception thay vì tắt rule
  • Giữ dữ liệu dài hạn ở frozen tier: điều tra thường cần nhìn lại vài tháng
Rủi ro chính Nguồn log ngừng gửi mà không ai biết: không có log thì không có cảnh báo. Theo dõi "last seen" của từng nguồn quan trọng và cảnh báo khi vượt ngưỡng.

Case 4: Observability

Bài toán

Khi khách hàng báo "thanh toán chậm", đội vận hành cần đi từ triệu chứng tới nguyên nhân: service nào chậm, request nào, log nào, máy nào quá tải.

Ba tín hiệu, một nơi lưu

Tín hiệuThu thậpLưu
MetricsElastic Agent (system, Kubernetes, Prometheus metrics)TSDS metrics-* + downsampling (Bài 23)
LogsElastic AgentData stream logs-*
TracesOpenTelemetry SDK hoặc Elastic APM agent trong ứng dụngData stream traces-apm-*
Cảnh báo latency p95 → Trace chậm → Span chậm nhất → Log theo trace.id → Metric host/pod
  • Tương quan bằng ID: ứng dụng ghi trace.id vào mọi dòng log. Đây là điều kiện để nhảy từ trace sang log
  • OpenTelemetry: dùng SDK chuẩn mở để không phụ thuộc nhà cung cấp, gửi tới APM Server/OTLP endpoint của Elastic
  • Sampling: trace 100% request rất tốn kém. Lấy mẫu theo tỷ lệ, nhưng giữ lại mọi trace có lỗi (tail-based sampling)
# Tìm mọi log của một request chậm
GET /logs-*/_search
{ "query": { "term": { "trace.id": "4bf92f3577b34da6a3ce929d0e0e4736" } },
  "sort": [ { "@timestamp": "asc" } ] }

Quyết định vận hành

  • Cảnh báo theo SLO (tỷ lệ request thành công và đủ nhanh), không theo từng metric hạ tầng
  • Metric độ phân giải cao giữ ngắn, downsampling cho dài hạn
  • Nếu đội đã dùng Prometheus/Grafana, có thể giữ metric ở đó và chỉ đưa log, trace vào Elasticsearch (Bài 24)

Case 5: Fraud Detection

Bài toán

Ngân hàng hoặc ví điện tử cần đánh dấu giao dịch đáng ngờ: nhiều giao dịch nhỏ liên tiếp, đăng nhập từ thiết bị hoặc quốc gia lạ, số tiền bất thường so với thói quen của khách hàng.

Vai trò của Elasticsearch

Elasticsearch thường không là nơi ra quyết định chặn giao dịch theo thời gian thực (việc đó thuộc hệ thống chấm điểm trong luồng thanh toán, độ trễ mili giây). Elasticsearch phù hợp cho:

  • Tính đặc trưng (feature) gần thời gian thực: số giao dịch của khách trong 10 phút, số tiền trung bình 30 ngày, số thiết bị khác nhau
  • Phát hiện bất thường sau giao dịch: rule và ML anomaly detection
  • Điều tra: chuyên viên tìm toàn bộ hoạt động của một tài khoản, thiết bị, IP
# Feature: số giao dịch và tổng tiền của một khách trong 10 phút gần nhất
GET /transactions-*/_search
{
  "size": 0,
  "query": { "bool": { "filter": [
    { "term":  { "customer.id": "C-102938" } },
    { "range": { "@timestamp": { "gte": "now-10m" } } }
  ] } },
  "aggs": {
    "tx_count":  { "value_count": { "field": "transaction.id" } },
    "tx_sum":    { "sum":   { "field": "transaction.amount" } },
    "devices":   { "cardinality": { "field": "device.id" } },
    "countries": { "terms": { "field": "source.geo.country_iso_code" } }
  }
}
# Transform: duy trì index tóm tắt hành vi từng khách hàng, cập nhật liên tục
PUT /_transform/customer-profile
{
  "source": { "index": "transactions-*" },
  "dest":   { "index": "customer-profile" },
  "pivot": {
    "group_by": { "customer.id": { "terms": { "field": "customer.id" } } },
    "aggregations": {
      "avg_amount_30d": { "avg": { "field": "transaction.amount" } },
      "max_amount_30d": { "max": { "field": "transaction.amount" } },
      "last_seen":      { "max": { "field": "@timestamp" } }
    }
  },
  "frequency": "1m",
  "sync": { "time": { "field": "@timestamp", "delay": "60s" } }
}

Hệ thống chấm điểm tra customer-profile theo ID (Get API, real-time, Bài 05) để so sánh giao dịch mới với thói quen của khách.

Quyết định vận hành

  • Document level security theo chi nhánh hoặc vai trò, field level security ẩn số tài khoản đầy đủ (Bài 13)
  • Audit log mọi truy cập dữ liệu khách hàng, đáp ứng yêu cầu quy định
  • CCR sang DC dự phòng (Bài 22), snapshot theo chính sách lưu giữ của ngành
  • Mã hóa disk và TLS mọi lớp
Rủi ro chính Dữ liệu tài chính và cá nhân rò rỉ qua quyền đọc quá rộng hoặc highlight/log chứa dữ liệu nhạy cảm. Che dữ liệu ngay từ ingest pipeline, cấp quyền tối thiểu, và rà soát quyền định kỳ.

Lỗi Thường Gặp

Những lỗi phổ biến khi đưa hệ thống lên production:
  • Thiết kế từ công nghệ thay vì từ truy vấn: mapping không phục vụ được câu hỏi nghiệp vụ, phải reindex.
  • Bỏ qua chuẩn hóa dữ liệu ở nguồn: mỗi team đặt tên field một kiểu, dashboard và rule không dùng chung được.
  • Bảo mật làm sau: bật security trên cluster đang chạy cần restart toàn bộ (Bài 13).
  • Không có vòng đời dữ liệu: disk đầy sau vài tháng, cluster red vào lúc bận nhất.
  • Có backup nhưng chưa từng restore: không biết RTO thật.
  • Không giám sát chính hệ thống giám sát: mọi thứ im lặng không có nghĩa là mọi thứ ổn.

  • Bắt đầu từ câu hỏi nghiệp vụ, thiết kế mapping và query trước khi thu thập dữ liệu
  • Chuẩn hóa theo ECS, đặt tên data stream theo naming scheme
  • Bảo mật, vòng đời, giám sát và backup có ngay từ ngày đầu, không để sau
  • Đo bằng dữ liệu thật trước khi chốt số shard, retention và phần cứng
  • Viết tài liệu kiến trúc và runbook song song với triển khai
