Logstash — Data Pipeline

Input → Filter → Output, grok, dissect, mutate, date, persistent queue, dead letter queue

Nguồn: Elastic — Logstash Reference, Elastic — Persistent Queues

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Hiểu kiến trúc input → filter → output của Logstash và khi nào nên dùng nó thay vì ingest pipeline. Bóc tách log bằng grok và dissect, chuẩn hóa bằng mutate, date, geoip. Rẽ nhánh xử lý bằng điều kiện. Gửi dữ liệu an toàn tới Elasticsearch có TLS. Bảo vệ dữ liệu bằng persistent queue và dead letter queue. Chạy nhiều pipeline và theo dõi chúng.

Kiến Trúc: Input → Filter → Output

Logstash là engine xử lý dữ liệu chạy trên JVM. Mỗi pipeline gồm ba tầng, mỗi tầng là một chuỗi plugin:

Input (beats, kafka, file, jdbc...) → Queue → Filter (grok, mutate, date...) → Output (elasticsearch, kafka, s3...) 
# pipeline/apache.conf
input {
  beats { port => 5044 }
}
filter {
  grok { match => { "message" => "%{COMBINEDAPACHELOG}" } }
}
output {
  elasticsearch { hosts => ["https://es01:9200"] }
}
  • Input đọc dữ liệu và tạo event (một document JSON có các field)
  • Các worker thread lấy event từ queue theo batch, chạy toàn bộ filter rồi output
  • pipeline.workers (mặc định bằng số CPU) và pipeline.batch.size (mặc định 125) quyết định throughput

Grok & Dissect

Grok: bóc tách bằng pattern regex có tên

Log: 2026-10-28 08:15:42 ERROR [order-service] Payment timeout after 3000ms user=u_42

filter {
  grok {
    match => { "message" => "%{TIMESTAMP_ISO8601:log_time} %{LOGLEVEL:level} \[%{DATA:service}\] %{GREEDYDATA:msg} user=%{WORD:user_id}" }
    tag_on_failure => ["_grok_failed"]
  }
}
# → log_time, level=ERROR, service=order-service, msg=..., user_id=u_42

Cú pháp %{PATTERN:field}, ép kiểu bằng %{NUMBER:bytes:int}. Logstash có sẵn pattern cho Apache, Nginx, syslog, Java stack trace...

# Pattern tự định nghĩa
grok {
  pattern_definitions => { "ORDER_ID" => "ORD-[0-9]{8}" }
  match => { "message" => "order %{ORDER_ID:order_id} created" }
}

Dissect: tách theo dấu phân cách, không dùng regex

Log: 2026-10-28T08:15:42Z|INFO|checkout|200|153

filter {
  dissect {
    mapping => { "message" => "%{ts}|%{level}|%{service}|%{status}|%{latency_ms}" }
    convert_datatype => { "status" => "int" "latency_ms" => "int" }
  }
}
GrokDissect
Cơ chếRegexDấu phân cách cố định
Tốc độChậm hơn, có thể rất chậm với pattern xấuNhanh
Phù hợpLog không đều định dạngLog có cấu trúc cố định
Grok chậm GREEDYDATA và DATA đặt sai chỗ khiến regex quay lui (backtracking) rất nhiều, đặc biệt khi không khớp. Neo pattern bằng ^, dùng pattern cụ thể nhất có thể, và cân nhắc dissect trước rồi mới grok phần còn lại. Thử pattern bằng Grok Debugger trong Kibana Dev Tools (Bài 14).

Mutate, Date, GeoIP

filter {
  # Đặt @timestamp theo thời gian trong log, không theo thời điểm Logstash nhận
  date {
    match => [ "log_time", "yyyy-MM-dd HH:mm:ss", "ISO8601" ]
    timezone => "Asia/Ho_Chi_Minh"
    target => "@timestamp"
  }

  mutate {
    rename       => { "msg" => "[event][message]" }
    convert      => { "latency_ms" => "integer" }
    lowercase    => [ "level" ]
    remove_field => [ "log_time" ]
    add_field    => { "[event][dataset]" => "orders.app" }
  }

  # Tra vị trí địa lý từ IP (dùng database GeoLite2 đi kèm)
  geoip {
    source => "client_ip"
    target => "client.geo"
  }

  # Che dữ liệu nhạy cảm trước khi lưu
  mutate {
    gsub => [ "[event][message]", "\b\d{12,19}\b", "[REDACTED]" ]
  }
}
Đặt tên field theo ECS Elastic Common Schema (ECS) quy ước tên field chung (@timestamp, log.level, service.name, client.ip, http.response.status_code...). Theo ECS giúp dashboard và rule bảo mật có sẵn của Elastic hoạt động ngay với dữ liệu của bạn.

Điều Kiện & Tag

filter {
  if [service] == "payment" {
    mutate { add_tag => ["pci"] }
  }

  if [level] in ["error", "fatal"] {
    mutate { add_field => { "alert" => "true" } }
  } else if [level] == "debug" {
    drop { }                       # bỏ log debug, không gửi đi
  }

  if "_grok_failed" in [tags] {
    mutate { add_field => { "[event][original]" => "%{message}" } }
  }
}

output {
  if "pci" in [tags] {
    elasticsearch { index => "logs-payment-%{+YYYY.MM.dd}" ... }
  } else {
    elasticsearch { data_stream => "true" ... }
  }
}

Tham chiếu field lồng nhau bằng [parent][child], chèn giá trị field vào chuỗi bằng %{field}, ngày tháng bằng %{+YYYY.MM.dd}.

Output Tới Elasticsearch

output {
  elasticsearch {
    hosts => ["https://es01:9200", "https://es02:9200", "https://es03:9200"]
    ssl_enabled => true
    ssl_certificate_authorities => ["/usr/share/logstash/certs/ca/ca.crt"]
    api_key => "${ES_API_KEY}"     # dạng id:api_key, đọc từ keystore hoặc biến môi trường

    # Ghi vào data stream logs-orders.app-default
    data_stream => "true"
    data_stream_type => "logs"
    data_stream_dataset => "orders.app"
    data_stream_namespace => "default"
  }
}
  • Output tự gom event thành bulk request và phân tải qua các host
  • Lỗi tạm thời (429, 503, mất kết nối) được retry vô hạn với backoff, nên Logstash tự chậm lại khi cluster quá tải (backpressure)
  • Lỗi vĩnh viễn (400 mapping conflict) không retry được: event bị bỏ, trừ khi bật dead letter queue
# Lưu secret vào keystore của Logstash
bin/logstash-keystore create
bin/logstash-keystore add ES_API_KEY

API key cho Logstash cần quyền ghi vào data stream đích, ví dụ privileges create_doc và auto_configure trên logs-*-* (Bài 13).

Persistent Queue & Dead Letter Queue

Persistent queue (PQ)

Mặc định Logstash dùng memory queue: Logstash crash là mất các event đang nằm trong bộ nhớ. Persistent queue ghi event xuống disk trước khi xử lý.

# logstash.yml (hoặc theo từng pipeline trong pipelines.yml)
queue.type: persisted
queue.max_bytes: 4gb        # đầy thì input bị chặn (backpressure)
path.queue: /var/lib/logstash/queue
  • Chịu được Logstash restart hoặc crash mà không mất event đã nhận
  • Hấp thụ đột biến traffic khi Elasticsearch chậm
  • Không thay thế được bộ đệm ở nguồn: Logstash hỏng disk thì vẫn mất dữ liệu trong PQ. Với yêu cầu không mất dữ liệu, đặt Kafka phía trước

Dead letter queue (DLQ)

Event bị Elasticsearch từ chối vĩnh viễn (400, 404) được ghi vào DLQ thay vì bị bỏ, để xử lý lại sau.

# logstash.yml
dead_letter_queue.enable: true
dead_letter_queue.max_bytes: 1gb

# Pipeline riêng đọc lại DLQ, sửa lỗi rồi gửi lại
input {
  dead_letter_queue {
    path => "/usr/share/logstash/data/dead_letter_queue"
    pipeline_id => "main"
    commit_offsets => true
  }
}
filter {
  # [@metadata][dead_letter_queue][reason] chứa lý do bị từ chối
  mutate { convert => { "status" => "string" } }
}
output { elasticsearch { ... } }

Nhiều Pipeline & Monitoring

# config/pipelines.yml
- pipeline.id: apache
  path.config: "/usr/share/logstash/pipeline/apache.conf"
  pipeline.workers: 4
  queue.type: persisted
- pipeline.id: orders
  path.config: "/usr/share/logstash/pipeline/orders.conf"
  pipeline.workers: 2

Tách pipeline theo nguồn dữ liệu giúp một nguồn chậm không làm nghẽn nguồn khác, và cấu hình workers, queue riêng cho từng loại. Pipeline có thể chuyển event cho nhau qua pipeline { send_to => ["orders"] } và pipeline { address => "orders" } (pipeline-to-pipeline).

# Monitoring API (cổng 9600)
curl "http://localhost:9600/_node/stats/pipelines?pretty"
# Xem events.in/out, duration_in_millis của từng plugin để tìm filter chậm

# Kiểm tra cú pháp cấu hình trước khi khởi động
bin/logstash -f pipeline/apache.conf --config.test_and_exit

Đặt id cho mỗi plugin (grok { id => "parse_apache" ... }) để số liệu monitoring dễ đọc. Kibana Stack Monitoring (Bài 18) hiển thị cùng số liệu này dạng biểu đồ.

Bài Lab: Pipeline Xử Lý Apache Access Log + Enrichment

Bước 1: Dữ liệu mẫu

mkdir -p logstash/pipeline logstash/data-in
cat > logstash/data-in/access.log <<'EOF'
203.113.152.10 - - [28/Oct/2026:08:15:42 +0700] "GET /api/products?page=2 HTTP/1.1" 200 5120 "-" "Mozilla/5.0 Chrome/129.0"
8.8.8.8 - - [28/Oct/2026:08:15:43 +0700] "POST /api/orders HTTP/1.1" 201 312 "https://shop.example/cart" "Mozilla/5.0 Safari/17.0"
113.161.70.5 - - [28/Oct/2026:08:16:01 +0700] "GET /api/products/9999 HTTP/1.1" 404 98 "-" "curl/8.5.0"
203.113.152.10 - - [28/Oct/2026:08:16:05 +0700] "GET /api/checkout HTTP/1.1" 500 210 "-" "Mozilla/5.0 Chrome/129.0"
this line is not an apache log
EOF

Bước 2: Pipeline

cat > logstash/pipeline/apache.conf <<'EOF'
input {
  file {
    path => "/data-in/access.log"
    start_position => "beginning"
    sincedb_path => "/dev/null"     # chỉ cho lab: đọc lại từ đầu mỗi lần chạy
  }
}
filter {
  grok {
    id => "parse_apache"
    match => { "message" => "%{COMBINEDAPACHELOG}" }
    tag_on_failure => ["_grok_failed"]
  }
  if "_grok_failed" not in [tags] {
    date {
      match => [ "timestamp", "dd/MMM/yyyy:HH:mm:ss Z" ]
      target => "@timestamp"
    }
    geoip {
      source => "[source][address]"
      target => "[source]"
      ecs_compatibility => "v8"
    }
    useragent {
      source => "[user_agent][original]"
      target => "[user_agent]"
    }
    if [http][response][status_code] >= 500 {
      mutate { add_tag => ["server_error"] }
    }
    mutate { remove_field => [ "timestamp" ] }
  }
}
output {
  elasticsearch {
    hosts => ["https://es01:9200"]
    ssl_enabled => true
    ssl_certificate_authorities => ["/usr/share/logstash/certs/ca/ca.crt"]
    api_key => "${ES_API_KEY}"
    data_stream => "true"
    data_stream_dataset => "apache.access"
  }
  stdout { codec => rubydebug { metadata => false } }
}
EOF
Tên field theo ECS Từ Logstash 8, COMBINEDAPACHELOG mặc định sinh field theo ECS: source.address, http.request.method, url.original, http.response.status_code, user_agent.original... Chạy lần đầu với output stdout để xem đúng tên field ở version của bạn trước khi viết điều kiện.

Checklist Kiến Thức

  • ☐ Viết pipeline đủ ba tầng input, filter, output
  • ☐ Bóc tách log bằng grok và dissect
  • ☐ Chuẩn hóa thời gian, kiểu dữ liệu, tên field theo ECS
  • ☐ Dùng điều kiện, tag và drop
  • ☐ Gửi tới Elasticsearch qua TLS bằng API key trong keystore
  • ☐ Bật persistent queue và dead letter queue
  • ☐ Cấu hình pipelines.yml và đọc monitoring API

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Không dùng filter date: @timestamp là lúc Logstash nhận, sai lệch khi log đến trễ hoặc khi đọc lại log cũ.
  • Bỏ qua tag _grok_failed: dòng không khớp pattern lặng lẽ đi vào index với field thiếu.
  • Memory queue cho dữ liệu quan trọng: restart hoặc crash là mất event.
  • API key hoặc mật khẩu trong file .conf: dùng keystore hoặc biến môi trường.
  • sincedb_path => "/dev/null" ở production: mỗi lần restart đọc lại toàn bộ file, sinh dữ liệu trùng.
  • Một pipeline khổng lồ cho mọi nguồn: một nguồn lỗi làm nghẽn tất cả.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Ưu tiên ingest pipeline khi đủ dùng, chỉ thêm Logstash khi có lý do cụ thể
  • Đặt id cho mọi plugin, theo dõi duration của từng filter
  • Dùng dissect cho phần có cấu trúc cố định, grok cho phần còn lại
  • Bật persistent queue cho pipeline quan trọng, đặt Kafka phía trước khi yêu cầu không được mất dữ liệu
  • Kiểm tra cấu hình bằng --config.test_and_exit trong CI trước khi triển khai
  • Theo ECS khi đặt tên field
