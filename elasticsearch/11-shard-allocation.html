Shard Allocation & Strategy

Shard sizing, over-sharding, allocation filtering, disk watermark, rebalancing — đặt shard đúng chỗ, đúng cỡ

Nguồn: Elastic — Size Your Shards, Elastic — Cluster-level Shard Allocation

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Chọn kích thước và số lượng shard hợp lý cho một index. Nhận biết và xử lý over-sharding. Dùng shrink/split để đổi số primary shard. Điều khiển shard nằm ở node nào bằng allocation filtering. Hiểu ba ngưỡng disk watermark và cách cluster phản ứng khi disk đầy. Kiểm soát rebalancing và recovery.

Kiến Thức Tiên Quyết

  • Bài 03: Kiến Trúc ES — Shard = Lucene index, cluster state
  • Bài 10: Cluster Management — Allocation explain, allocation exclude

Shard Sizing

Không có con số đúng cho mọi trường hợp, nhưng Elastic đưa ra các mốc khởi điểm:

Tiêu chíKhuyến nghị
Kích thước một shardKhoảng 10–50 GB
Số document một shardDưới 200 triệu
Dữ liệu time-seriesDùng rollover theo kích thước (Bài 12) để mỗi shard tự đạt cỡ mục tiêu
Tư duy cốt lõi Shard là đơn vị phân tán và đơn vị phục hồi. Shard quá nhỏ: tốn overhead và làm cluster state phình. Shard quá lớn: recovery và rebalance chậm, mất node lâu hồi phục. Mục tiêu là đủ lớn để overhead không đáng kể, đủ nhỏ để di chuyển nhanh.

Ước tính số primary shard

Dữ liệu dự kiến sau 1 năm: 600 GB (chưa tính replica)
Kích thước shard mục tiêu:  30 GB
→ Số primary ≈ 600 / 30 = 20

Với dữ liệu time-series: không cần đoán trước.
Đặt 1-2 primary cho mỗi index nền, rollover khi đạt max_primary_shard_size: 50gb.

Search song song theo shard: một query trên index 20 shard chạy trên 20 shard (mỗi shard một thread). Nhiều shard hơn không phải lúc nào cũng nhanh hơn, vì các shard cạnh tranh cùng CPU của node.

Over-sharding

Over-sharding là có quá nhiều shard nhỏ so với lượng dữ liệu. Đây là nguyên nhân phổ biến nhất khiến cluster chậm hoặc không ổn định.

  • Mỗi index, shard và field tốn heap trên master (cluster state) và data node (metadata)
  • Cluster state lớn làm việc publish chậm, master dễ quá tải (Bài 03)
  • Search phải gom kết quả từ nhiều shard nhỏ, tốn overhead điều phối
  • Recovery sau sự cố phải xử lý hàng nghìn shard
# Đếm shard theo node
GET /_cat/allocation?v

# Tìm index nhỏ có nhiều shard
GET /_cat/indices?v&h=index,pri,rep,docs.count,store.size&s=store.size:asc

# Giới hạn an toàn mặc định
GET /_cluster/settings?include_defaults=true&filter_path=**.max_shards_per_node
cluster.max_shards_per_node Mặc định 1000 shard (không tính frozen tier) cho mỗi data node. Khi chạm giới hạn, ES từ chối tạo index mới. Nâng giới hạn chỉ là chữa triệu chứng. Cách xử lý gốc: gộp index nhỏ, giảm số primary, xóa index không dùng, hoặc dùng ILM để rollover theo kích thước.

Các mẫu gây over-sharding

  • Tạo index theo ngày cho dữ liệu chỉ vài MB/ngày, kèm 5 primary shard mặc định của template cũ
  • Một index cho mỗi khách hàng (tenant) với hàng nghìn tenant nhỏ. Cân nhắc gộp chung và dùng routing theo tenant_id
  • Giữ lại vô thời hạn index cũ không còn truy vấn

Shrink & Split

Số primary shard cố định khi tạo index (Bài 03). Có hai API tạo index mới với số shard khác, nhanh hơn reindex vì dùng hard-link segment khi có thể.

Shrink: giảm số shard

# 1. Dồn một bản sao của mọi shard về cùng node, chặn ghi
PUT /logs-2026.09/_settings
{
  "index.routing.allocation.require._name": "es01",
  "index.blocks.write": true
}

# 2. Chờ relocation xong (green)
GET /_cluster/health/logs-2026.09?wait_for_status=green&wait_for_no_relocating_shards=true

# 3. Shrink 6 → 1 shard. Số shard đích phải là ước số của số shard gốc
POST /logs-2026.09/_shrink/logs-2026.09-shrunk
{
  "settings": {
    "index.number_of_shards": 1,
    "index.number_of_replicas": 1,
    "index.routing.allocation.require._name": null,
    "index.blocks.write": null
  }
}

Split: tăng số shard

PUT /orders/_settings
{ "index.blocks.write": true }

# Số shard đích phải là bội số của số shard gốc (2 → 4, 6, 8...)
POST /orders/_split/orders-v2
{ "settings": { "index.number_of_shards": 4 } }
Sau shrink/split Index mới có tên khác. Chuyển ứng dụng sang index mới bằng alias để không phải đổi code, rồi xóa index cũ khi đã xác minh. ILM (Bài 12) có action shrink tự làm việc này ở warm phase.

Allocation Filtering

Allocation filtering quyết định shard của một index được phép nằm trên node nào, dựa vào thuộc tính có sẵn (_name, _ip, _host) hoặc thuộc tính tự định nghĩa (node.attr.*).

RuleÝ nghĩa
requireNode phải có tất cả giá trị liệt kê
includeNode phải có ít nhất một giá trị liệt kê
excludeNode không được có giá trị nào trong danh sách
# elasticsearch.yml: gắn nhãn phần cứng
node.attr.disk_type: ssd

# Index tìm kiếm nóng chỉ nằm trên node SSD
PUT /products/_settings
{ "index.routing.allocation.require.disk_type": "ssd" }

# Không cho index nằm trên 2 node đang bảo trì
PUT /products/_settings
{ "index.routing.allocation.exclude._name": "es04,es05" }

# Giới hạn số shard của index trên mỗi node, tránh dồn nhiều shard nóng vào một node
PUT /products/_settings
{ "index.routing.allocation.total_shards_per_node": 2 }
total_shards_per_node quá chặt Nếu tổng shard (primary + replica) lớn hơn số node × total_shards_per_node, một số shard sẽ không bao giờ được cấp phát. Khi mất một node, giới hạn này cũng có thể chặn phục hồi. Chừa dư ít nhất một node.

Cho dữ liệu hot/warm/cold, ưu tiên dùng data tiers (role data_hot, data_warm...) thay vì tự định nghĩa attribute. ILM tự di chuyển shard giữa các tier (Bài 12).

Disk Watermark

ES theo dõi dung lượng disk của từng node và phản ứng theo ba ngưỡng:

NgưỡngMặc địnhPhản ứng
low85% đã dùngKhông cấp phát shard mới (replica, index mới) lên node này. Primary của index mới tạo vẫn được cấp phát
high90%Chủ động di chuyển shard ra khỏi node
flood_stage95%Đặt index.blocks.read_only_allow_delete cho mọi index có shard trên node: chặn ghi
# Xem dung lượng disk theo node
GET /_cat/allocation?v&h=node,shards,disk.percent,disk.used,disk.avail

# Điều chỉnh ngưỡng (có thể dùng giá trị tuyệt đối dạng dung lượng còn trống)
PUT /_cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.disk.watermark.low": "85%",
    "cluster.routing.allocation.disk.watermark.high": "90%",
    "cluster.routing.allocation.disk.watermark.flood_stage": "95%"
  }
}
Khi chạm flood_stage Ứng dụng nhận lỗi HTTP 429 cluster_block_exception với thông điệp kiểu TOO_MANY_REQUESTS/12/disk usage exceeded flood-stage watermark, index has read-only-allow-delete block. Từ ES 7.4, block tự gỡ khi disk xuống dưới high watermark. Hướng xử lý: xóa index cũ, giảm replica tạm thời, hoặc thêm node/disk. Không xử lý bằng cách nâng watermark lên 99%: khi disk đầy hẳn, Lucene không ghi được segment và node có thể hỏng dữ liệu.

Rebalancing & Recovery

Master liên tục cân bằng shard giữa các node, dựa trên số shard, dung lượng disk và tải ghi ước tính. Từ ES 8.6, thuật toán desired balance tính trước trạng thái đích rồi di chuyển dần, giảm việc chuyển qua chuyển lại.

PUT /_cluster/settings
{
  "persistent": {
    "cluster.routing.rebalance.enable": "all",
    "cluster.routing.allocation.cluster_concurrent_rebalance": 2,
    "indices.recovery.max_bytes_per_sec": "100mb"
  }
}

# Theo dõi shard đang di chuyển
GET /_cat/recovery?v&active_only=true&h=index,shard,stage,source_node,target_node,bytes_percent
rebalance.enableÝ nghĩa
all (mặc định)Rebalance mọi shard
primaries / replicasChỉ rebalance một loại
noneTắt rebalance (dùng tạm khi bảo trì)

Khác biệt giữa allocation và rebalance: allocation là cấp phát shard chưa có chỗ (unassigned), rebalance là di chuyển shard đã có chỗ để cân bằng. allocation.enable (Bài 10) và rebalance.enable là hai setting riêng.

Bài Lab: Rebalance, Filtering & Watermark

Chuẩn bị

Dùng cluster 5 node từ Bài 10 (security tắt, chỉ dùng cục bộ).

Bước 1: Quan sát phân bổ hiện tại

curl -X PUT "http://localhost:9200/lab-alloc" -H 'Content-Type: application/json' \
  -d '{"settings":{"number_of_shards":5,"number_of_replicas":1}}'
curl "http://localhost:9200/_cat/allocation?v"
curl "http://localhost:9200/_cat/shards/lab-alloc?v&h=shard,prirep,node"

Bước 2: Đẩy index ra khỏi es04, es05

curl -X PUT "http://localhost:9200/lab-alloc/_settings" -H 'Content-Type: application/json' \
  -d '{"index.routing.allocation.exclude._name":"es04,es05"}'
# Quan sát shard chuyển về es01-es03
curl "http://localhost:9200/_cat/shards/lab-alloc?v&h=shard,prirep,node"

# Gỡ rule, shard rebalance trở lại 5 node
curl -X PUT "http://localhost:9200/lab-alloc/_settings" -H 'Content-Type: application/json' \
  -d '{"index.routing.allocation.exclude._name":null}'

Bước 3: Mô phỏng flood_stage

Trong lab Docker, mọi node dùng chung disk của máy host. Hạ ngưỡng xuống rất thấp để mọi node "vượt" ngưỡng:

curl -X PUT "http://localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d '{
  "persistent": {
    "cluster.routing.allocation.disk.watermark.low": "1%",
    "cluster.routing.allocation.disk.watermark.high": "2%",
    "cluster.routing.allocation.disk.watermark.flood_stage": "3%"
  }}'

# Chờ khoảng 30 giây (chu kỳ kiểm tra disk), thử ghi
curl -X POST "http://localhost:9200/lab-alloc/_doc" -H 'Content-Type: application/json' -d '{"x":1}'
# Mong đợi lỗi 429 cluster_block_exception: index read-only / allow delete

curl "http://localhost:9200/lab-alloc/_settings?filter_path=**.blocks"

Bước 4: Khôi phục

curl -X PUT "http://localhost:9200/_cluster/settings" -H 'Content-Type: application/json' -d '{
  "persistent": {
    "cluster.routing.allocation.disk.watermark.low": null,
    "cluster.routing.allocation.disk.watermark.high": null,
    "cluster.routing.allocation.disk.watermark.flood_stage": null
  }}'
# Block tự gỡ khi disk dưới high watermark. Nếu không, gỡ tay:
curl -X PUT "http://localhost:9200/lab-alloc/_settings" -H 'Content-Type: application/json' \
  -d '{"index.blocks.read_only_allow_delete":null}'
Xác minh thành công Bạn đã thấy: allocation filtering di chuyển shard theo rule, rebalance tự trả shard về khi gỡ rule, và flood_stage chặn ghi bằng index block. Ghi nhớ thông báo lỗi ở bước 3 để nhận ra ngay khi gặp ở production.

Checklist Kiến Thức

  • ☐ Ước tính được số primary shard từ dung lượng dữ liệu
  • ☐ Nhận diện over-sharding qua _cat/allocation và _cat/indices
  • ☐ Thực hiện shrink và split
  • ☐ Dùng allocation filtering với attribute tự định nghĩa
  • ☐ Hiểu và cấu hình ba ngưỡng disk watermark

  • ☐ Kiểm soát tốc độ rebalance và recovery

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Index theo ngày cho dữ liệu nhỏ: hàng nghìn shard vài MB. Dùng rollover theo kích thước.
  • Nâng max_shards_per_node thay vì giảm shard: trì hoãn sự cố, không giải quyết nó.
  • Nâng watermark để cluster ghi tiếp: có nguy cơ disk đầy hẳn và hỏng dữ liệu.
  • Quên gỡ index.blocks.write sau shrink: index mới không ghi được.
  • total_shards_per_node vừa khít số node: mất một node là có shard unassigned vĩnh viễn.
  • Tắt rebalance rồi quên bật lại: shard dồn lệch về vài node theo thời gian.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Nhắm 10–50 GB mỗi shard, dữ liệu time-series dùng rollover theo max_primary_shard_size
  • Theo dõi tổng số shard và số shard mỗi node như một metric vận hành
  • Cảnh báo khi disk vượt 80%, trước khi chạm low watermark
  • Dùng data tiers cho hot/warm/cold thay vì attribute tự đặt
  • Dùng alias để chuyển ứng dụng sang index sau khi shrink, split hoặc reindex
