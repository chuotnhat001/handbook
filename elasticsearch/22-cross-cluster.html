Cross-Cluster Search & Replication

CCS truy vấn nhiều cluster, CCR leader/follower, kiến trúc multi-datacenter và failover

Nguồn: Elastic — Cross-Cluster Search, Elastic — Cross-Cluster Replication

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Kết nối cluster với remote cluster theo chế độ sniff hoặc proxy. Hiểu hai mô hình bảo mật cho kết nối giữa các cluster. Truy vấn dữ liệu trên nhiều cluster bằng Cross-Cluster Search (CCS). Sao chép index giữa các cluster bằng Cross-Cluster Replication (CCR), cấu hình auto-follow cho dữ liệu time-series. Thực hiện failover khi cluster chính gặp sự cố. Chọn kiến trúc multi-datacenter phù hợp.

Kết Nối Remote Cluster

Một cluster (local) khai báo cluster khác là remote cluster bằng một alias. Node gửi request ra ngoài cần role remote_cluster_client (có sẵn mặc định khi không cấu hình node.roles).

Chế độCách kết nốiKhi nào dùng
sniff (mặc định)Kết nối tới seed node, lấy danh sách node rồi nối thẳng tới các gateway nodeHai cluster cùng mạng, local nhìn thấy trực tiếp mọi node của remote
proxyMọi kết nối đi qua một địa chỉ duy nhất (load balancer, proxy)Remote nằm sau NAT, Kubernetes, cloud, chỉ mở một endpoint
# Trên cluster local: đặt alias "dc2" cho cluster ở datacenter thứ hai
PUT /_cluster/settings
{
  "persistent": {
    "cluster.remote.dc2.mode": "sniff",
    "cluster.remote.dc2.seeds": ["10.1.0.1:9300", "10.1.0.2:9300"],
    "cluster.remote.dc2.skip_unavailable": true
  }
}

# Hoặc chế độ proxy
PUT /_cluster/settings
{ "persistent": { "cluster.remote.dc2.mode": "proxy",
                  "cluster.remote.dc2.proxy_address": "es-dc2.example.com:9300" } }

# Kiểm tra trạng thái kết nối
GET /_remote/info
skip_unavailable Từ ES 8.15, mặc định là true: remote không khả dụng thì CCS bỏ qua cluster đó và trả kết quả từ các cluster còn lại (response ghi rõ cluster nào bị bỏ qua). Đặt false khi kết quả thiếu một cluster là không chấp nhận được. Ở các version trước, mặc định là false.

Cross-Cluster Search

CCS cho phép một request search chạy trên index của nhiều cluster cùng lúc. Cú pháp: <alias>:<index>.

# Tìm trên cluster local và hai remote
GET /logs-*,dc2:logs-*,dc3:logs-*/_search
{
  "query": { "match": { "message": "payment timeout" } },
  "aggs": { "by_cluster": { "terms": { "field": "_index" } } }
}

# Mọi remote cluster
GET /*:logs-*/_search

# Async search cho truy vấn dài trên nhiều cluster
POST /logs-*,dc2:logs-*/_async_search?wait_for_completion_timeout=2s&keep_alive=5m
{ "query": { ... } }
GET /_async_search/<id>
ccs_minimize_roundtripsHành vi
true (mặc định)Mỗi cluster tự thực hiện search và trả về kết quả đã gom. Ít round-trip qua mạng WAN, phù hợp khi latency giữa cluster cao
falseLocal điều phối trực tiếp từng shard của remote như shard của chính nó
  • Kibana data view có thể dùng pattern dc2:logs-* để dashboard hiển thị dữ liệu của nhiều cluster
  • Response có mục _clusters cho biết bao nhiêu cluster thành công, bị bỏ qua, hoặc lỗi
  • Version tương thích: CCS hỗ trợ remote cluster khác version trong một phạm vi giới hạn. Xem bảng tương thích trong tài liệu trước khi nâng cấp lệch
Tư duy cốt lõi CCS để dữ liệu ở nguyên chỗ và đưa query tới dữ liệu. Phù hợp khi dữ liệu phải nằm ở nơi phát sinh (yêu cầu pháp lý theo quốc gia, chi phí truyền dữ liệu), hoặc khi mỗi đội tự vận hành cluster riêng nhưng cần một nơi tìm kiếm chung.

Cross-Cluster Replication

CCR sao chép liên tục một index từ cluster này (leader) sang cluster khác (follower). Cần license trả phí.

Ứng dụng ghi → Leader index (dc1) → Follower kéo thay đổi → Follower index (dc2, chỉ đọc)
  • Follower kéo (pull) thay đổi từ leader theo từng shard, dựa trên lịch sử thao tác (history retention leases)
  • Follower index chỉ đọc: không ghi trực tiếp được
  • Replication là active-passive theo từng index: một index chỉ có một leader
  • Follower tụt lại không quá xa sẽ tự bắt kịp. Tụt quá lâu (leader đã giải phóng lịch sử) thì phải tạo lại follower
# Trên cluster FOLLOWER (dc2), kết nối tới leader với alias "dc1"
PUT /orders-follower/_ccr/follow?wait_for_active_shards=1
{
  "remote_cluster": "dc1",
  "leader_index": "orders"
}

# Theo dõi độ trễ: so sánh leader_global_checkpoint và follower_global_checkpoint
GET /orders-follower/_ccr/stats
GET /_ccr/stats

# Tạm dừng / tiếp tục
POST /orders-follower/_ccr/pause_follow
POST /orders-follower/_ccr/resume_follow
Điều kiện của leader index Leader cần soft deletes (mặc định bật cho index tạo từ ES 7.0). Mapping và settings được sao chép tự động. Quyền cần thiết: user trên follower có manage_ccr và quyền manage_follow_index trên index follower; phía leader cần read_ccr (mô hình certificate) hoặc quyền replication trong cross-cluster API key.

Auto-follow

Với dữ liệu time-series, index mới sinh ra liên tục (rollover). Auto-follow pattern tự tạo follower cho mọi index mới khớp pattern trên leader.

PUT /_ccr/auto_follow/logs-from-dc1
{
  "remote_cluster": "dc1",
  "leader_index_patterns": [ "logs-*" ],
  "leader_index_exclusion_patterns": [ "logs-debug-*" ],
  "follow_index_pattern": "{{leader_index}}"
}

GET /_ccr/auto_follow/logs-from-dc1
GET /_ccr/stats?filter_path=auto_follow_stats
  • Auto-follow chỉ áp cho index tạo sau khi pattern tồn tại. Index đã có phải follow thủ công
  • Data stream được sao chép theo backing index: follower nhận đầy đủ data stream nhưng chỉ đọc
  • ILM chạy độc lập trên mỗi cluster. Follower index chưa được coi là "đã rollover" cho tới khi tách khỏi leader, nên cấu hình ILM của cluster follower cần tính đến điều này

Failover

Khi cluster leader sập lâu, chuyển follower thành index ghi được:

# Trên cluster follower (dc2)
POST /orders-follower/_ccr/pause_follow
POST /orders-follower/_close
POST /orders-follower/_ccr/unfollow
POST /orders-follower/_open
# orders-follower giờ là index thường, ghi được. Trỏ ứng dụng sang dc2 (alias, DNS, cấu hình client)
BướcLưu ý
Quyết định failoverThao tác unfollow không đảo ngược được. Chỉ làm khi xác định leader không quay lại kịp theo RTO
Dữ liệu mấtNhững thao tác ghi leader chưa kịp sao chép (RPO thường vài giây, tùy độ trễ CCR)
Chuyển hướng ghiỨng dụng phải ghi vào cluster mới. Chuẩn bị sẵn cơ chế (DNS, cấu hình, feature flag)
FailbackKhi dc1 hồi phục, index cũ trên dc1 đã lệch. Thường phải xóa nó và cho dc1 follow ngược lại từ dc2, sau đó chuyển vai trò về theo lịch bảo trì

Kiến Trúc Multi-datacenter

Kiến trúcMô tảƯuNhược
Active-passive (DR)dc1 nhận mọi ghi, dc2 follow toàn bộĐơn giản, RPO thấpdc2 chỉ để chờ, failover thủ công
Active-active theo dữ liệuMỗi DC là leader cho dữ liệu của mình và follow dữ liệu của DC kia. Ví dụ orders-hn-* ghi ở Hà Nội, orders-hcm-* ghi ở TP.HCM, cả hai được đọc ở cả hai nơiCả hai DC đều làm việc, đọc gần người dùngỨng dụng phải định tuyến ghi đúng DC, quản lý phức tạp hơn
Hub-and-spoke (CCS)Mỗi chi nhánh hoặc region giữ cluster riêng, một cluster trung tâm tìm kiếm qua CCSDữ liệu ở nguyên chỗ, tuân thủ quy định địa phươngSearch phụ thuộc mạng WAN
Aggregation (CCR)Các cluster nguồn được sao chép về một cluster trung tâm cho báo cáoSearch tập trung nhanh, không phụ thuộc WAN lúc truy vấnTốn lưu trữ và băng thông
Không có active-active ghi cùng một index Elasticsearch không hỗ trợ hai cluster cùng ghi vào một index rồi tự hòa giải xung đột. Mô hình "active-active" phải chia rõ dữ liệu nào do DC nào làm leader.

Bài Lab: Hai Cluster Với CCS và CCR

Lab cần hai cluster trên cùng máy. Để nhẹ, cluster thứ hai (dc2) chỉ có một node, cả hai dùng chung CA từ Bài 13 và mô hình bảo mật certificate-based. CCR cần license trả phí: lab dùng trial 30 ngày.

Bước 1: Certificate cho node của cluster thứ hai

cat > certs/instances-dc2.yml <<'EOF'
instances:
  - name: dc2-es01
    dns: [ dc2-es01, localhost ]
    ip:  [ 127.0.0.1 ]
EOF
docker run --rm -u 0 -v "$PWD/certs:/certs" docker.elastic.co/elasticsearch/elasticsearch:8.15.0 bash -c '
  bin/elasticsearch-certutil cert --silent --pem --ca-cert /certs/ca/ca.crt --ca-key /certs/ca/ca.key \
    --in /certs/instances-dc2.yml --out /certs/dc2.zip && unzip -o -q /certs/dc2.zip -d /certs && chown -R 1000:0 /certs'

Bước 2: Thêm cluster dc2 vào docker-compose.yml

  dc2-es01:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.15.0
    ports: [ "9201:9200" ]
    environment:
      - node.name=dc2-es01
      - cluster.name=es-dc2
      - discovery.type=single-node
      - ELASTIC_PASSWORD=${ELASTIC_PASSWORD}
      - xpack.security.enabled=true
      - xpack.security.http.ssl.enabled=true
      - xpack.security.http.ssl.key=certs/dc2-es01/dc2-es01.key
      - xpack.security.http.ssl.certificate=certs/dc2-es01/dc2-es01.crt
      - xpack.security.http.ssl.certificate_authorities=certs/ca/ca.crt
      - xpack.security.transport.ssl.enabled=true
      - xpack.security.transport.ssl.key=certs/dc2-es01/dc2-es01.key
      - xpack.security.transport.ssl.certificate=certs/dc2-es01/dc2-es01.crt
      - xpack.security.transport.ssl.certificate_authorities=certs/ca/ca.crt
      - xpack.security.transport.ssl.verification_mode=certificate
      - "ES_JAVA_OPTS=-Xms1g -Xmx1g"
    volumes:
      - dc2data01:/usr/share/elasticsearch/data
      - ./certs:/usr/share/elasticsearch/config/certs
# Thêm dc2data01: {} vào mục volumes
docker compose up -d dc2-es01
source .env
ES2=https://localhost:9201
curl $AUTH "$ES2/_cluster/health?filter_path=cluster_name,status"

curl $AUTH -X POST "$ES2/_license/start_trial?acknowledge=true"

# dc1 (cluster chính) thấy dc2, và ngược lại

Bước 4: Cross-Cluster Search

curl $AUTH -X POST "$ES2/logs-branch/_doc?refresh=true" -H 'Content-Type: application/json' \
  -d '{"@timestamp":"2026-10-28T09:00:00Z","branch":"hcm","message":"payment timeout"}'
curl $AUTH -X POST "$ES/logs-branch/_doc?refresh=true" -H 'Content-Type: application/json' \
  -d '{"@timestamp":"2026-10-28T09:01:00Z","branch":"hn","message":"payment timeout"}'

curl $AUTH "$ES/logs-branch,dc2:logs-branch/_search?pretty" -H 'Content-Type: application/json' -d '{
  "query": { "match": { "message": "payment" } }, "_source": ["branch"] }'
# 2 hits: một từ cluster local, một có _index "dc2:logs-branch"; _clusters.successful = 2

Bước 5: Cross-Cluster Replication

# Leader trên dc1
curl $AUTH -X PUT "$ES/orders-dc1" -H 'Content-Type: application/json' -d '{"settings":{"number_of_replicas":0}}'
curl $AUTH -X POST "$ES/orders-dc1/_doc/1?refresh=true" -H 'Content-Type: application/json' -d '{"total":100}'

# Follower trên dc2
curl $AUTH -X PUT "$ES2/orders-dc1-follower/_ccr/follow?wait_for_active_shards=1" \
  -H 'Content-Type: application/json' -d '{"remote_cluster":"dc1","leader_index":"orders-dc1"}'

# Ghi thêm trên leader, đọc ở follower
curl $AUTH -X POST "$ES/orders-dc1/_doc/2?refresh=true" -H 'Content-Type: application/json' -d '{"total":250}'
curl $AUTH "$ES2/orders-dc1-follower/_count"          # 2 (có thể cần vài giây)

# Follower không ghi được
curl $AUTH -X POST "$ES2/orders-dc1-follower/_doc" -H 'Content-Type: application/json' -d '{"total":1}'
# → lỗi: không ghi trực tiếp vào follower index

curl $AUTH "$ES2/orders-dc1-follower/_ccr/stats?pretty" | grep -E "leader_global_checkpoint|follower_global_checkpoint"

Bước 6: Mô phỏng failover

docker compose stop es01 es02 es03        # "dc1 sập" (cả es04, es05 nếu có)

curl $AUTH -X POST "$ES2/orders-dc1-follower/_ccr/pause_follow"
curl $AUTH -X POST "$ES2/orders-dc1-follower/_close"
curl $AUTH -X POST "$ES2/orders-dc1-follower/_ccr/unfollow"
curl $AUTH -X POST "$ES2/orders-dc1-follower/_open"
curl $AUTH -X POST "$ES2/orders-dc1-follower/_doc/3?refresh=true" -H 'Content-Type: application/json' -d '{"total":75}'
curl $AUTH "$ES2/orders-dc1-follower/_count"          # 3: dc2 đã nhận ghi

docker compose start es01 es02 es03
Xác minh thành công Một request CCS trả kết quả từ cả hai cluster. Document ghi vào leader xuất hiện trên follower sau vài giây, và follower từ chối ghi trực tiếp. Sau failover, index trên dc2 nhận ghi bình thường. Bạn đã tự tay đi qua toàn bộ vòng đời của một kế hoạch DR dùng CCR.

Câu Hỏi Ôn Tập

  1. Chế độ sniff và proxy khác nhau thế nào? Khi nào bắt buộc dùng proxy?
  2. So sánh mô hình bảo mật certificate-based và API key-based cho remote cluster.
  3. ccs_minimize_roundtrips ảnh hưởng thế nào tới hiệu năng khi các cluster cách xa nhau?
  4. Vì sao follower index chỉ đọc? Replication theo chiều nào (push hay pull)?
  5. Auto-follow giải quyết bài toán gì với dữ liệu rollover?
  6. Liệt kê các bước failover. Vì sao bước unfollow cần cân nhắc kỹ?
  7. Thiết kế kiến trúc cho ngân hàng có hai DC, mỗi DC phục vụ một miền, cả hai cần đọc dữ liệu của nhau.

Checklist Kiến Thức

  • ☐ Khai báo remote cluster ở chế độ sniff và proxy
  • ☐ Hiểu hai mô hình bảo mật cho kết nối giữa cluster
  • ☐ Viết query CCS và đọc mục _clusters trong response
  • ☐ Tạo follower index và theo dõi độ trễ CCR
  • ☐ Cấu hình auto-follow pattern
  • ☐ Thực hiện failover và hiểu yêu cầu của failback
  • ☐ Chọn kiến trúc multi-datacenter phù hợp yêu cầu

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Kéo dài một cluster qua hai DC xa nhau: dùng hai cluster và CCR/CCS thay vì một cluster trải rộng.
  • Coi CCR là backup: xóa nhầm document trên leader được sao chép sang follower. Vẫn cần snapshot.
  • Không theo dõi độ trễ CCR: follower tụt quá xa và phải tạo lại từ đầu.
  • Quên index cũ khi bật auto-follow: chỉ index mới được sao chép.
  • Failover chưa diễn tập: ứng dụng không biết chuyển hướng ghi, RTO thực tế dài gấp nhiều lần dự kiến.
  • Chặn cổng 9300/9443 giữa hai DC: CCS và CCR đi qua transport hoặc cổng remote cluster, không qua cổng HTTP 9200.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Mỗi DC hoặc region một cluster, kết nối bằng CCS cho đọc chung và CCR cho DR
  • Dùng API key-based security khi remote thuộc đội hoặc tổ chức khác
  • Auto-follow cho dữ liệu time-series, follow thủ công cho index đã tồn tại
  • Cảnh báo khi độ trễ CCR vượt RPO cho phép (Bài 18)
  • Viết runbook failover và failback, diễn tập định kỳ cùng đội ứng dụng
  • Giữ các cluster trong phạm vi version tương thích, nâng cấp theo kế hoạch chung
