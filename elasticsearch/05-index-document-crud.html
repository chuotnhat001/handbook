Index & Document CRUD

Index, Get, Update, Delete, Bulk, Reindex — thao tác document và tối ưu throughput ghi

Nguồn: Elastic — Document APIs, Elastic — Bulk API

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Thực hiện CRUD document bằng Index/Get/Update/Delete API. Dùng Bulk API để ghi hàng loạt hiệu quả. Copy/transform dữ liệu bằng Reindex API. Xử lý cập nhật/xóa theo query. Hiểu versioning và optimistic concurrency control để tránh ghi đè mất dữ liệu.

Kiến Thức Tiên Quyết

  • Bài 03: Kiến Trúc ES — Routing, primary/replica, write path
  • Bài 02: Lucene — Update = delete + insert; refresh ≠ flush
  • REST/JSON — HTTP methods, request body JSON

Index API — Tạo / Ghi Đè Document

"Index" (động từ) = đưa document vào Elasticsearch. Có hai cách chỉ định ID:

# 1. ID tường minh (PUT) — ghi đè nếu đã tồn tại
PUT /products/_doc/1
{ "name": "Laptop", "price": 1200, "in_stock": true }

# 2. ID tự sinh (POST) — luôn tạo document mới
POST /products/_doc
{ "name": "Mouse", "price": 25 }

op_type=create — chỉ tạo, không ghi đè

# Lỗi 409 nếu _id đã tồn tại (dùng khi cần đảm bảo không ghi đè)
PUT /products/_create/1
{ "name": "Laptop", "price": 1200 }

# Tương đương:
PUT /products/_doc/1?op_type=create
{ "name": "Laptop", "price": 1200 }

Response trả về _version, _seq_no, _primary_term, và result (created hoặc updated).

Get API — Đọc Document

# Lấy toàn bộ document
GET /products/_doc/1

# Chỉ kiểm tra tồn tại (HEAD → 200/404)
HEAD /products/_doc/1

# _source filtering — chỉ lấy field cần
GET /products/_doc/1?_source=name,price
GET /products/_doc/1?_source_excludes=description
Get là real-time Khác với search (near real-time, chờ refresh), Get API đọc được document ngay sau khi index — nó kiểm tra translog trước khi segment được refresh.

Update API — Cập Nhật Một Phần

# Partial update — chỉ gửi field thay đổi (merge vào document hiện có)
POST /products/_update/1
{ "doc": { "price": 1100 } }

# Scripted update — tăng giảm, thao tác động
POST /products/_update/1
{
  "script": {
    "source": "ctx._source.price -= params.discount",
    "params": { "discount": 100 }
  }
}

# Upsert — update nếu có, insert nếu chưa
POST /products/_update/1
{
  "doc": { "price": 999 },
  "doc_as_upsert": true
}
Update thực chất là gì? Ở Lucene level (Bài 02), update = lấy document cũ → merge → xóa bản cũ (mark deleted) → index bản mới. Nó không "sửa tại chỗ". Vì vậy update thường xuyên trên cùng document tạo nhiều deleted docs chờ merge.

Delete API

# Xóa theo ID
DELETE /products/_doc/1
# Response result: "deleted" (hoặc "not_found")

Bulk API — Ghi Hàng Loạt

Gửi từng request riêng cho hàng nghìn document là cực chậm (mỗi request một round-trip HTTP). Bulk API gộp nhiều thao tác vào một request.

Định dạng NDJSON

Bulk dùng newline-delimited JSON: mỗi thao tác gồm 2 dòng (action metadata + body), riêng delete chỉ 1 dòng. Mỗi dòng kết thúc bằng newline, kể cả dòng cuối.

POST /_bulk
{ "index":  { "_index": "products", "_id": "1" } }
{ "name": "Laptop", "price": 1200 }
{ "create": { "_index": "products", "_id": "2" } }
{ "name": "Mouse", "price": 25 }
{ "update": { "_index": "products", "_id": "1" } }
{ "doc": { "price": 1100 } }
{ "delete": { "_index": "products", "_id": "3" } }
Tư duy cốt lõi Bulk là chìa khóa của indexing throughput. Mỗi bulk request độc lập — một action lỗi không làm hỏng các action khác (kiểm tra errors: true trong response và duyệt từng item).

Kích thước batch

  • Bắt đầu từ 1.000–5.000 document hoặc 5–15 MB mỗi batch, rồi tinh chỉnh theo benchmark
  • Batch quá lớn → áp lực heap, dễ bị circuit breaker. Quá nhỏ → mất lợi ích gộp request
  • Dùng nhiều thread/client song song để bão hòa cluster

Reindex API — Copy / Transform Index

Reindex copy document từ index này sang index khác — dùng khi đổi mapping, đổi số shard, hoặc transform dữ liệu.

# Cơ bản
POST /_reindex
{
  "source": { "index": "products-v1" },
  "dest":   { "index": "products-v2" }
}

# Có filter + transform bằng script
POST /_reindex
{
  "source": {
    "index": "products-v1",
    "query": { "range": { "price": { "gte": 100 } } }
  },
  "dest": { "index": "products-v2" },
  "script": { "source": "ctx._source.price *= 1.1" }
}
# Remote reindex — từ cluster khác
POST /_reindex
{
  "source": {
    "remote": { "host": "https://old-cluster:9200", "username": "elastic", "password": "***" },
    "index": "products"
  },
  "dest": { "index": "products" }
}
Chạy nền với task Reindex lớn nên chạy async: thêm ?wait_for_completion=false → trả về task id, theo dõi qua GET /_tasks/<task_id>.

Update / Delete by Query

# Cập nhật hàng loạt theo điều kiện
POST /products/_update_by_query
{
  "query": { "term": { "in_stock": false } },
  "script": { "source": "ctx._source.status = 'discontinued'" }
}

# Xóa theo điều kiện
POST /products/_delete_by_query
{ "query": { "range": { "price": { "lt": 10 } } } }

Versioning & Optimistic Concurrency Control

Khi nhiều client cùng cập nhật một document, có nguy cơ lost update (ghi đè mất thay đổi của nhau). ES dùng optimistic concurrency control (OCC): mỗi document mang _seq_no và _primary_term, client gửi kèm giá trị mình đã đọc; nếu không khớp → lỗi 409.

# 1. Đọc document, ghi nhớ _seq_no và _primary_term
GET /products/_doc/1
# → "_seq_no": 5, "_primary_term": 1

# 2. Ghi có điều kiện — chỉ thành công nếu document chưa đổi
PUT /products/_doc/1?if_seq_no=5&if_primary_term=1
{ "name": "Laptop", "price": 1050 }
# Nếu ai đó đã sửa trước → 409 version_conflict_engine_exception
Vì sao không dùng _version thủ công nữa? ES ≥ 6.7 khuyến nghị if_seq_no + if_primary_term thay cho external version cũ — chúng phản ánh đúng thứ tự thao tác trên primary shard, an toàn hơn trong môi trường phân tán.

Refresh Parameter

Nhắc lại từ Bài 02: document chỉ searchable sau refresh (mặc định 1s). Tham số refresh kiểm soát hành vi này khi ghi:

Giá trịÝ nghĩa
false (mặc định)Không ép refresh — chờ chu kỳ refresh thường. Throughput cao nhất.
wait_forChờ đến refresh tiếp theo rồi mới trả response (không ép refresh ngay)
trueÉp refresh ngay lập tức. Tốn kém — tránh dùng trong vòng lặp ghi nóng.
PUT /products/_doc/1?refresh=wait_for
{ "name": "Laptop", "price": 1200 }

Bài Lab: Import 10k Documents & Benchmark Bulk vs Single

Mục tiêu

So sánh thời gian index 10.000 document theo 2 cách: từng request vs bulk.

Bước 1: Tạo index

PUT /lab-bulk
{ "settings": { "number_of_shards": 1, "number_of_replicas": 0, "refresh_interval": "-1" } }
# Tắt refresh trong lúc bulk load → nhanh hơn

Bước 2: Script bulk (bash + curl)

# Dùng cluster lab Bài 04 (security tắt, http).
# Cluster có security: thêm -k -u elastic và đổi sang https://
# Sinh file NDJSON 10k docs
python3 - <<'PY' > bulk.ndjson
for i in range(10000):
    print('{"index":{"_id":"%d"}}' % i)
    print('{"n":%d,"name":"item-%d","price":%d}' % (i, i, i % 500))
PY

# Load một phát bằng bulk
time curl -s -H 'Content-Type: application/x-ndjson' \
  -XPOST 'http://localhost:9200/lab-bulk/_bulk?refresh=wait_for' \
  --data-binary @bulk.ndjson > /dev/null

Bước 3: So sánh với single request

# Index 1000 docs từng cái một (chỉ để đo — sẽ chậm rõ rệt)
time for i in $(seq 1 1000); do
  curl -s -XPOST 'http://localhost:9200/lab-single/_doc' \
    -H 'Content-Type: application/json' -d "{\"n\":$i}" > /dev/null
done

Bước 4: Bật lại refresh & kiểm tra

PUT /lab-bulk/_settings
{ "refresh_interval": "1s" }
POST /lab-bulk/_refresh
GET /lab-bulk/_count
# Mong đợi: count = 10000
Xác minh thành công Bulk load 10k docs nhanh hơn single request hàng chục đến hàng trăm lần. Bạn cũng thấy refresh_interval: -1 trong lúc load giúp tăng throughput — một kỹ thuật chuẩn cho initial bulk load.

Câu Hỏi Ôn Tập

  1. Khác biệt giữa PUT /_doc/1 và POST /_doc? Khi nào dùng op_type=create?
  2. Vì sao Get API là real-time còn search thì near real-time?
  3. Ở Lucene level, update một document thực chất gồm những bước nào?
  4. Giải thích định dạng NDJSON của Bulk API. Vì sao bulk nhanh hơn single request?
  5. Khi nào dùng Reindex API? Làm sao chạy reindex lớn mà không block?
  6. Optimistic concurrency control hoạt động thế nào với if_seq_no/if_primary_term?
  7. So sánh refresh=true, wait_for, false. Vì sao không nên refresh=true trong vòng lặp ghi?

Checklist Kiến Thức

  • ☐ Thực hiện Index/Get/Update/Delete thành thạo
  • ☐ Phân biệt auto-id vs explicit id, op_type=create
  • ☐ Dùng partial update, scripted update, upsert
  • ☐ Viết bulk request đúng định dạng NDJSON
  • ☐ Reindex với query filter + script, chạy async
  • ☐ Dùng update/delete by query
  • ☐ Áp dụng OCC với if_seq_no + if_primary_term
  • ☐ Hiểu tham số refresh và ảnh hưởng performance

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Index từng document trong vòng lặp — Dùng Bulk API. Single request cho khối lượng lớn là chống chỉ định.
  • Quên newline cuối file NDJSON — Bulk request lỗi parse. Mỗi dòng (kể cả dòng cuối) phải kết thúc bằng \n.
  • refresh=true sau mỗi ghi — Tạo vô số segment nhỏ, giết performance. Để ES tự refresh theo chu kỳ.
  • Không xử lý version conflict — Bỏ qua 409 → mất cập nhật. Phải retry với giá trị _seq_no mới.
  • Update liên tục cùng document — Sinh nhiều deleted docs, tốn merge. Cân nhắc gom thay đổi hoặc thiết kế lại.
  • Không tắt refresh khi bulk load khởi tạo — Đặt refresh_interval: -1 trong lúc load lớn, bật lại sau.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Luôn dùng Bulk API cho ghi khối lượng lớn; tinh chỉnh batch size bằng benchmark
  • Khởi tạo load lớn: refresh_interval: -1 + number_of_replicas: 0, bật lại sau khi xong
  • Dùng OCC (if_seq_no/if_primary_term) cho mọi update có cạnh tranh; retry khi 409
  • Reindex lớn chạy async với wait_for_completion=false, theo dõi qua Tasks API
  • Kiểm tra errors trong bulk response và xử lý từng item lỗi riêng
  • Prefer upsert cho logic "tạo hoặc cập nhật" thay vì get-rồi-ghi hai bước
