Cluster Management & Scaling

Thêm/bớt node, rolling restart, cluster health, allocation awareness — vận hành cluster không downtime

Nguồn: Elastic — Add and Remove Nodes, Elastic — Full and Rolling Restart

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Đọc đúng cluster health và chẩn đoán shard chưa được cấp phát bằng allocation explain. Thêm và gỡ node (kể cả master-eligible node) mà không mất dữ liệu. Thực hiện rolling restart để nâng cấp hoặc đổi cấu hình không downtime. Cấu hình allocation awareness để cluster chịu được mất cả một zone.

Cluster Health: Green / Yellow / Red

GET /_cluster/health
GET /_cluster/health?level=indices      # chi tiết từng index
GET /_cat/indices?v&health=yellow        # chỉ index đang yellow
GET /_cat/shards?v&h=index,shard,prirep,state,unassigned.reason
Trạng tháiÝ nghĩaHành động
greenMọi primary và replica đã cấp phátBình thường
yellowPrimary đủ, thiếu replica. Dữ liệu vẫn đọc/ghi được nhưng giảm khả năng chịu lỗiTìm lý do replica không cấp phát được
redCó primary chưa cấp phát. Một phần dữ liệu không truy cập được, ghi vào shard đó thất bạiXử lý ngay
Yellow trong lúc bảo trì là bình thường Khi restart một node, các replica trên node đó tạm thời unassigned nên cluster chuyển yellow. Điều cần theo dõi là cluster có quay về green sau khi node quay lại hay không.

Allocation Explain

Đây là công cụ quan trọng nhất khi cluster không green. API trả lời câu hỏi: "Vì sao shard này chưa được cấp phát, hoặc vì sao nó nằm ở node này?"

# Không truyền body → giải thích shard unassigned đầu tiên tìm thấy
GET /_cluster/allocation/explain

# Hỏi về một shard cụ thể
GET /_cluster/allocation/explain
{ "index": "orders", "shard": 0, "primary": false }

Trong response, xem unassigned_info.reason và danh sách node_allocation_decisions. Mỗi node có một loạt deciders với kết quả NO kèm lý do. Các lý do hay gặp:

DeciderÝ nghĩa
same_shardKhông đặt replica cùng node với primary (thường gặp ở cluster 1 node)
disk_thresholdNode vượt disk watermark (Bài 11)
filterAllocation filtering loại trừ node này
awarenessVi phạm quy tắc phân bổ theo zone
max_retryCấp phát đã thất bại quá số lần cho phép (mặc định 5)
# Sau khi sửa nguyên nhân gốc, thử cấp phát lại các shard đã hết lượt retry
POST /_cluster/reroute?retry_failed=true

Thêm Node

Node mới chỉ cần cùng cluster.name và trỏ discovery.seed_hosts tới các node hiện có. Master tự động rebalance shard sang node mới.

# elasticsearch.yml của node mới
cluster.name: my-production-cluster
node.name: node-4
node.roles: [ data ]
discovery.seed_hosts: ["10.0.0.1", "10.0.0.2", "10.0.0.3"]
# KHÔNG đặt cluster.initial_master_nodes cho node join cluster đã có
initial_master_nodes trên node mới Đặt cluster.initial_master_nodes trên node join cluster có sẵn có thể khiến nó tự bootstrap một cluster riêng, tách khỏi cluster chính. Tham số này chỉ dùng một lần khi khởi tạo cluster lần đầu.

Kiểm soát tốc độ di chuyển shard để không làm nghẽn cluster đang phục vụ:

PUT /_cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.node_concurrent_recoveries": 2,
    "indices.recovery.max_bytes_per_sec": "100mb"
  }
}

Gỡ Node

Gỡ data node

Không tắt node đột ngột. Trước hết, di chuyển hết shard ra khỏi node bằng allocation filtering:

# 1. Đẩy shard ra khỏi node-4
PUT /_cluster/settings
{ "persistent": { "cluster.routing.allocation.exclude._name": "node-4" } }

# 2. Chờ đến khi node-4 không còn shard nào
GET /_cat/allocation?v
GET /_cat/shards?v&h=index,shard,prirep,state,node | grep node-4

# 3. Dừng node-4, rồi xóa setting exclude
PUT /_cluster/settings
{ "persistent": { "cluster.routing.allocation.exclude._name": null } }

Gỡ master-eligible node

Với master-eligible node, cần đưa node ra khỏi voting configuration trước để quorum không bị ảnh hưởng:

# 1. Loại node khỏi voting configuration
POST /_cluster/voting_config_exclusions?node_names=node-3

# 2. Dừng node-3

# 3. Sau khi node-3 đã rời cluster hẳn, xóa danh sách exclusion
DELETE /_cluster/voting_config_exclusions
Gỡ từng node một Đừng tắt cùng lúc một nửa số master-eligible node. ES tự điều chỉnh voting configuration khi node rời đi từ từ, nhưng nếu mất đa số cùng lúc thì cluster mất quorum và không bầu được master.

Rolling Restart

Rolling restart nghĩa là khởi động lại từng node một trong khi cluster vẫn phục vụ. Dùng khi nâng cấp minor version, đổi cấu hình tĩnh, hoặc bảo trì OS.

Tắt cấp phát replica → Flush → Restart 1 node → Chờ join → Bật lại cấp phát → Chờ green 
# 1. Chỉ cho phép cấp phát primary, tránh ES copy replica khi node tạm vắng
PUT /_cluster/settings
{ "persistent": { "cluster.routing.allocation.enable": "primaries" } }

# 2. Flush để giảm lượng dữ liệu cần recovery từ translog
POST /_flush

# 3. Dừng node, nâng cấp hoặc đổi cấu hình, khởi động lại

# 4. Kiểm tra node đã join
GET /_cat/nodes?v

# 5. Bật lại cấp phát đầy đủ
PUT /_cluster/settings
{ "persistent": { "cluster.routing.allocation.enable": null } }

# 6. Chờ green rồi mới chuyển sang node tiếp theo
GET /_cluster/health?wait_for_status=green&timeout=10m
Tư duy cốt lõi Mặc định, khi một node rời cluster, ES chờ index.unassigned.node_left.delayed_timeout (1 phút) rồi mới copy replica sang node khác. Bước 1 khiến ES không di chuyển dữ liệu dù node vắng lâu hơn thế. Khi node quay lại, shard cũ trên disk được dùng lại, chỉ cần đồng bộ phần thay đổi.

Thứ tự khuyến nghị khi nâng cấp version: restart các node không phải master trước, master-eligible node sau cùng. Node đã nâng cấp có thể nhận shard từ node cũ, nhưng không theo chiều ngược lại.

Allocation Awareness

Nếu primary và replica của một shard cùng nằm trong một rack hoặc availability zone, mất zone đó là mất cả hai bản. Allocation awareness dạy ES biết vị trí vật lý của node để tách các bản sao ra.

# elasticsearch.yml trên từng node: gắn attribute vị trí
node.attr.zone: zone-a        # node ở zone-b đặt zone-b

# Cấu hình cluster (động)
PUT /_cluster/settings
{ "persistent": { "cluster.routing.allocation.awareness.attributes": "zone" } }

Với 2 zone và number_of_replicas: 1, ES đặt primary ở một zone và replica ở zone kia.

Forced Awareness

Awareness thường có một hệ quả bất ngờ: khi zone-b sập, ES cố dồn toàn bộ replica sang zone-a. Zone-a có thể không đủ disk/RAM gánh gấp đôi dữ liệu và bị quá tải theo. Forced awareness khai báo trước danh sách zone, nên ES không cấp phát replica của zone đã mất vào zone còn lại:

PUT /_cluster/settings
{
  "persistent": {
    "cluster.routing.allocation.awareness.attributes": "zone",
    "cluster.routing.allocation.awareness.force.zone.values": "zone-a,zone-b"
  }
}
# Mất zone-b → cluster yellow (thiếu replica) nhưng zone-a không bị quá tải
Master node cũng cần trải zone Với 3 master-eligible node, đặt mỗi node ở một zone khác nhau. Nếu đặt 2 master ở zone-a, mất zone-a đồng nghĩa mất quorum và cả cluster dừng hoạt động.

Bài Lab: Scale Cluster Từ 3 Lên 5 Node, Không Downtime

Chuẩn bị

Dùng cluster lab 3 node từ Bài 04 (security tắt, chỉ dùng cục bộ). Tạo index và chạy vòng lặp ghi liên tục để chứng minh không downtime:

curl -X PUT "http://localhost:9200/lab-scale" -H 'Content-Type: application/json' \
  -d '{"settings":{"number_of_shards":6,"number_of_replicas":1}}'

# Terminal riêng: ghi 1 document mỗi giây, in ra lỗi nếu có
while true; do
  curl -s -o /dev/null -w "%{http_code}\n" -X POST "http://localhost:9200/lab-scale/_doc" \
    -H 'Content-Type: application/json' -d "{\"ts\":\"$(date -u +%FT%TZ)\"}"
  sleep 1
done

Bước 1: Thêm es04 và es05 vào docker-compose.yml

  es04:
    image: docker.elastic.co/elasticsearch/elasticsearch:8.15.0
    environment:
      - node.name=es04
      - cluster.name=es-docker-cluster
      - node.roles=data
      - discovery.seed_hosts=es01,es02,es03
      - xpack.security.enabled=false
      - "ES_JAVA_OPTS=-Xms2g -Xmx2g"
    volumes: [ "data04:/usr/share/elasticsearch/data" ]
  # es05: tương tự, đổi node.name=es05 và volume data05
# Thêm data04, data05 vào mục volumes. Không đặt cluster.initial_master_nodes.

Bước 2: Khởi động node mới và quan sát rebalance

docker compose up -d es04 es05
curl "http://localhost:9200/_cat/nodes?v&h=name,node.role,master"
# Lặp lại vài lần để thấy shard chuyển sang es04, es05
curl "http://localhost:9200/_cat/shards/lab-scale?v&h=shard,prirep,state,node"
curl "http://localhost:9200/_cat/recovery?v&active_only=true"

Bước 3: Rolling restart es02

curl -X PUT "http://localhost:9200/_cluster/settings" -H 'Content-Type: application/json' \
  -d '{"persistent":{"cluster.routing.allocation.enable":"primaries"}}'
curl -X POST "http://localhost:9200/_flush"
docker compose restart es02
curl -X PUT "http://localhost:9200/_cluster/settings" -H 'Content-Type: application/json' \
  -d '{"persistent":{"cluster.routing.allocation.enable":null}}'
curl "http://localhost:9200/_cluster/health?wait_for_status=green&timeout=5m&pretty"
Xác minh thành công Cluster có 5 node, health green, shard của lab-scale trải đều trên 5 node. Vòng lặp ghi chỉ in 201 trong suốt quá trình. Nếu có lỗi, đó thường là do request rơi đúng lúc es01 (node nhận request qua cổng 9200) restart. Production dùng load balancer hoặc client trỏ tới nhiều node để tránh trường hợp này.

Checklist Kiến Thức

  • ☐ Đọc cluster health và _cat/shards để tìm shard có vấn đề
  • ☐ Dùng _cluster/allocation/explain và reroute?retry_failed
  • ☐ Thêm node mới đúng cấu hình discovery
  • ☐ Gỡ data node bằng allocation exclude
  • ☐ Gỡ master-eligible node bằng voting config exclusions
  • ☐ Thực hiện rolling restart đủ 6 bước
  • ☐ Cấu hình allocation awareness và forced awareness theo zone

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Tắt node khi chưa chuyển shard đi: nếu replica còn thiếu, mất node có thể làm cluster red.
  • Quên bật lại allocation sau rolling restart: cluster kẹt ở yellow vì replica không bao giờ được cấp phát lại.
  • Restart node tiếp theo khi cluster chưa green: có thể mất cả primary lẫn replica của cùng một shard.
  • Quên xóa allocation exclude: node mới cùng tên về sau sẽ không nhận được shard.
  • Awareness không forced: mất một zone kéo theo zone còn lại quá tải disk.
  • Dồn master vào một zone: mất zone đó là mất quorum toàn cluster.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Viết runbook rolling restart và luôn chờ green giữa các node
  • Dùng persistent cho cấu hình cluster cần giữ qua restart, tránh transient (đã bị đánh dấu deprecated)
  • Giới hạn tốc độ recovery khi cluster đang phục vụ traffic cao
  • Bật forced awareness khi chạy multi-zone, trải 3 master qua 3 zone
  • Client kết nối tới nhiều node hoặc qua load balancer, không trỏ cứng vào một node
