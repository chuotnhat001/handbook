Aggregations & Analytics

Metric, bucket, pipeline, composite — biến Elasticsearch thành engine phân tích dữ liệu thời gian thực

Nguồn: Elastic — Aggregations, Elastic — Composite Aggregation

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Hiểu aggregation là gì và chạy trên dữ liệu nào. Dùng metric aggregation (avg, sum, cardinality, percentiles) và bucket aggregation (terms, histogram, date_histogram, range). Lồng sub-aggregation, dùng pipeline aggregation, phân trang bucket bằng composite. Hiểu giới hạn độ chính xác của terms và cardinality, cùng các mẹo tối ưu performance.

  • Bài 06: Mapping — keyword và doc_values cho aggregate
  • Bài 08: Search DSL — Query/filter giới hạn tập dữ liệu được aggregate

Aggregation Là Gì

Aggregation tính toán thống kê trên tập document khớp với query, tương tự GROUP BY + hàm tổng hợp trong SQL. Aggregation đọc dữ liệu từ doc_values (column store), không phải inverted index.

GET /orders/_search
{
  "size": 0,
  "query": { "range": { "created_at": { "gte": "now-30d/d" } } },
  "aggs": {
    "revenue": { "sum": { "field": "total" } }
  }
}
# size: 0 → không trả hits, chỉ trả kết quả aggregation
LoạiTác dụngTương đương SQL
MetricTính một giá trị từ các documentSUM, AVG, COUNT(DISTINCT)
BucketChia document thành các nhómGROUP BY
PipelineTính toán trên kết quả của aggregation khácWindow function, subquery
Tư duy cốt lõi Query quyết định dữ liệu nào được tính, aggregation quyết định tính gì. Cùng một request vừa trả kết quả tìm kiếm vừa trả facet, nhờ vậy search UI có bộ lọc kèm số lượng chỉ với một lần gọi.

Metric Aggregations

GET /orders/_search
{
  "size": 0,
  "aggs": {
    "avg_total":     { "avg": { "field": "total" } },
    "max_total":     { "max": { "field": "total" } },
    "total_stats":   { "stats": { "field": "total" } },
    "unique_users":  { "cardinality": { "field": "user_id" } },
    "latency_pct":   { "percentiles": { "field": "latency_ms", "percents": [50, 95, 99] } },
    "order_count":   { "value_count": { "field": "order_id" } }
  }
}
AggregationTrả về
avg, sum, min, maxMột giá trị
stats / extended_statscount, min, max, avg, sum (+ variance, std_deviation)
cardinalitySố giá trị khác nhau (ước lượng, HyperLogLog++)
percentilesPhân vị p50/p95/p99 (ước lượng, TDigest)
top_hitsCác document tiêu biểu trong mỗi bucket

Bucket Aggregations

terms — nhóm theo giá trị

"aggs": {
  "by_category": {
    "terms": { "field": "category", "size": 10, "order": { "_count": "desc" } }
  }
}
# Kết quả: buckets [{ "key": "laptop", "doc_count": 1520 }, ...]

histogram & date_histogram

"aggs": {
  "price_ranges": { "histogram": { "field": "price", "interval": 100 } },
  "orders_per_day": {
    "date_histogram": {
      "field": "created_at",
      "calendar_interval": "1d",
      "time_zone": "Asia/Ho_Chi_Minh",
      "min_doc_count": 0
    }
  }
}
calendar_interval vs fixed_interval calendar_interval theo lịch (1d, 1w, 1M, có xét độ dài tháng và giờ DST). fixed_interval theo khoảng cố định (30m, 12h). Luôn đặt time_zone, nếu không bucket "ngày" sẽ cắt theo UTC và lệch 7 tiếng với giờ Việt Nam.

range & filters

"aggs": {
  "price_bands": {
    "range": { "field": "price", "ranges": [
      { "key": "rẻ", "to": 200 },
      { "key": "trung bình", "from": 200, "to": 1000 },
      { "key": "cao cấp", "from": 1000 }
    ]}
  },
  "status_groups": {
    "filters": { "filters": {
      "errors":  { "range": { "status_code": { "gte": 500 } } },
      "success": { "range": { "status_code": { "lt": 400 } } }
    }}
  }
}

Sub-aggregations

Bucket có thể chứa aggregation con, tính riêng cho từng bucket:

GET /orders/_search
{
  "size": 0,
  "aggs": {
    "by_category": {
      "terms": { "field": "category", "size": 5 },
      "aggs": {
        "revenue":   { "sum": { "field": "total" } },
        "avg_order": { "avg": { "field": "total" } },
        "per_month": {
          "date_histogram": { "field": "created_at", "calendar_interval": "1M" },
          "aggs": { "revenue": { "sum": { "field": "total" } } }
        }
      }
    }
  }
}
# Doanh thu theo danh mục, và theo tháng trong từng danh mục

Sắp xếp bucket theo metric con:

"terms": { "field": "category", "size": 5, "order": { "revenue": "desc" } }

Pipeline Aggregations

Pipeline aggregation lấy đầu vào là kết quả của aggregation khác qua buckets_path.

GET /orders/_search
{
  "size": 0,
  "aggs": {
    "per_day": {
      "date_histogram": { "field": "created_at", "calendar_interval": "1d" },
      "aggs": {
        "revenue": { "sum": { "field": "total" } },
        "revenue_7d_avg": {
          "moving_fn": { "buckets_path": "revenue", "window": 7, "script": "MovingFunctions.unweightedAvg(values)" }
        },
        "revenue_change": { "derivative": { "buckets_path": "revenue" } },
        "revenue_running": { "cumulative_sum": { "buckets_path": "revenue" } }
      }
    },
    "best_day": { "max_bucket": { "buckets_path": "per_day>revenue" } }
  }
}
PipelineTác dụng
derivativeChênh lệch so với bucket trước
cumulative_sumTổng lũy kế
moving_fnTrung bình trượt hoặc hàm cửa sổ
max_bucket / avg_bucketTìm hoặc tính trên toàn bộ bucket anh em
bucket_selectorLọc bucket theo điều kiện (như SQL HAVING)
bucket_sortSắp xếp và cắt danh sách bucket
# HAVING revenue > 10000
"high_revenue_only": {
  "bucket_selector": {
    "buckets_path": { "rev": "revenue" },
    "script": "params.rev > 10000"
  }
}

Composite Aggregation & Phân Trang Bucket

terms với size lớn tốn bộ nhớ và không phân trang được. Khi cần duyệt toàn bộ tổ hợp bucket (export, đồng bộ sang hệ thống khác), dùng composite:

GET /orders/_search
{
  "size": 0,
  "aggs": {
    "user_daily": {
      "composite": {
        "size": 1000,
        "sources": [
          { "user": { "terms": { "field": "user_id" } } },
          { "day":  { "date_histogram": { "field": "created_at", "calendar_interval": "1d" } } }
        ]
      },
      "aggs": { "spent": { "sum": { "field": "total" } } }
    }
  }
}
# Response có "after_key" → truyền vào "after" để lấy trang tiếp:
# "composite": { "size": 1000, "sources": [...], "after": { "user": "u_981", "day": 1761523200000 } }

Độ Chính Xác

terms trên nhiều shard

Mỗi shard trả về top shard_size term của riêng nó, coordinating node gộp lại. Một term phổ biến toàn cục nhưng không lọt top ở một shard nào đó có thể bị đếm thiếu.

  • Response có doc_count_error_upper_bound và sum_other_doc_count để đánh giá sai số
  • Tăng shard_size (mặc định khoảng size × 1.5 + 10) để chính xác hơn, đổi lại tốn tài nguyên
  • Index một shard thì kết quả terms chính xác tuyệt đối

cardinality & percentiles là ước lượng

"unique_users": {
  "cardinality": { "field": "user_id", "precision_threshold": 3000 }
}
# Dưới ngưỡng precision_threshold: gần như chính xác. Tối đa 40000.
Đừng dùng cho số liệu kế toán Cardinality (HyperLogLog++) và percentiles (TDigest) đánh đổi một ít độ chính xác lấy bộ nhớ cố định và tốc độ. Phù hợp cho dashboard và monitoring, không phù hợp cho báo cáo tài chính cần số chính xác tuyệt đối.

Performance

  • Luôn size: 0 khi chỉ cần aggregation, để bỏ qua fetch phase
  • Thu hẹp dữ liệu bằng filter trước khi aggregate (khoảng thời gian, tenant)
  • Aggregate trên keyword/numeric, không bật fielddata cho field text
  • Tránh terms với cardinality cực cao kèm size lớn, dùng composite
  • Request cache: request size: 0 được cache theo shard, hiệu quả cho dashboard trên index ít thay đổi
  • Giới hạn số bucket: search.max_buckets chặn aggregation tạo quá nhiều bucket (bảo vệ heap)
# Lấy mẫu để aggregate nhanh trên dữ liệu rất lớn
"aggs": {
  "sample": {
    "random_sampler": { "probability": 0.1 },
    "aggs": { "avg_latency": { "avg": { "field": "latency_ms" } } }
  }
}

Bước 2: Một request cho cả dashboard

GET /access-logs/_search
{
  "size": 0,
  "query": { "range": { "@timestamp": { "gte": "2026-10-27T00:00:00+07:00", "lt": "2026-10-28T00:00:00+07:00" } } },
  "aggs": {
    "requests_per_hour": {
      "date_histogram": { "field": "@timestamp", "fixed_interval": "1h", "time_zone": "Asia/Ho_Chi_Minh" },
      "aggs": {
        "p95_latency": { "percentiles": { "field": "latency_ms", "percents": [95] } },
        "errors": { "filter": { "range": { "status_code": { "gte": 500 } } } }
      }
    },
    "top_paths": {
      "terms": { "field": "path", "size": 5 },
      "aggs": { "avg_latency": { "avg": { "field": "latency_ms" } } }
    },
    "status_classes": {
      "range": { "field": "status_code", "ranges": [
        { "key": "2xx", "from": 200, "to": 300 },
        { "key": "4xx", "from": 400, "to": 500 },
        { "key": "5xx", "from": 500, "to": 600 }
      ]}
    },
    "unique_clients": { "cardinality": { "field": "client_ip" } },
    "slowest_request": {
      "top_hits": { "size": 1, "sort": [{ "latency_ms": "desc" }], "_source": ["path", "latency_ms"] }
    }
  }
}

Bước 3: Đọc kết quả

  • requests_per_hour: biểu đồ traffic theo giờ, kèm p95 latency và số lỗi 5xx mỗi giờ
  • top_paths: endpoint được gọi nhiều nhất và độ trễ trung bình
  • status_classes: tỷ lệ 2xx/4xx/5xx
  • unique_clients: số IP khác nhau (ước lượng)
  • slowest_request: request chậm nhất để điều tra
Xác minh thành công Một request trả đủ dữ liệu cho 5 panel dashboard. Kibana Lens (Bài 14) tạo đúng các aggregation kiểu này dưới nền, nên hiểu chúng giúp bạn debug dashboard chậm.

  1. Ba loại aggregation là gì? Mỗi loại tương ứng với khái niệm SQL nào?
  2. Vì sao aggregation đọc từ doc_values thay vì inverted index?
  3. Khác biệt giữa calendar_interval và fixed_interval? Vì sao cần time_zone?
  4. Vì sao terms aggregation trên nhiều shard có thể sai số? Giảm sai số bằng cách nào?
  5. Khi nào dùng composite thay cho terms?
  6. Viết pipeline aggregation tương đương SQL HAVING SUM(total) > 10000.
  7. Vì sao không nên dùng cardinality cho báo cáo tài chính?

Checklist Kiến Thức

  • ☐ Phân biệt metric, bucket, pipeline aggregation
  • ☐ Dùng avg/sum/stats/cardinality/percentiles
  • ☐ Dùng terms, histogram, date_histogram, range, filters
  • ☐ Lồng sub-aggregation và sort bucket theo metric con
  • ☐ Dùng derivative, cumulative_sum, moving_fn, bucket_selector
  • ☐ Phân trang bucket bằng composite + after_key
  • ☐ Hiểu sai số của terms, cardinality, percentiles
  • ☐ Áp dụng size: 0, filter trước, request cache

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Aggregate trên field text: lỗi fielddata disabled. Dùng sub-field .keyword.
  • Quên size: 0: tốn công fetch hits không dùng đến.
  • date_histogram không đặt time_zone: bucket ngày cắt theo UTC, số liệu theo ngày lệch.
  • terms size: 100000: ngốn heap, dễ chạm search.max_buckets. Dùng composite để duyệt hết.
  • Coi cardinality là số chính xác: đó là ước lượng, có sai số khi vượt precision_threshold.
  • Lồng quá nhiều tầng terms: số bucket nhân lên theo cấp số nhân.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Thiết kế mapping với keyword và numeric cho mọi field cần group hoặc tính toán
  • Đặt size: 0 và filter khoảng thời gian cho mọi request dashboard
  • Dùng composite cho export và đồng bộ dữ liệu, terms cho top-N hiển thị
  • Đặt time_zone rõ ràng cho date_histogram
  • Cân nhắc random_sampler cho phân tích xu hướng trên dữ liệu rất lớn
  • Với số liệu tổng hợp lặp lại, cân nhắc transform hoặc rollup sang index tóm tắt (Bài 23)
