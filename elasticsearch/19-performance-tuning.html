Performance Tuning

Sizing phần cứng, JVM heap, tối ưu indexing và search, profile, benchmark với Rally

Nguồn: Elastic — Tune for Indexing Speed, Elastic — Tune for Search Speed

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Chọn phần cứng phù hợp với từng loại node. Cấu hình JVM heap và hệ điều hành đúng khuyến nghị. Tăng throughput indexing bằng bulk, refresh interval, replica và mapping. Giảm latency search bằng thiết kế query, mapping và cache. Tìm query chậm bằng Profile API và slow log. Đo trước và sau khi tuning bằng Rally theo một phương pháp có kiểm soát.

Phần Cứng

Thành phầnKhuyến nghịLý do
DiskSSD/NVMe local cho hot tier. Tránh network storage có latency caoRefresh, merge, search đều phụ thuộc I/O ngẫu nhiên
RAM64 GB là cỡ phổ biến cho data node hotKhoảng một nửa cho heap, nửa còn lại cho filesystem cache
CPUNhiều core hơn là xung nhịp cao hơnThread pool search và write chạy song song theo số core
MạngLatency thấp, ổn định giữa các node trong cùng clusterReplication và cluster state đi qua transport layer
  • Master node dedicated cần ít tài nguyên (ví dụ 2–4 CPU, 8–16 GB RAM) nhưng cần ổn định
  • Coordinating node cần CPU và heap cho việc gom kết quả, aggregation lớn
  • Warm/cold dùng disk lớn và rẻ hơn, tỷ lệ dữ liệu trên RAM cao hơn hot nhiều lần
Không chia cluster qua nhiều datacenter xa nhau Một cluster trải qua hai region có latency cao sẽ chậm mọi thao tác ghi và dễ mất ổn định khi mạng chập chờn. Dùng cluster riêng ở mỗi region và kết nối bằng CCS/CCR (Bài 22). Trải qua nhiều availability zone trong cùng region thì phù hợp (Bài 10).

JVM Heap & Hệ Điều Hành

Heap

  • Đặt -Xms bằng -Xmx, tránh JVM co giãn heap lúc chạy
  • Không quá khoảng 50% RAM: phần còn lại cho filesystem cache, nơi Lucene đọc segment
  • Không quá ngưỡng compressed oops (thường khoảng 26–31 GB). Vượt ngưỡng này, con trỏ 64-bit làm heap lớn hơn nhưng chứa được ít đối tượng hơn
  • Từ ES 7.11, nếu không đặt heap, Elasticsearch tự tính theo role và RAM. Mặc định này phù hợp với đa số trường hợp
# Kiểm tra compressed oops đang bật
GET /_nodes/jvm?filter_path=nodes.*.name,nodes.*.jvm.using_compressed_ordinary_object_pointers,nodes.*.jvm.mem.heap_max
Tư duy cốt lõi Heap lớn hơn không làm Elasticsearch nhanh hơn. Search nhanh nhờ filesystem cache giữ segment trong RAM. Heap 64 GB trên máy 64 GB RAM khiến OS không còn chỗ cache, mọi search phải đọc disk.

# Chuẩn bị index cho load ban đầu
PUT /bulk-load/_settings
{ "index": { "refresh_interval": "-1", "number_of_replicas": 0 } }

# ... bulk load ...

# Trả lại cấu hình bình thường
PUT /bulk-load/_settings
{ "index": { "refresh_interval": "30s", "number_of_replicas": 1 } }
POST /bulk-load/_refresh
Dấu hiệu indexing đã chạm trần Thread pool write có rejected tăng, client nhận 429, hoặc indexing latency tăng mà rate đứng yên. Khi đó thêm client không giúp gì: cần thêm node, giảm tải trên mỗi document, hoặc giảm số shard ghi đồng thời trên mỗi node.

Tối Ưu Search

Thiết kế query

  • Điều kiện không ảnh hưởng thứ hạng đặt vào filter (Bài 08): bỏ qua scoring và được cache
  • Chỉ lấy field cần: _source filtering, hoặc "_source": false kèm fields
  • size: 0 khi chỉ cần aggregation (Bài 09)
  • Tránh wildcard đầu chuỗi, regex, script query trên tập dữ liệu lớn
  • Tránh deep pagination bằng from/size, dùng search_after + PIT
  • Dùng track_total_hits: false (hoặc giới hạn số) khi UI không cần tổng chính xác

Thiết kế dữ liệu

  • Denormalize thay vì nested và join khi có thể
  • Tính sẵn lúc index thay vì tính lúc search: ví dụ lưu field price_range: "200-500" thay vì range aggregation mỗi lần
  • Range query trên số thường dùng như ID, mã: map thành keyword nếu chỉ cần exact match
  • Index sorting (index.sort.field) khi luôn sort theo một field cố định: search có thể dừng sớm
  • Custom routing theo tenant hoặc user (Bài 03): query chỉ chạm một shard
  • Force merge index chỉ đọc xuống ít segment (Bài 12)
# Index sắp sẵn theo thời gian giảm dần, phù hợp với "log mới nhất"
PUT /events-sorted
{
  "settings": { "index": { "sort.field": "@timestamp", "sort.order": "desc" } },
  "mappings": { "properties": { "@timestamp": { "type": "date" } } }
}

# Hiệu quả cache theo node
GET /_nodes/stats/indices/query_cache,request_cache,fielddata?human&filter_path=nodes.*.name,nodes.*.indices

# Xóa cache khi đo benchmark (không làm ở production đang chạy)
POST /my-index/_cache/clear
Làm request cache hoạt động Request cache dùng chính nội dung JSON của request làm khóa. Hai request giống nhau nhưng khác thứ tự field hoặc dùng now trong range sẽ không trúng cache. Làm tròn thời gian (now-1d/d) giúp các request trong cùng một khoảng thời gian dùng chung cache.

Profile API & Slow Log

Profile API

GET /products/_search
{
  "profile": true,
  "query": {
    "bool": {
      "must":   [ { "match": { "name": "laptop" } } ],
      "filter": [ { "wildcard": { "sku": "*-PRO" } } ]
    }
  }
}
# Response: profile.shards[].searches[].query[] cho từng clause:
#   type, description, time_in_nanos, breakdown (build_scorer, next_doc, score...)
# Clause tốn nhiều thời gian nhất là nơi cần sửa đầu tiên

Kibana Dev Tools có Search Profiler hiển thị kết quả profile dạng cây trực quan. Profile thêm overhead, chỉ dùng khi điều tra.

Slow log

PUT /products/_settings
{

  "index.search.slowlog.threshold.query.info": "500ms",
  "index.search.slowlog.threshold.fetch.warn": "1s",
  "index.indexing.slowlog.threshold.index.warn": "5s",
  "index.search.slowlog.include.user": true
}

Rally

Rally là công cụ benchmark chính thức của Elastic. Rally chạy một track (bộ dữ liệu + chuỗi thao tác) lên cluster và báo cáo throughput, latency theo percentile, lỗi.

# Cài Rally (Python 3.8+)
pip install esrally

# Chạy track có sẵn lên cluster đã có (không để Rally tự dựng cluster)
esrally race --track=http_logs --target-hosts=es01:9200 \
  --pipeline=benchmark-only \
  --client-options="use_ssl:true,verify_certs:true,ca_certs:'./certs/ca/ca.crt',basic_auth_user:'elastic',basic_auth_password:'${ELASTIC_PASSWORD}'" \
  --test-mode   # chạy với tập dữ liệu nhỏ để thử; bỏ đi khi benchmark thật

# So sánh hai lần chạy
esrally list races
esrally compare --baseline=<race-id-1> --contender=<race-id-2>
TrackMô phỏng
http_logsWeb server log, nặng về indexing và aggregation
geonamesDữ liệu địa lý, đa dạng loại query
nyc_taxisDữ liệu số lớn, aggregation
pmcFull-text search trên văn bản dài

Với workload riêng, tạo track tùy chỉnh từ index có sẵn: esrally create-track --track=my-track --target-hosts=... --indices="orders-*", rồi thêm các query thật của ứng dụng vào phần challenge.

Không benchmark trên production đang phục vụ Rally được thiết kế để tạo tải tối đa. Chạy trên cluster đang phục vụ người dùng sẽ gây sự cố thật. Dùng cluster riêng có cấu hình giống production.

Phương Pháp Tuning

Đo baseline → Tìm điểm nghẽn → Đổi MỘT thứ → Đo lại → Giữ hoặc hoàn tác
  1. Xác định mục tiêu bằng con số: "p95 search < 200 ms ở 500 req/s", "index 50.000 doc/s"
  2. Đo baseline với workload giống thật, chạy đủ lâu để vượt qua giai đoạn warm-up
  3. Tìm điểm nghẽn: CPU, disk I/O, heap/GC, mạng, hay thread pool. Tối ưu thứ không phải điểm nghẽn không có tác dụng
  4. Đổi một biến mỗi lần để biết chính xác thay đổi nào có hiệu quả
  5. Ghi lại mỗi lần thử: cấu hình, kết quả, kết luận

Bài Lab: Benchmark Với Rally, Tối Ưu Từ Baseline

Bước 1: Baseline

pip install esrally
source .env
RALLY_OPTS="use_ssl:true,verify_certs:true,ca_certs:'$PWD/certs/ca/ca.crt',basic_auth_user:'elastic',basic_auth_password:'$ELASTIC_PASSWORD'"

esrally race --track=http_logs --test-mode --pipeline=benchmark-only \
  --target-hosts=localhost:9200 --client-options="$RALLY_OPTS" \
  --user-tags="run:baseline"

Ghi lại từ báo cáo: Median Throughput của task index-append, 90th percentile latency của các task query, và error rate.

Bước 2: Thử một thay đổi về indexing

Track http_logs hỗ trợ tham số để đổi cấu hình index mà không cần sửa track:

esrally list tracks   # xem các track-param được hỗ trợ của http_logs

esrally race --track=http_logs --test-mode --pipeline=benchmark-only \
  --target-hosts=localhost:9200 --client-options="$RALLY_OPTS" \
  --track-params="number_of_replicas:0,refresh_interval:'30s',bulk_size:5000" \
  --user-tags="run:tuned-indexing"

Bước 3: So sánh

esrally list races
esrally compare --baseline=<id-baseline> --contender=<id-tuned-indexing>

Bước 4: Profile một query chậm

curl $AUTH "$ES/logs-*/_search?pretty" -H 'Content-Type: application/json' -d '{
  "profile": true, "size": 0,
  "query": { "bool": { "filter": [ { "wildcard": { "request": "*images*" } } ] } }
}' | python -c "import sys,json; r=json.load(sys.stdin); [print(q['type'], q['time_in_nanos']//1000000, 'ms') for s in r['profile']['shards'] for q in s['searches'][0]['query']]"
Tên index và field phụ thuộc track Track http_logs tạo các index logs-* với field request. Nếu version track của bạn khác, xem GET /_cat/indices?v và mapping để đổi tên tương ứng. Kết quả --test-mode chỉ dùng để học cách đọc báo cáo, không dùng để kết luận về performance thật.
Xác minh thành công Bảng esrally compare cho thấy throughput indexing thay đổi bao nhiêu phần trăm so với baseline khi tắt replica và giãn refresh interval. Profile chỉ ra clause wildcard chiếm phần lớn thời gian query. Bạn đã có quy trình đo, đổi, đo lại thay cho việc đổi cấu hình theo cảm tính.

Checklist Kiến Thức

  • ☐ Chọn phần cứng theo role của node
  • ☐ Cấu hình heap, tắt swap, kiểm tra compressed oops
  • ☐ Áp dụng bulk, refresh interval, replica 0 cho load ban đầu
  • ☐ Viết query dùng filter, _source filtering, size: 0 đúng chỗ
  • ☐ Hiểu 4 loại cache và cách làm request cache hiệu quả
  • ☐ Dùng Profile API và slow log
  • ☐ Chạy Rally và so sánh hai lần chạy

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Heap = RAM: không còn filesystem cache, search phải đọc disk liên tục.
  • Tuning khi chưa đo: không biết thay đổi có tác dụng hay làm tệ đi.
  • Quên bật lại replica và refresh sau bulk load: index không có bản sao, dữ liệu mới không hiện trong search.
  • Network storage chậm cho hot tier: mọi thao tác bị giới hạn bởi latency của disk.
  • Benchmark bằng một query lặp lại: kết quả chỉ đo hiệu quả của cache, không phản ánh tải thật.
  • Bật fielddata để sort trên text: tốn heap, dễ chạm circuit breaker.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Để Elasticsearch tự tính heap trừ khi có lý do và số liệu cụ thể
  • SSD local cho hot tier, đủ RAM ngoài heap cho filesystem cache
  • Bật slow log với ngưỡng hợp lý trên mọi index quan trọng
  • Tạo track Rally từ dữ liệu và query thật của ứng dụng
  • Benchmark lại sau mỗi lần nâng cấp version hoặc đổi phần cứng
  • Ghi lại mọi thay đổi cấu hình cùng số liệu trước và sau
