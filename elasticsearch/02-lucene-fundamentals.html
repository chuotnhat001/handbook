Apache Lucene — Nền Tảng Search Engine

Inverted index, segments, merge policy, scoring BM25 — hiểu Lucene là hiểu cách Elasticsearch tìm kiếm

Nguồn: Apache Lucene Docs, Elastic — Near Real-Time Search

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Hiểu Apache Lucene là gì và vai trò nền tảng của nó trong Elasticsearch. Giải thích cấu trúc inverted index. Hiểu segments, immutability và merge process. Nắm được cơ chế scoring: TF-IDF và BM25. Liên hệ Lucene concepts với ES operations.

Kiến Thức Tiên Quyết

  • Bài 01: Hệ Thống Phân Tán — Hiểu sharding (mỗi shard = 1 Lucene index)
  • Data structures cơ bản — Hash maps, sorted arrays, trees
  • Khái niệm full-text search — Tìm kiếm trong nội dung text, không chỉ exact match

Lucene Là Gì

Apache Lucene là một thư viện search engine mã nguồn mở viết bằng Java, được Doug Cutting tạo ra năm 1999. Lucene không phải là một ứng dụng hoàn chỉnh — nó là thư viện cấp thấp mà các hệ thống khác xây dựng phía trên.

Mối quan hệ với Elasticsearch

LuceneElasticsearch
Thư viện Java (library)Distributed system chạy trên nhiều nodes
Xử lý 1 index trên 1 máyQuản lý nhiều shards trên nhiều máy
Không có REST APIREST API hoàn chỉnh
Không có replicationAutomatic replication
Single-threaded indexingConcurrent, distributed indexing
Tư duy cốt lõi Mỗi Elasticsearch shard = 1 Lucene index. Khi bạn hiểu Lucene hoạt động thế nào, bạn hiểu được behavior của từng shard — và từ đó hiểu toàn bộ cluster.

Ví Dụ Từ Đời Sống — Index Sách Giáo Khoa

Mở bất kỳ cuốn sách giáo khoa nào, lật đến trang cuối — bạn sẽ thấy phần "Chỉ mục" (Index):

Algorithm .......... 12, 45, 78, 156
Binary search ...... 23, 89
Database ........... 34, 67, 112, 145
Hash table ......... 56, 90

Thay vì đọc từng trang để tìm "Database", bạn tra chỉ mục → nhảy thẳng đến trang 34, 67, 112, 145. Đây chính xác là cách inverted index hoạt động:

  • Term = từ khóa ("Database")
  • Postings list = danh sách vị trí (trang 34, 67, 112, 145 → trong Lucene là document IDs)

Khác biệt: index sách giáo khoa được tạo thủ công bởi người biên soạn. Lucene tự động xây dựng inverted index cho mọi từ trong mọi document.

Inverted Index

Inverted index là cấu trúc dữ liệu cốt lõi cho full-text search. Gọi là "inverted" vì nó đảo ngược mối quan hệ: thay vì "document → chứa từ nào", nó lưu "từ → xuất hiện trong documents nào".

Cấu trúc

Giả sử có 3 documents:

Doc 1: "Elasticsearch is a search engine"
Doc 2: "Lucene powers Elasticsearch search"
Doc 3: "A distributed search engine"

Inverted index sẽ là:

TermDocument FrequencyPostings List [doc_id: positions]
a2[1: [3]], [3: [0]]
distributed1[3: [1]]
elasticsearch2[1: [0]], [2: [2]]
engine2[1: [5]], [3: [3]]
is1[1: [1]]
lucene1[2: [0]]
powers1[2: [1]]
search3[1: [4]], [2: [3]], [3: [2]]

Thành phần của Inverted Index

  • Term Dictionary — Sorted list tất cả unique terms, thường lưu dạng FST (Finite State Transducer) để tìm nhanh
  • Postings List — Mỗi term có danh sách document IDs chứa term đó, kèm frequency và positions
  • Stored Fields — Giá trị gốc của document (để trả về trong kết quả, như _source trong ES)
  • Doc Values — Column-oriented storage cho sorting và aggregations

Tại sao inverted index nhanh?

Tìm kiếm "search engine" chỉ cần:

  1. Lookup term "search" → postings [1, 2, 3]
  2. Lookup term "engine" → postings [1, 3]
  3. Intersect → [1, 3] (cả hai term đều xuất hiện)

Complexity: O(log N) cho mỗi term lookup + O(min(m,n)) cho intersection. Không cần scan toàn bộ documents.

Segments & Immutability

Lucene index không phải là một cấu trúc dữ liệu duy nhất — nó là tập hợp nhiều segments.

Segment là gì?

Mỗi segment là một mini inverted index hoàn chỉnh và immutable (không thể thay đổi sau khi tạo).

New Docs → In-Memory Buffer → Refresh (1s) → New Segment → Searchable!

Tại sao immutable?

  • Không cần locking — Nhiều threads đọc đồng thời mà không conflict
  • OS file system cache hiệu quả — File không đổi → OS cache được maximize
  • Compression tốt hơn — Dữ liệu cố định → nén tối ưu một lần
  • Đơn giản hóa concurrency — Write-once, read-many pattern

Hệ quả của immutability

OperationCách Lucene thực hiện
Insert documentThêm vào segment mới
Delete documentĐánh dấu "deleted" trong .del file (không xóa thật)
Update document= Delete cũ + Insert mới (2 operations)

Near Real-Time Search

ES mặc định refresh mỗi 1 giây — tạo segment mới từ buffer, làm documents mới searchable. Đây là "near real-time" (NRT): document indexed nhưng chưa searchable cho đến lần refresh tiếp theo.

# Kiểm tra refresh interval
GET /my-index/_settings?filter_path=**.refresh_interval

# Force refresh ngay lập tức
POST /my-index/_refresh

Commit Point

Commit point = file liệt kê tất cả segments hiện tại. Khi Lucene "commit" (flush), dữ liệu được persist xuống disk an toàn. Trước commit, dữ liệu ở translog (write-ahead log) để phòng crash.

Merge Policy

Vấn đề: mỗi giây tạo 1 segment → tích lũy hàng nghìn segments nhỏ → search phải scan qua tất cả segments → chậm dần.

Segment Merging

Lucene tự động merge các segments nhỏ thành segments lớn hơn trong background:

Seg 1 (10 docs) + Seg 2 (15 docs) + Seg 3 (12 docs) → Merged Seg (37 docs)

Lợi ích của merge

  • Giảm số segments → search nhanh hơn
  • Loại bỏ deleted documents thực sự (reclaim disk space)
  • Tối ưu hóa cấu trúc index

Tiered Merge Policy (ES default)

ES sử dụng tiered merge: segments được nhóm theo size tier, merge xảy ra trong cùng tier. Configurable:

PUT /my-index/_settings
{
  "index.merge.policy.max_merged_segment": "5gb",
  "index.merge.policy.segments_per_tier": 10
}

Force Merge

Cho read-only indices (ví dụ: logs cũ), có thể force merge xuống 1 segment:

POST /old-logs-2024/_forcemerge?max_num_segments=1
Cảnh báo Không force merge trên index đang actively write — sẽ tạo segments rất lớn, tốn I/O và có thể ảnh hưởng performance.

TF-IDF — Scoring Cổ Điển

Khi search trả về nhiều documents, cần xếp hạng (ranking) theo mức độ liên quan (relevance). TF-IDF là thuật toán scoring cổ điển:

Term Frequency (TF)

Từ xuất hiện nhiều lần trong document → document đó likely liên quan hơn.

TF(t, d) = số lần term t xuất hiện trong document d

Inverse Document Frequency (IDF)

Từ xuất hiện ít documents → có giá trị phân biệt cao hơn. "the" xuất hiện khắp nơi → ít giá trị. "elasticsearch" xuất hiện ít → rất có giá trị.

IDF(t) = log(N / DF(t))
// N = tổng documents, DF = số documents chứa term t

Kết hợp

Score = TF(t, d) × IDF(t)

Ví dụ: document có "elasticsearch" 5 lần (TF cao) và "elasticsearch" chỉ xuất hiện trong 10/10000 documents (IDF cao) → score rất cao.

BM25 — Scoring Hiện Đại (ES Default)

BM25 (Best Matching 25) là cải tiến của TF-IDF, trở thành scoring mặc định của Elasticsearch từ version 5.0.

Cải tiến chính

Vấn đề TF-IDFBM25 giải quyết
TF tăng không giới hạn (từ xuất hiện 100 lần → score gấp 100 lần so với 1 lần)TF bão hòa (saturation) — sau ngưỡng nhất định, thêm occurrences ít ảnh hưởng
Không normalize theo document lengthDocument ngắn chứa term = relevant hơn document dài chứa cùng term

Công thức BM25

score(D, Q) = Σ IDF(qi) × [ f(qi, D) × (k1 + 1) ] / [ f(qi, D) + k1 × (1 - b + b × |D|/avgdl) ]

Trong đó:
- f(qi, D) = term frequency của qi trong document D
- |D| = document length
- avgdl = average document length
- k1 = saturation parameter (default 1.2)
- b = length normalization (default 0.75)

Tham số có thể tune

  • k1 (default 1.2) — Kiểm soát TF saturation. k1 cao = TF ảnh hưởng nhiều hơn. k1=0 = bỏ qua TF hoàn toàn.
  • b (default 0.75) — Kiểm soát document length normalization. b=1 = normalize hoàn toàn. b=0 = bỏ qua length.
PUT /my-index
{
  "settings": {
    "index.similarity.default": {
      "type": "BM25",
      "k1": 1.2,
      "b": 0.75
    }
  }
}

Yêu cầu

Elasticsearch cluster đang chạy (dùng cluster từ Lab Bài 01 hoặc single-node Docker).

Bước 1: Xem analyzer xử lý text

POST _analyze
{
  "analyzer": "standard",
  "text": "Elasticsearch is a Distributed search Engine!"

# → lowercase, loại bỏ punctuation

PUT /lucene-lab

{"index":{"_id":"1"}}
{"title":"Elasticsearch is a search engine","body":"Built on Apache Lucene"}
{"index":{"_id":"2"}}
{"title":"Lucene powers search","body":"Lucene is the core library"}
{"index":{"_id":"3"}}

GET /lucene-lab/_segments

Xác minh thành công Bạn đã thấy: analyzer tokenize text thế nào, BM25 scoring giải thích relevance ra sao, và segments merge lại với nhau. Đây là nền tảng cho mọi search operation trong ES.

Câu Hỏi Ôn Tập

  1. Inverted index "inverted" so với cái gì? Tại sao cấu trúc này nhanh cho full-text search?
  2. Tại sao Lucene segments là immutable? Liệt kê 3 lợi ích.
  3. Khi bạn "delete" document trong ES, chuyện gì thực sự xảy ra ở Lucene level?
  4. Giải thích sự khác biệt giữa refresh và flush trong ES.
  5. BM25 cải tiến gì so với TF-IDF? Tại sao cần TF saturation?
  6. Khi nào nên dùng force merge? Khi nào không?
  7. 1 ES index với 5 primary shards = bao nhiêu Lucene indices?

Checklist Kiến Thức

  • ☐ Giải thích được inverted index hoạt động thế nào
  • ☐ Hiểu term dictionary, postings list, stored fields, doc values
  • ☐ Mô tả được lifecycle: buffer → refresh → segment → merge
  • ☐ Hiểu immutability và hệ quả (delete = mark, update = delete + insert)
  • ☐ Giải thích TF-IDF và tại sao BM25 tốt hơn
  • ☐ Biết tune k1 và b trong BM25
  • ☐ Map được ES concepts (index, shard, refresh, flush) sang Lucene

Lỗi Thường Gặp

Những hiểu lầm phổ biến:
  • Nghĩ delete xóa dữ liệu ngay — Thực tế chỉ mark deleted, dữ liệu bị xóa thật khi segment merge
  • Refresh = flush — Refresh chỉ mở segment mới cho search (in-memory). Flush = commit to disk (durability).
  • Quá nhiều force merge trên active index — Gây I/O storm, block indexing, ảnh hưởng cluster
  • Bỏ qua BM25 parameters — Defaults hoạt động tốt 90% cases, nhưng biết tune k1/b quan trọng cho specific use cases
  • Nghĩ indexing = searchable ngay lập tức — Cần đợi refresh (default 1s). Đây là "near real-time", không phải "real-time"

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Hiểu refresh interval: giảm xuống nếu cần near-real-time hơn, tăng lên nếu ưu tiên indexing throughput
  • Force merge chỉ trên read-only indices (time-based data đã rollover)
  • Dùng _analyze API để debug tokenization trước khi tạo complex mappings
  • Sử dụng explain: true để hiểu tại sao document A ranked cao hơn B
  • Mặc định BM25 params (k1=1.2, b=0.75) tốt cho hầu hết cases — chỉ tune khi có evidence cụ thể
