Index Lifecycle Management (ILM)

Hot → warm → cold → frozen → delete, rollover, data tiers — tự động hóa vòng đời dữ liệu time-series

Nguồn: Elastic — ILM, Elastic — Data Tiers

Mục Tiêu Học Tập

Sau khi hoàn thành bài này, bạn sẽ: Hiểu vì sao dữ liệu time-series cần quản lý vòng đời. Nắm kiến trúc data tiers (hot, warm, cold, frozen). Biết các phase và action của ILM. Cấu hình rollover qua alias hoặc data stream. Viết, áp dụng và theo dõi một ILM policy hoàn chỉnh.

Kiến Thức Tiên Quyết

  • Bài 02: Lucene — Force merge, segment
  • Bài 11: Shard Allocation — Shard sizing, shrink, data tiers

Vì Sao Cần ILM

Log, metric, sự kiện bảo mật đều là dữ liệu time-series: ghi liên tục, được truy vấn nhiều khi còn mới, ít khi truy vấn khi đã cũ, và cuối cùng bị xóa. Giữ mọi thứ trên SSD đắt tiền là lãng phí. Quản lý thủ công thì dễ quên và dễ sai.

Index Lifecycle Management (ILM) tự động hóa vòng đời: tạo index mới khi index hiện tại đủ lớn, chuyển index cũ sang phần cứng rẻ hơn, tối ưu chúng cho chế độ chỉ đọc, và xóa khi hết hạn lưu giữ.

Tư duy cốt lõi Giá trị truy vấn của dữ liệu giảm theo thời gian, nên chi phí lưu trữ cũng nên giảm theo. ILM biến chính sách lưu giữ (retention policy) thành cấu hình mà cluster tự thực thi.

Data Tiers

TierRoleĐặc điểmPhần cứng điển hình
Hotdata_hotĐang ghi, truy vấn nhiều nhấtSSD/NVMe nhanh, CPU mạnh
Warmdata_warmKhông còn ghi, vẫn truy vấn thường xuyênDisk lớn hơn, chậm hơn
Colddata_coldHiếm khi truy vấn, chấp nhận chậmDisk rẻ. Có thể dùng searchable snapshot
Frozendata_frozenRất hiếm khi truy vấnDữ liệu nằm ở object storage (S3...), node chỉ giữ cache
Contentdata_contentDữ liệu không theo thời gian (catalog, user)Như hot
# elasticsearch.yml
node.roles: [ data_hot, data_content ]   # node hot
node.roles: [ data_warm ]                 # node warm
node.roles: [ data_frozen ]               # node frozen

# Index mới mặc định nằm ở tier ưu tiên sau
GET /logs-app/_settings?filter_path=**._tier_preference
# → "index.routing.allocation.include._tier_preference": "data_hot"

Khi index chuyển phase, ILM tự cập nhật _tier_preference (action migrate) và shard được di chuyển sang tier tương ứng.

Phases & Actions

Hot → Warm → Cold → Frozen → Delete

Mỗi phase có min_age: thời gian tối thiểu kể từ khi index được tạo, hoặc kể từ khi rollover nếu index đã rollover. Phase nào không khai báo thì được bỏ qua.

ActionPhase dùng đượcTác dụng
rolloverHotTạo index ghi mới khi đạt ngưỡng kích thước/tuổi/số doc
set_priorityHot, Warm, ColdƯu tiên recovery cho index quan trọng sau sự cố
forcemergeHot (sau rollover), WarmGộp segment, giảm dung lượng và tăng tốc search
shrinkHot (sau rollover), WarmGiảm số primary shard
readonlyHot, Warm, ColdChặn ghi
allocateWarm, ColdĐổi số replica, đặt allocation rule
migrateWarm, ColdChuyển sang tier tương ứng (tự động mặc định)
searchable_snapshotHot, Cold, FrozenChuyển index thành searchable snapshot trên repository
downsampleHot, Warm, ColdGộp metric theo khoảng thời gian (TSDS, Bài 23)
deleteDeleteXóa index

Rollover

Rollover tạo index mới khi index đang ghi đạt ngưỡng. Ứng dụng luôn ghi vào cùng một tên (alias hoặc data stream), không cần biết index thật phía sau.

Điều kiệnÝ nghĩa
max_primary_shard_sizeMột primary shard đạt kích thước (khuyến nghị dùng, ví dụ 50gb)
max_ageIndex đạt tuổi (ví dụ 30d)
max_docs / max_primary_shard_docsĐạt số document

Rollover xảy ra khi đạt bất kỳ điều kiện nào. Từ ES 8.4, index rỗng không bị rollover (tránh sinh index trống). ILM kiểm tra điều kiện theo chu kỳ indices.lifecycle.poll_interval (mặc định 10 phút).

Cách 1: Data stream (khuyến nghị cho dữ liệu append-only)

PUT /_index_template/logs-app-template
{
  "index_patterns": ["logs-app-*"],
  "data_stream": {},
  "template": {
    "settings": { "index.lifecycle.name": "logs-policy" }
  }
}

# Data stream tự tạo khi ghi document đầu tiên
POST /logs-app-default/_doc
{ "@timestamp": "2026-10-28T08:00:00Z", "message": "started" }
# Index thật phía sau: .ds-logs-app-default-2026.10.28-000001

Cách 2: Index alias (khi cần update/delete theo ID)

PUT /_index_template/orders-template
{
  "index_patterns": ["orders-*"],
  "template": {
    "settings": {
      "index.lifecycle.name": "orders-policy",
      "index.lifecycle.rollover_alias": "orders"
    }
  }
}

# Bootstrap index đầu tiên. Tên phải kết thúc bằng số để rollover tăng dần
PUT /orders-000001
{ "aliases": { "orders": { "is_write_index": true } } }
Data stream hay alias? Data stream chỉ cho phép thêm mới (op_type=create) và bắt buộc có @timestamp. Phù hợp với log, metric, event. Nếu cần cập nhật document theo ID thường xuyên, dùng alias. Chi tiết về data stream ở Bài 23.

Viết Policy

PUT /_ilm/policy/logs-policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": { "max_primary_shard_size": "50gb", "max_age": "1d" },
          "set_priority": { "priority": 100 }
        }
      },
      "warm": {
        "min_age": "7d",
        "actions": {
          "shrink": { "number_of_shards": 1 },
          "forcemerge": { "max_num_segments": 1 },
          "allocate": { "number_of_replicas": 1 },
          "set_priority": { "priority": 50 }
        }
      },
      "cold": {
        "min_age": "30d",
        "actions": {
          "allocate": { "number_of_replicas": 0 },
          "set_priority": { "priority": 0 }
        }
      },
      "delete": {
        "min_age": "90d",
        "actions": { "delete": {} }
      }
    }
  }
}
Replica 0 ở cold Giảm replica xuống 0 tiết kiệm một nửa dung lượng, nhưng mất node là mất dữ liệu cold của node đó. Chỉ làm vậy khi đã có snapshot (Bài 20), hoặc dùng action searchable_snapshot để snapshot trên object storage đóng vai trò bản sao.

min_age tính từ thời điểm rollover. Với policy trên, một index sinh ngày 1/10 và rollover ngày 2/10 sẽ vào warm khoảng ngày 9/10 và bị xóa khoảng ngày 31/12. Như vậy dữ liệu cũ nhất được giữ khoảng 90 ngày cộng thời gian index còn là write index.

Áp Dụng & Theo Dõi

# Index đang ở phase/action/step nào, có lỗi không
GET /logs-app-default/_ilm/explain
GET /orders-*/_ilm/explain?only_errors=true

# Trạng thái ILM toàn cluster
GET /_ilm/status

# Sau khi sửa nguyên nhân lỗi, cho index chạy lại step bị lỗi
POST /orders-000003/_ilm/retry

# Gắn policy cho index đã có sẵn
PUT /old-logs-*/_settings
{ "index.lifecycle.name": "logs-policy" }

Các trường cần đọc trong _ilm/explain: phase, action, step, age, và step_info nếu có lỗi.

Sửa policy đang dùng Khi cập nhật policy, index đang ở giữa một phase vẫn chạy theo định nghĩa phase đã cache lúc vào phase đó. Thay đổi chỉ áp dụng từ phase kế tiếp. Muốn áp dụng ngay, cần đổi policy cho index và có thể phải chuyển step thủ công.

Các lỗi ILM hay gặp

LỗiNguyên nhân
rollover alias ... can not be foundThiếu rollover_alias hoặc alias chưa trỏ write index
Kẹt ở step check-migrationKhông có node thuộc tier đích (ví dụ chưa có node data_warm)
Shrink không tiến triểnKhông có node đủ disk để chứa một bản sao của mọi shard
Index không bao giờ rolloverIndex rỗng, hoặc chưa đạt điều kiện và chưa qua chu kỳ poll

Bài Lab: ILM Cho Logs (30d Hot, 90d Warm, 365d Cold)

Chuẩn bị

Dùng cluster lab Bài 10–11 (security tắt, chỉ dùng cục bộ). Lab Docker không chia tier, nên tạm tắt action migrate để ILM không kẹt ở bước chờ node warm/cold.

Bước 1: Tạo policy theo yêu cầu thật

curl -X PUT "http://localhost:9200/_ilm/policy/lab-logs-policy" -H 'Content-Type: application/json' -d '{
  "policy": { "phases": {
    "hot":    { "actions": { "rollover": { "max_primary_shard_size": "50gb", "max_age": "30d" } } },
    "warm":   { "min_age": "30d",  "actions": { "migrate": { "enabled": false }, "forcemerge": { "max_num_segments": 1 } } },
    "cold":   { "min_age": "120d", "actions": { "migrate": { "enabled": false }, "allocate": { "number_of_replicas": 0 } } },
    "delete": { "min_age": "485d", "actions": { "delete": {} } }
  }}}'
# 30 ngày hot → 90 ngày warm (đến ngày 120) → 365 ngày cold (đến ngày 485) → xóa

Bước 2: Phiên bản rút gọn để quan sát trong vài phút

# Kiểm tra ILM mỗi 10 giây thay vì 10 phút (chỉ cho lab)
curl -X PUT "http://localhost:9200/_cluster/settings" -H 'Content-Type: application/json' \
  -d '{"persistent":{"indices.lifecycle.poll_interval":"10s"}}'

curl -X PUT "http://localhost:9200/_ilm/policy/lab-fast-policy" -H 'Content-Type: application/json' -d '{
  "policy": { "phases": {
    "hot":    { "actions": { "rollover": { "max_docs": 5 } } },
    "warm":   { "min_age": "1m", "actions": { "migrate": { "enabled": false }, "forcemerge": { "max_num_segments": 1 } } },
    "delete": { "min_age": "3m", "actions": { "delete": {} } }
  }}}'

curl -X PUT "http://localhost:9200/_index_template/lab-logs" -H 'Content-Type: application/json' -d '{
  "index_patterns": ["lab-logs-*"],
  "data_stream": {},
  "template": { "settings": { "index.lifecycle.name": "lab-fast-policy", "number_of_replicas": 1 } }
}'

Bước 3: Ghi dữ liệu và quan sát

for i in $(seq 1 12); do
  curl -s -o /dev/null -X POST "http://localhost:9200/lab-logs-app/_doc" -H 'Content-Type: application/json' \
    -d "{\"@timestamp\":\"$(date -u +%FT%TZ)\",\"msg\":\"event $i\"}"
  sleep 15
done

# Ở terminal khác, chạy lặp lại
curl "http://localhost:9200/_data_stream/lab-logs-app?filter_path=**.indices.index_name"
curl "http://localhost:9200/lab-logs-app/_ilm/explain?filter_path=**.index,**.phase,**.action,**.step"

Bước 4: Dọn dẹp

curl -X PUT "http://localhost:9200/_cluster/settings" -H 'Content-Type: application/json' \
  -d '{"persistent":{"indices.lifecycle.poll_interval":null}}'
curl -X DELETE "http://localhost:9200/_data_stream/lab-logs-app"
Xác minh thành công Data stream sinh thêm backing index mỗi khi đủ 5 document. Index cũ lần lượt chuyển sang warm (force merge) rồi bị xóa sau khoảng 3 phút kể từ rollover. Bạn đã thấy ILM vận hành toàn bộ vòng đời mà không cần thao tác tay.

Câu Hỏi Ôn Tập

  1. Kể tên 5 data tier và loại dữ liệu phù hợp với từng tier.
  2. min_age được tính từ thời điểm nào khi index đã rollover?
  3. Vì sao max_primary_shard_size thường tốt hơn max_age làm điều kiện rollover chính?
  4. Khi nào chọn data stream, khi nào chọn index alias để rollover?
  5. Vì sao index có thể kẹt ở step check-migration?
  6. Đặt number_of_replicas: 0 ở cold phase có rủi ro gì? Giảm rủi ro bằng cách nào?
  7. Sửa ILM policy có ảnh hưởng ngay tới index đang ở giữa phase không?

Checklist Kiến Thức

  • ☐ Giải thích được hot/warm/cold/frozen/content tier
  • ☐ Biết các action chính và phase mà chúng dùng được
  • ☐ Cấu hình rollover qua data stream và qua alias
  • ☐ Viết ILM policy với min_age đúng yêu cầu retention
  • ☐ Theo dõi và retry bằng _ilm/explain, _ilm/retry
  • ☐ Chẩn đoán các lỗi ILM phổ biến

Lỗi Thường Gặp

Những lỗi phổ biến:
  • Tính min_age từ ngày tạo thay vì ngày rollover: dữ liệu bị giữ lâu hơn hoặc xóa sớm hơn dự kiến.
  • Có phase warm nhưng không có node warm: ILM kẹt ở bước migrate.
  • Bootstrap index alias không có số ở cuối tên: rollover thất bại.
  • Đặt poll_interval 10s ở production: master tốn tài nguyên vô ích. Chỉ dùng cho lab.
  • Không có snapshot trước khi xóa: dữ liệu hết hạn retention mất vĩnh viễn. Cân nhắc yêu cầu pháp lý.
  • Index template không gắn policy: index mới sinh ra không có ILM và tích tụ mãi mãi.

Best Practices & Tài Liệu Tham Khảo

Best Practices

  • Gắn ILM policy qua index template, không gắn tay từng index
  • Rollover chủ yếu theo max_primary_shard_size: 50gb, kèm max_age làm giới hạn trên
  • Force merge và shrink ở warm, khi index đã thôi ghi
  • Kết hợp ILM với SLM (Bài 20) để dữ liệu có snapshot trước phase delete
  • Theo dõi _ilm/explain?only_errors=true trong hệ thống monitoring (Bài 18)
