Gherkin Scenarios

Ngôn ngữ đặc tả hành vi cho Behavior-Driven Development (BDD)

Nguồn: Cucumber Official Docs — Gherkin Reference
Tư duy cốt lõi Gherkin không phải test code — đây là living documentation viết bằng ngôn ngữ tự nhiên để cả developer lẫn business stakeholder đều đọc được, đồng thời có thể tự động hóa thành executable specifications.

Gherkin là Domain-Specific Language (DSL) dùng để viết acceptance tests theo phong cách BDD. Mỗi file .feature mô tả một tính năng, mỗi Scenario là một ví dụ cụ thể minh họa business rule.

Mục đích & Lợi ích

  • Cầu nối Business-Tech: PO, BA, Dev, QA đều đọc hiểu được requirements
  • Living Documentation: Tài liệu luôn đồng bộ với code vì nó chính là test
  • Executable Specifications: Cucumber đọc file .feature → tìm step definitions → chạy test
  • Đa ngôn ngữ: Hỗ trợ 70+ ngôn ngữ tự nhiên (khai báo # language: vi)
.feature file → Step Definitions → Automated Tests → Living Docs

Feature

Từ khóa bắt đầu mỗi file .feature. Tên Feature xuất hiện trong test reports.

Feature: Đăng nhập người dùng
  Cho phép users đăng nhập vào hệ thống
  với email và password đã đăng ký.

  Scenario: ...

Mô tả phía dưới Feature là tùy chọn (free-form text), không được parse bởi Cucumber.

Scenario

Mỗi Scenario = một test case độc lập, chạy trong trạng thái riêng biệt. Còn gọi là Example.

Scenario: Đăng nhập thành công với credentials hợp lệ
  Given user đang ở trang đăng nhập
  When user nhập email "user@example.com" và password "secret"
  Then user được redirect đến dashboard
  And hiển thị message "Chào mừng trở lại"

Given — When — Then

Ba từ khóa chính tạo nên cấu trúc của mỗi Scenario:

KeywordVai tròVí dụ
Given Thiết lập context/precondition (trạng thái ban đầu) Given giỏ hàng có 3 sản phẩm
When Hành động của user hoặc sự kiện xảy ra When user click "Thanh toán"
Then Kết quả mong đợi (observable outcome) Then hiển thị trang xác nhận
Lưu ý kỹ thuật Cucumber không phân biệt Given/When/Then khi match step definitions — chỉ là convention để tăng tính đọc hiểu. Không dùng chéo (Given ở vị trí Then) để tránh nhầm lẫn.

And & But

Dùng để nối tiếp các step cùng loại, giúp Scenario dễ đọc hơn:

Scenario: Thanh toán với voucher
  Given user đã đăng nhập
  And giỏ hàng có 2 sản phẩm
  And tổng tiền là 500,000đ
  When user nhập mã voucher "SAVE20"
  And user click "Áp dụng"
  Then tổng tiền giảm còn 400,000đ
  But phí vận chuyển không thay đổi

* có thể thay thế bất kỳ keyword nào khi liệt kê:

Scenario: Tạo đơn hàng với nhiều sản phẩm
  Given các sản phẩm sau trong giỏ:
    * Laptop Dell
    * Chuột Logitech
    * Bàn phím cơ
  When user xác nhận đơn hàng
  Then đơn hàng được tạo thành công

Background

Chứa các steps dùng chung, chạy trước MỖI Scenario trong Feature.

Feature: Quản lý tài khoản

  Background:
    Given database đã được khởi tạo
    And admin user đã tồn tại trong hệ thống

  Scenario: Thay đổi password
    When admin thay đổi password
    Then password mới được lưu

  Scenario: Cập nhật profile
    When admin cập nhật email
    Then email mới được lưu
Khi nào dùng Background
  • Khi có 3+ Scenarios cùng share preconditions
  • Giữ Background ngắn gọn (2-4 steps)
  • Không đặt logic phức tạp — khó debug khi Scenario fail

Scenario Outline (Data-Driven)

Template để chạy cùng một Scenario với nhiều bộ dữ liệu khác nhau:

Scenario Outline: Tính giá sau thuế
  Given sản phẩm có giá <gia_goc>
  When áp dụng thuế suất <thue_suat>%
  Then giá cuối là <gia_cuoi>

  Examples:
    | gia_goc | thue_suat | gia_cuoi |
    | 100     | 10        | 110      |
    | 200     | 5         | 210      |
    | 50      | 20        | 60       |
  • <tên_cột> là placeholder được thay thế bởi giá trị trong Examples
  • Mỗi hàng trong Examples = một Scenario riêng biệt được tạo ra
  • Có thể có nhiều khối Examples với Tags khác nhau

Rule (Gherkin 6+)

Nhóm các Scenarios liên quan đến cùng một business rule:

Feature: Thanh toán đơn hàng

  Rule: Không cho phép thanh toán khi giỏ hàng rỗng
    Scenario: Giỏ hàng rỗng
      Given giỏ hàng không có sản phẩm
      When user click "Thanh toán"
      Then hiển thị lỗi "Giỏ hàng trống"

  Rule: Áp dụng discount cho thành viên VIP
    Background:
      Given user có status VIP

    Scenario: Mua sản phẩm thường
      Given sản phẩm giá 100,000đ
      When user thêm vào giỏ
      Then giá hiển thị 90,000đ

Tags

Dùng để filter, nhóm tests và tích hợp CI/CD:

@smoke @regression
Feature: Thanh toán

  @happy-path
  Scenario: Thanh toán thành công
    ...

  @edge-case @slow
  Scenario: Thanh toán với voucher hết hạn
    ...

Filter khi chạy: cucumber --tags "@smoke and not @slow"

Tags thường gặp

TagMục đích
@smokeTest nhanh, chạy sau mỗi deploy
@regressionTest đầy đủ
@wipWork in progress, chưa có step definition
@skipBỏ qua tạm thời
@slowTest chạy lâu, tách riêng

Data Tables

Truyền dữ liệu dạng bảng vào một step:

Scenario: Thêm nhiều sản phẩm vào giỏ hàng
  Given các sản phẩm sau đây có trong catalog:
    | tên            | giá   | tồn kho |
    | Laptop Dell    | 25000 | 10      |
    | Chuột Logitech | 500   | 50      |
  When user thêm "Laptop Dell" vào giỏ hàng
  Then giỏ hàng có 1 sản phẩm
Data Table vs Examples
  • Data Table: Argument của một step, không tạo thêm Scenarios
  • Examples: Mỗi hàng tạo ra một Scenario riêng biệt

Doc Strings

Truyền text nhiều dòng vào step:

Scenario: Gửi email thông báo
  Given template email như sau:
    """
    Kính gửi {name},

    Đơn hàng #{order_id} đã được xác nhận.
    Vui lòng kiểm tra email để theo dõi.

    Trân trọng.
    """
  When hệ thống gửi email
  Then email được gửi thành công

Dùng """ hoặc backticks. Indentation bên trong được preserve.

Nguyên tắc viết tốt

DO — Nên làm
  • Mỗi Scenario độc lập, không phụ thuộc thứ tự chạy
  • Dùng ngôn ngữ business, không dùng UI-specific language
  • Given = state (danh từ), When = action (động từ), Then = observable outcome
  • Tên Scenario ngắn gọn, mô tả đúng behavior
  • Giữ Scenario dưới 10 steps
DON'T — Tránh
  • Viết UI steps: "click button ID='btn-123'" → fragile
  • Background phức tạp → khó trace khi fail
  • Scenario phụ thuộc nhau (Scenario 2 cần Scenario 1 chạy trước)
  • Scenario Outline với chỉ 1-2 rows
  • Assertions trong Given hoặc When

Anti-patterns thường gặp

Anti-patternVấn đềCách fix
And I click the blue button UI coupling, fragile Dùng intent: "user xác nhận thanh toán"
Scenario 20+ steps Khó đọc, khó debug Tách thành nhiều Scenarios nhỏ
Dùng data từ Scenario trước Test không độc lập Mỗi Scenario tự setup data
"Given I am logged in" lặp lại Redundant Dùng Background hoặc hooks
Then kiểm tra database trực tiếp Test biết quá nhiều về implementation Kiểm tra qua UI/API observable

Ví dụ hoàn chỉnh

# language: en
@ecommerce
Feature: Quản lý giỏ hàng
  Cho phép user thêm, xóa sản phẩm và xem tổng tiền

  Background:
    Given user đã đăng nhập với tài khoản "buyer@test.com"
    And catalog có sản phẩm "Laptop" giá 20,000,000đ

  @happy-path
  Scenario: Thêm sản phẩm vào giỏ hàng
    Given giỏ hàng đang trống
    When user thêm "Laptop" vào giỏ hàng
    Then giỏ hàng hiển thị 1 sản phẩm
    And tổng tiền là 20,000,000đ

  @happy-path
  Scenario Outline: Áp dụng discount code
    Given giỏ hàng có tổng tiền 100,000đ
    When user nhập mã giảm giá "<ma>"
    Then tổng tiền giảm còn <gia_cuoi>đ

    Examples:
      | ma        | gia_cuoi |
      | SAVE10    | 90,000   |
      | SAVE20    | 80,000   |
      | INVALID   | 100,000  |

  @edge-case
  Scenario: Thêm sản phẩm hết hàng
    Given sản phẩm "Laptop" đã hết hàng
    When user cố thêm "Laptop" vào giỏ hàng
    Then hiển thị thông báo "Sản phẩm tạm hết hàng"
    But giỏ hàng vẫn trống
