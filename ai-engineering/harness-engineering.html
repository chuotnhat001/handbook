Harness Engineering

Kỷ luật xây dựng infrastructure để LLM hoạt động như autonomous agent đáng tin cậy

Tổng hợp từ: Martin Fowler, Viblo, arXiv, và nhiều nguồn khác

Harness Engineering là kỷ luật thiết kế môi trường, tooling, constraints, và feedback loops xung quanh AI agents — tất cả mọi thứ ngoại trừ bản thân model. Nếu prompt engineering là nghệ thuật "nói chuyện" với model, thì harness engineering là nghệ thuật xây dựng "môi trường sống" cho model.

Tư duy cốt lõi "The model provides the intelligence. The harness provides reliability." — Độ tin cậy của AI agent không đến từ model mạnh hơn, mà đến từ hệ thống bao quanh nó. Engineer nên đầu tư vào harness thay vì chờ model cải tiến.
Agent = Model + Harness

Công thức này được đúc kết bởi Mitchell Hashimoto (2026). Trong đó:

  • Model = khả năng reasoning (suy luận, sinh text, hiểu ngữ cảnh)
  • Harness = toàn bộ infrastructure bao quanh: system prompts, tools, retrieval, memory, state, safety, context, orchestration

Ba tầng kỹ thuật xây dựng theo tầng

Harness Engineering là tầng cao nhất trong 3 tầng kỹ thuật AI Engineering:

TầngTập trung vàoThời kỳ
Prompt EngineeringĐịnh nghĩa vai trò, mục tiêu, hành vi, output format2022–2023
Context EngineeringCung cấp thông tin, dữ liệu, tools, retrieval mechanisms2024–2025
Harness EngineeringTạo môi trường cho autonomous work: state, execution, permissions, feedback, verification loops2025–nay

Harness engineering không thay thế các tầng trước — nó bao quanh và kết hợp chúng thành một reliable runtime.

Tại sao Harness quan trọng hơn Model?

LLM thuần túy là stateless — mỗi session bắt đầu lại từ đầu. Không có harness, agent thất bại theo các pattern lặp đi lặp lại:

  • Context overflow — Cố hoàn thành toàn bộ task trong 1 lượt, hết context ở giữa
  • Victory declaration bias — Tuyên bố thành công sau khi thấy progress một phần mà không verify
  • Context degradation — Chất lượng suy giảm khi token window đầy dần
  • Hallucinated tool calls — Gọi tool với parameters không hợp lệ
  • Lost progress — Mất toàn bộ progress khi fail, buộc restart từ đầu
Insight từ thực tế Cùng một model với basic scaffold (23 turns) đạt 23% task completion trên SWE-bench. Với optimized scaffold (250 turns, advanced harness) đạt 45%+. Delta = 22 điểm — không phải từ model mới mà từ harness tốt hơn.

Case Study: LangChain Terminal-Bench 2.0

Harness changes alone (không thay model) đưa coding agent từ Top 30 → Top 5. Minh chứng trực tiếp cho "reliability comes from the system, not the model".

Case Study: OpenAI Field Report

3 engineers ship ~1 triệu dòng code dùng Codex agents. Thành công nhờ tập trung vào harness quality, không chờ model cải tiến.

Vòng lặp cốt lõi (The Core Loop)

Mọi agent đều hoạt động theo vòng lặp cơ bản:

Plan → Act → Observe → Verify → Repair → Continue

Hay dưới dạng ReAct pattern: Reason → Act → Observe → Repeat

Các điều kiện dừng:

  • Goal achieved — task hoàn thành thành công
  • Turn limit exceeded — chống infinite loop
  • Budget exhausted — cost/token/time control

Hai loại Controls: Guides vs Sensors

Theo Birgitta Böckeler (Martin Fowler), có hai loại control bổ sung nhau trong harness:

LoạiKhi nàoMục đíchVí dụ
Guides (Feedforward) Trước khi agent hành động Định hướng để tăng chất lượng ngay lần đầu (first-attempt quality) AGENTS.md files, skill activation rules, architecture principles, templates
Sensors (Feedback) Sau khi agent hành động Quan sát kết quả, phát hiện vấn đề, kích hoạt self-correction Tests, linters, security scanners, code review agents, runtime signals

Kết hợp cả hai tạo thành một vòng kiểm soát khép kín (closed control loop).

Nguyên tắc thiết kế Guides

  • Lean — Giữ AGENTS.md dưới 60 dòng, đóng vai trò table of contents, không phải encyclopedia
  • Progressive disclosure — Activate skills và knowledge on-demand thay vì load tất cả upfront
  • Intent-based — Đặt tên tools theo intent (không theo implementation)

Nguyên tắc thiết kế Sensors

  • Success is silent — Chỉ surface lỗi, kết quả pass không cần báo cáo
  • Fail loudly — Return errors mà agent có thể act upon
  • Structured output — Return predictable, parseable results

Computational vs Inferential Controls

Cả Guides và Sensors đều có thể được implement theo hai chế độ:

Chế độĐặc điểmTốc độVí dụ
Computational Deterministic, có thể lặp lại chính xác Nhanh (milliseconds–seconds) Tests, linters, type checkers, static analysis, complexity metrics
Inferential Phân tích ngữ nghĩa qua AI, non-deterministic Chậm hơn (seconds–minutes) Code review agents, semantic validation, judgment calls
Nguyên tắc: Computational trước, Inferential sau Chạy deterministic checks trước (fast, cheap) trên mọi change. Reserve semantic checks (model-based) cho harder scenarios mà computational checks không cover được.

Ba nhóm Regulation Categories

Theo Martin Fowler, harness cần kiểm soát 3 nhóm chất lượng:

1. Maintainability Harness

Mục tiêu: Kiểm soát chất lượng nội tại của code (internal code quality)

  • Computational tools: Phân tích cấu trúc — complexity metrics, test coverage, style violations, dependency analysis
  • Inferential tools: Đánh giá semantic (ít tin cậy hơn computational)
  • Điểm mạnh: Computational sensors rất đáng tin cậy cho structural issues

2. Architecture Fitness Harness

Mục tiêu: Đảm bảo code phù hợp với đặc điểm kiến trúc của ứng dụng

  • Kết hợp guides và sensors: performance requirements đi kèm performance tests
  • Logging standards đi kèm debugging guidance
  • Cân bằng giữa định nghĩa đặc tính (guide) và kiểm chứng (sensor)

3. Behaviour Harness

Mục tiêu: Đảm bảo code làm đúng những gì được yêu cầu về mặt hành vi

  • Thách thức nhất trong ba nhóm
  • Cách tiếp cận hiện tại: functional specifications (feedforward) + AI-generated test suites (feedback)
  • Thường phải bổ sung manual testing
  • Gap lớn: Chưa có cách đáng tin cậy để xây dựng genuine confidence về behavioral correctness

Bảy thành phần bắt buộc của một Harness

Kiến trúc 3 tầng chi tiết

Layer 1 — Information Layer

Quản lý dữ liệu và tool permissions:

  • Vector storage cho long-term memory
  • Context construction qua retrieval pipelines
  • Tool registry định nghĩa callable actions
  • Progressive disclosure — summary trước, chi tiết chỉ khi cần

Layer 2 — Control Loop

Điều khiển luồng thực thi:

  • Thực thi model, observe output, check goal conditions
  • Retry logic, timeouts, error routing
  • Escalation to humans khi cần
  • Coordinate multi-agent workflows
  • Loop retry với failure context hoặc thử alternative tools

Layer 3 — Guardrail Layer

Đảm bảo an toàn và tuân thủ:

  • Validate outputs trước khi deliver cho user/system
  • Enforce content safety, data handling, compliance
  • Block, modify, hoặc escalate non-compliant outputs
  • Audit trail cho regulatory requirements

Guardrail Placement

Vị tríMục đích
Pre-promptInjection prevention — ngăn prompt injection
Post-responseCompliance validation — baseline cho enterprise
In-loopEssential cho multi-step autonomous sequences

Architecture Patterns

Pattern A: Single-Agent Supervisor

User → Harness → Model → Tools → Result

Một model loop với tools và memory. Phù hợp với bounded tasks như customer support agent, single-domain tasks.

Khi nào dùng: Bắt đầu với pattern này. Chỉ chuyển sang multi-agent khi một agent đơn chứng minh không đủ.

Pattern B: Initializer-Executor Split

Initializer → Executor 1 → Executor 2 → Executor N
  • Initializer phase: Tạo scaffolding, progress logs, baseline conditions một lần
  • Executor/Worker phase: Verify baseline trước khi add incremental work — mỗi session làm một feature, test, commit

Mỗi executor session không cần prior context — progress được externalize ra files và commit history.

Pattern C: Multi-Agent Coordination

Orchestrator → Researcher → Writer → Reviewer

Specialist agents, harness quản lý handoffs giữa các steps. Phù hợp với complex projects.

Cảnh báo: Premature Multi-Agent Thêm agents trước khi một agent đơn chứng minh không đủ là anti-pattern. Multi-agent adds tokens, latency, và failure surfaces.

Context Rot — Vấn đề cốt lõi

Khi token count vượt ngưỡng model-specific, accuracy của model giảm đáng kể — đặc biệt trong việc áp dụng instructions được đặt ở đầu context.

"The goal is not to show the model everything. It is to give it the right working set at the right time and allow it to dynamically make decisions to manage its own context."
Số liệu thực tế Sau khi chuyển sang semantic retrieval + progressive disclosure, average context giảm từ 480,000 xuống 62,000 tokens trong khi accuracy cải thiện đáng kể.

Compaction Strategies

Khi context window gần đầy, harness phải compact để giữ model hoạt động hiệu quả.

Trigger Mechanisms

  • Token threshold: 85–90% của context window
  • Pre-compaction warning: 75% capacity — bắt đầu proactive compaction ở đây, không đợi 100%

Các kỹ thuật Compaction

1. LLM-Powered Summarization:

  1. Gửi conversation cho model với structured sections (primary request, concepts, errors, fixes, pending tasks)
  2. Model sinh scratchpad phân tích (stripped trước khi lưu) + final summary
  3. Summary trở thành synthetic message prepend vào conversation tail còn giữ lại

2. Sliding Window Eviction:

  1. Bắt đầu remove oldest messages (10–30% mỗi pass)
  2. Tăng % mỗi iteration đến khi usage drop dưới threshold
  3. Preserve messages gần nhất là priority cao nhất

3. Tool Result Clamping:

  • Per-result caps: 2KB–50KB mỗi tool output
  • Aggregate caps: 200K chars mỗi message
  • Oversized results: Move to disk + compressed 2KB preview + reference để fetch sau
Safety Rules khi Compaction Không bao giờ truncate giữa một tool-call/result pair. Preserve tool-call boundaries. Pre-compaction state flush — để agent persist memory trước khi bị xóa.

Subagent Context Isolation

Subagents hoạt động như "Context Firewalls" — ngăn context của main agent bị nhiễm bởi exploratory noise.

Subagents nhận isolated sessions — không có parent conversation history:

  • Chỉ nhận task string làm user message
  • Filtered workspace context (minimal allowlist approach)
  • Restricted tool set phù hợp với delegated task
  • Results trả về dưới dạng summary cho parent

Khi nào dùng: Delegate research và exploration tasks cho isolated agents với fresh context windows.

Năm Failure Patterns phổ biến nhất

Theo nghiên cứu, 5 patterns này chiếm 88% production failures:

#PatternTriệu chứngFix
1 Context Rot Token overflow làm giảm accuracy Progressive disclosure + semantic retrieval
2 State Loss Không có persistence giữa sessions → inconsistent behavior Externalize state vào files và version control
3 Absent Guardrails Compliance violations, PII exposure reach users Multi-layer guardrails ở pre-prompt, post-response, in-loop
4 Brittle Tool Integration Tool failures do rate limits, timeouts, schema variations Design error handling trước khi viết integration code
5 No Feedback Loop Các lỗi giống nhau lặp lại không có prevention Capture failure patterns → embed vào harness environment
Meta-principle "Anytime an agent makes a mistake, engineer a solution so it never makes that mistake again." — Mỗi lỗi là cơ hội cải thiện harness, không phải lý do đổ lỗi cho model.

Anti-Patterns cần tránh

1. Model Over-Trust

Dùng model capability để bù đắp cho missing tools hoặc bad harness. Intelligence trong model không thể compensate cho missing hands (tools). Wrapper thường quyết định production reliability, không phải raw weights.

2. Excessive Agency / Weak Controls

Single weak controls không đủ ngăn harm. Unbounded capabilities cần layered constraints, structured permissions, và human review gates trên irreversible actions.

3. Context Bloat

Cramped context = slow + less accurate. Progressive loading và compaction bảo toàn window capacity cho reasoning thay vì storage.

4. Graph-first Thinking

Predefine states và transitions quá sớm. Câu hỏi không còn là "Which node should the agent move to next?" mà là "What environment should I create so the model can complete this independently?"

5. Premature Multi-Agent

Thêm agents trước khi một agent đơn chứng minh không đủ. Multi-agent adds tokens, latency, và failure surfaces. Bắt đầu bằng một capable agent.

6. No Vendor Abstraction

Lock vào provider-specific SDK calls. Nên abstract model như pluggable component — keep context assembly, tool dispatch, guardrail logic, state management trong harness layer, độc lập với provider.

Harnessability — Không phải codebase nào cũng dễ kiểm soát

Theo Martin Fowler, "harnessability" là mức độ một codebase cho phép harness hoạt động hiệu quả.

Yếu tố thuận lợi

  • Strongly typed languages — Enable type-checking sensors
  • Clear module boundaries — Enable architectural rules
  • Consistent frameworks — Giảm agent uncertainty
  • Topology consistency — Nhất quán cấu trúc
  • Clear conventions — Quy ước rõ ràng
  • Defined tech stacks — Tech stack xác định

Thách thức

  • Legacy systems với technical debt — Thách thức lớn nhất, nhưng lại cần harness nhất
  • Greenfield teams có thể bake harnessability vào từ đầu
  • Legacy teams phải retrofit — khó hơn nhiều

Ashby's Law áp dụng vào Harness

"A regulator must have at least as much variety as the system it governs."

Commit vào specific topologies giúp thu hẹp không gian output của agent → harness toàn diện trở nên khả thi hơn. Diversity of outputs = difficulty of control: càng nhiều loại code agent có thể tạo ra, càng khó kiểm soát đầy đủ.

Practical Patterns

1. Context Management Pattern

Treat context window như working memory budget — tài nguyên khan hiếm:

  • Progressive disclosure: Activate skills và knowledge on-demand thay vì load tất cả upfront
  • Ngăn context pollution: Duy trì agent performance bằng cách chỉ load cần thiết
  • Prompt caching: Reuse stable prefixes across multiple calls — giảm latency và cost đáng kể

2. Mechanical Enforcement Pattern

Enforce architectural invariants qua automated linters và structural tests, không micromanage agent qua prompt:

  • Layered dependencies — không cho phép import ngược tầng
  • Structured logging — enforce format nhất quán
  • Naming conventions — tự động kiểm tra naming rules

3. Feature Lists for Long-Running Work

Break large tasks thành verifiable milestones, track trong structured files:

  1. Initializer agent tạo feature list
  2. Coding agents làm tuần tự từng feature
  3. Mark complete chỉ sau khi verification pass

4. Repository-Local Knowledge

Mọi thứ agent cần phải discoverable và version-controlled trong repo:

Undocumented knowledge = không tồn tại với agent

5. Self-Verification Pattern

Agent chạy tests, inspect outputs, đọc logs để confirm results:

  • Không trust claims — verify bằng actual execution
  • Package compilation/test failures → route back to model (self-correction loop)

6. Keep Quality Left

Phân phối checks dọc theo timeline phát triển dựa trên cost và speed:

  • Fast controls (linters, basic review) → chạy pre-commit hoặc pre-integration
  • Expensive controls (mutation testing, detailed review) → chạy post-integration trong pipelines

Mục tiêu: Bắt vấn đề càng sớm càng rẻ.

7. The Steering Loop

Con người liên tục cải thiện harness khi phát hiện vấn đề tái diễn:

  • Agents có thể hỗ trợ xây dựng custom controls
  • Viết structural tests, scaffold linters, generate rules từ patterns
  • Đây là vòng lặp học hỏi giữa human expertise và agent capabilities

Minimum Viable Harness

Để deploy production, cần tối thiểu:

  1. Clear system prompt và reliable tools
  2. Sandboxed code execution environment
  3. Filesystem cho state persistence
  4. Ít nhất một verification test
  5. Basic tracing từ ngày đầu

Scale theo thứ tự

  1. Memory tiers khi sessions vượt single window
  2. Evals và permissions
  3. Observability dashboards
  4. Orchestration chỉ khi một agent đơn chứng minh không đủ

Observability Requirements

Capture đủ để debug non-deterministic failures:

  • Mọi tool call với inputs và outputs
  • Model decisions tại mỗi turn
  • Correlate events across multi-step runs (OpenTelemetry-style call graphs)
  • Traces enable faithful reproduction của failing runs
  • Trajectory review xác định nơi reasoning diverged đầu tiên
