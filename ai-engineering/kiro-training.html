Kiro Training Guide

Tài liệu đào tạo sử dụng Kiro IDE — từ ý tưởng đến phần mềm có kiểm soát

Nguồn: kiro.dev — AWS, 2025
Tư duy cốt lõi SDLC là luật chơi. Vibe, Spec, AI-DLC là cách làm việc với AI. Mọi cách dùng AI đều phải nằm trong SDLC và chính sách nội bộ — AI không thay thế quy trình, AI hỗ trợ bạn trong quy trình.

Kiro là IDE được hỗ trợ bởi AI, ra mắt bởi AWS giữa năm 2025. Không chỉ gợi ý code như Copilot, Kiro có thể đọc và hiểu toàn bộ project, lên kế hoạch trước khi làm, thực hiện nhiều bước liên tiếp, và dừng lại hỏi bạn khi không chắc chắn.

Cách Tiếp Cận — 4 Bước

Hãy coi Kiro như một đồng nghiệp kỹ thuật mới — giao việc rõ ràng, đưa tài liệu, giới hạn phạm vi, kiểm tra kết quả.
1. Giao việc → 2. Đưa tài liệu → 3. Cho phép → 4. Kiểm tra
BướcCâu hỏiVí dụ
Giao việcCần đạt kết quả gì?Sửa bug, thêm feature, review code
Đưa tài liệuXem file/lỗi nào?Stack trace, file code, tài liệu yêu cầu
Cho phépĐược làm đến đâu?Supervised/Autopilot, file được sửa
Kiểm traBiết đúng bằng cách nào?Test pass, diff đúng ý, không side effect

Vibe Mode — Việc Nhỏ/Cục Bộ

VIBE Prompt → Kiro đề xuất → Review → Accept/Reject → Done

Không có approval gates — bạn review trực tiếp trong chat.

Dấu hiệu nhận biết:

  • Một module, ít file
  • Không đổi quy tắc nghiệp vụ
  • Dễ quay lại (reversible)
  • Không cần nhiều người thống nhất

Kiro Spec — Feature Vừa

SPEC Requirements → Design → Tasks → Execute

Có approval gates giữa mỗi phase.

Dấu hiệu nhận biết:

  • Có quy tắc/API/data model
  • Cần BA–Dev–QA thống nhất
  • Cần tài liệu để trace

Ví dụ trong ngân hàng:

Iterate On Specs

Requirements-First:

  1. Modify requirements.md trực tiếp hoặc qua chat
  2. Click Refine trên design.md → cập nhật design và tasks
  3. Sync Files trên tasks.md → map new requirements

Design-First:

  1. Update design.md trực tiếp hoặc request changes
  2. Ask Kiro regenerate requirements
  3. Sync Files → reflect architectural changes

#spec:user-authentication implement task 2.3

EARS Format — Viết Requirements Testable

WHEN [condition/trigger]
THE SYSTEM SHALL [behavior]

Ví dụ:

WHEN yêu cầu giao dịch có cùng idempotency key được gửi lại,
THE SYSTEM SHALL trả về kết quả ban đầu và không ghi nợ lần hai.

AI-DLC — Sáng Kiến Lớn

AI-DLC 5 Phases — 33 Stages — 14 Agents

Methodology cấu trúc AI-assisted software development thành các phases có thể lặp lại và trace được.

Dấu hiệu nhận biết:

  • Nhiều hệ thống/đội tham gia
  • Cần Business–Risk–Security–Ops

Thay vì dùng hàng chục narrow specialist agents, AI-DLC sử dụng 11 broadly capable domain experts tham gia across multiple stages.

Context Engineering — Công Thức OCCE

Prompt tốt chưa đủ. Context đúng mới tạo khác biệt. Hãy giao việc như một hợp đồng kỹ thuật nhỏ, không phải một lời ước.
OOutcome
Kết quả gì?
CContext
Dựa vào đâu?
CConstraints
Không được gì?
EEvidence
Chứng minh sao?
Thành phầnCâu hỏiVí dụ
OutcomeKết quả nào?Phân tích, sửa, thiết kế, review
ContextDựa vào đâu?File, lỗi, terminal, diff, policy
ConstraintsKhông được làm gì?Phạm vi, dependency, dữ liệu
EvidenceChứng minh ra sao?Test, lint, typecheck, diff summary

Context Providers

Folder#Folder:src/servicesCả thư mục
Problems#problemsDiagnostics hiện tại

Git Diff#git diffThay đổi chưa commit
Spec#spec:feature-nameInclude full spec context

Nguyên Tắc Context Tối Thiểu

Context tối thiểu cần thiết vừa tăng độ chính xác, vừa giảm rủi ro dữ liệu.
Nên làmLý do
Chỉ file liên quanFocus vào vấn đề
Dùng stack trace thay vì cả logGiảm noise
Mock data thay vì real dataBảo mật
Không nên làmRủi ro
Kéo cả folder lớnToken waste, confusion
Include secretsData leak
Include PIICompliance violation

Ví dụ Prompt OCCE

#terminal #File:PaymentLimitServiceTest.java

[Outcome]
Phân tích và sửa lỗi để PaymentLimitServiceTest pass.

[Context]
Dựa trên lỗi trong terminal và file test.

[Constraints]
Trước khi sửa, tóm tắt nguyên nhân và kế hoạch.
Chỉ sửa service/file test liên quan.
Không đổi dependency hoặc config.

[Evidence]
Chạy test mục tiêu. Báo kết quả, file đã đổi,
diff chính và rủi ro còn lại.

Hooks — Event-Driven Guardrails

Hooks là shell commands hoặc agent prompts thực thi tự động khi specific events xảy ra.

8 Hook Triggers

TriggerEventBlockable
PromptSubmitMessage sent to agentYes
AgentStopAgent finishes respondingNo
SessionStartNew session begins (IDE only)No
PreToolUseBefore tool executionYes
PostToolUseAfter tool executesNo
FileCreateAgent creates fileNo
FileSaveAgent saves/edits fileNo

File triggers chỉ respond với agent-initiated changes, không phải manual edits.

Hook Configuration

Location: .kiro/hooks/

{
  "version": "v1",
  "hooks": [{
    "name": "ESLint on TypeScript save",
    "trigger": "PostFileSave",
    "matcher": "\\.(ts|tsx)$",
    "action": {
      "type": "command",
      "command": "npx eslint --fix ${file}"
    },
    "timeout": 30,
    "enabled": true
  }]
}

Common Hook Use Cases

1. Lint sau khi save:

{ "trigger": "PostFileSave", "matcher": "\\.(ts|tsx)$",
  "command": "npx eslint --fix ${file}" }

2. Test sau khi sửa service:

{ "trigger": "PostFileSave", "matcher": "Service\\.java$",
  "command": "mvn test -Dtest=${fileName}Test" }

3. Block dangerous operations:

{ "trigger": "PreToolUse", "matcher": "git.*--force",
  "command": "echo 'Force push blocked by policy' && exit 1" }

4. Security scan:

{ "trigger": "PostFileSave", "matcher": "\\.(java|ts|js)$",
  "command": "semgrep --config=auto ${file}" }

Permission Model

Kiro sử dụng capability-based permissions model:

EffectBehavior
denyBlock always, không hỏi — deny wins
askPrompt user mỗi lần
allowProceed silently
"deny wins" — một deny rule ở bất kỳ scope nào sẽ block action, bất kể allow rules khác.

Permission Configuration

rules:
  # Allow common git commands
  - capability: shell
    match: ["git status", "git log *", "git diff *"]
    effect: allow

  # Block writes to sensitive files
  - capability: fs_write
    match: ["*.env", "*.key", "*.pem", "secrets/*"]
    effect: deny

  # Ask before running npm scripts
  - capability: shell
    match: ["npm run *"]
    effect: ask

Best Practices

Principle of Least Privilege:

# ❌ Bad - quá broad
- capability: shell
  match: ["*"]
  effect: allow

# ✅ Good - specific patterns
- capability: shell
  match: ["mvn test", "mvn verify", "npm test"]
  effect: allow

Deny Sensitive Patterns:

# Block dangerous commands
- capability: shell
  match: ["rm -rf *", "git push --force *", "DROP TABLE *"]
  effect: deny

# Block sensitive file writes
- capability: fs_write
  match: ["*.env*", "*.key", "*.pem", "*credentials*"]
  effect: deny
Headless/Unattended Mode Trong headless context, mọi "ask" effect trở thành deny. Không có interactive channel để prompt → safer default.

# File: .kiro/steering/testing.md
---
inclusion: always
---

# Testing Standards

## Test Pyramid
- Unit tests: 70% coverage minimum
- Integration tests: Critical paths only
- E2E tests: Happy path only

## Naming Convention
- Test methods: should_[expected]_when_[condition]
- Example: should_returnError_when_amountExceedsLimit

## Fixtures
- Use TestContainers for database
- Mock external APIs with WireMock
- Never use production data

## Commands
- Unit: `mvn test`
- Integration: `mvn verify -P integration`

Bài Tập 5: Permission Rules

Mục tiêu: Cấu hình permissions cho project

# File: .kiro/permissions.yaml
rules:
  # Allow common commands
  - capability: shell
    match: ["git status", "git log *", "mvn test", "npm test"]
    effect: allow

  # Block sensitive file writes
  - capability: fs_write
    match: ["*.env*", "*.key", "*.pem", "secrets/*"]
    effect: deny

  # Ask before npm install
  - capability: shell
    match: ["npm install *", "mvn dependency:*"]
    effect: ask
